## Story

As a **usuario**,
I want **subir un archivo CSV al chat con transacciones (ej. exportadas de mi banco) y que el bot las importe a Firefly III**,
so that **pueda cargar movimientos históricos o masivos sin registrarlos uno por uno**.

## Acceptance Criteria

<!-- LOCKED. -->

1. El bot acepta un archivo CSV adjunto al chat y, antes de importar nada, valida su formato (columnas esperadas, tipos de dato) — un archivo mal formado se rechaza con un mensaje claro de qué está mal, sin intentar una importación parcial.
2. Antes de ejecutar la importación, el bot muestra un resumen (cantidad de filas válidas, rango de fechas, monto total) y **pide confirmación explícita** (mismo criterio que 4.3) — importar en masa es, en la práctica, tan irreversible como cualquier acción destructiva si el usuario se equivoca de archivo.
3. Confirmada la importación, el bot reporta el resultado: cuántas transacciones se crearon con éxito y cuántas fallaron (con el motivo de cada falla, sin exponer el PAT).
4. Una importación se puede cancelar antes de confirmar sin que se haya creado ninguna transacción.
5. El archivo subido no queda persistido en disco del Bot Service más allá del tiempo necesario para procesarlo.
6. La operación usa el PAT del propio usuario — las transacciones importadas quedan en la cuenta de Firefly III de quien subió el archivo, nunca en la de otro.

## Tasks / Subtasks

- [ ] Implementar el resumen pre-importación y el flujo de confirmación (AC: #2, #4)
- [ ] Implementar la importación fila-por-fila contra el cliente REST de transacciones (reutilizando `firefly-client.ts` de 3.1 donde aplique) con reporte de éxitos/fallas (AC: #3, #6)
- [ ] Confirmar la limpieza del archivo temporal tras el procesamiento, éxito o error (AC: #5)

- El criterio de "importación masiva requiere confirmación explícita" extiende el mismo principio de la historia 4.3 (re-scope) a esta historia, aunque tampoco pasa por el MCP — el riesgo de un error masivo es análogo al de una acción irreversible individual, a mayor escala. - Falla parcial (algunas filas importan, otras no) es un resultado válido y esperado (AC #3) — no se implementa como todo-o-nada transaccional, ya que Firefly III no ofrece una transacción atómica multi-fila vía su API REST estándar. [Inference]

## Testing

<!-- LOCKED. -->

- **Approach:** Unitario para el parseo/validación de CSV (con archivos de prueba válidos e inválidos) y para el flujo de confirmación/importación (con el cliente REST de transacciones mockeado).
- **Key scenarios:** CSV válido completo; CSV con columnas faltantes (rechazado antes de importar); CSV con algunas filas inválidas dentro de un archivo mayormente válido (resumen pre-importación las excluye); confirmación y cancelación pre-importación; importación con éxitos y fallas mezcladas; archivo temporal limpiado tras el procesamiento.
- **Per-AC verification:** AC #1 → archivo mal formado rechazado sin ninguna llamada a Firefly III; AC #2 → resumen correcto mostrado y confirmación requerida antes de ejecutar; AC #3 → reporte final con conteo de éxitos/fallas y motivo, sin PAT; AC #4 → cancelación no crea ninguna transacción; AC #5 → verificación de que no queda el archivo tras el procesamiento; AC #6 → todas las transacciones creadas quedan en la cuenta del usuario que subió el archivo.
- **Fixtures / mocks:** archivos CSV de prueba (válido, con columnas faltantes, con filas parcialmente inválidas); mock del cliente REST de transacciones; mock de `getFile`.
- **Edge cases to cover:** archivo vacío (0 filas); archivo con una sola fila inválida entre miles válidas; archivo que no es un CSV en absoluto (ej. una imagen con extensión .csv); doble confirmación accidental (no importar dos veces).
