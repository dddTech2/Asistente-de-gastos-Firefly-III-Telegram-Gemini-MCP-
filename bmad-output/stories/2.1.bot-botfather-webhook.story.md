# 2.1: Crear bot en BotFather y configurar el webhook

**Story ID:** 2.1
**Epic:** 2 — Bot de Telegram (esqueleto)
**Slug:** bot-botfather-webhook
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As an **administrador del sistema (el desarrollador/operador)**,
I want **crear el bot en BotFather y dejar el webhook de Telegram configurado y verificado contra el Bot Service**,
so that **el sistema empiece a recibir mensajes de Telegram de forma segura, como base para toda la lógica del bot que viene después**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Existe un bot de Telegram creado vía `@BotFather`, con su token guardado fuera del control de versiones (`.env` / variable de entorno), no hardcodeado en el código.
2. El Bot Service expone un endpoint HTTP `POST /webhook/telegram` accesible públicamente vía HTTPS (a través del reverse proxy de Epic 0).
3. El webhook está registrado en la API de Telegram (`setWebhook`) apuntando a la URL pública del endpoint, con un `secret_token` configurado — Telegram no debe aceptar el webhook solo por conocer la URL.
4. El Bot Service valida en cada request entrante que el header `X-Telegram-Bot-Api-Secret-Token` coincide con el `secret_token` configurado; si no coincide, responde `401`/`403` y no procesa el update.
5. `getWebhookInfo` de la API de Telegram confirma que el webhook quedó registrado sin errores (`last_error_message` vacío tras una prueba manual).

## Tasks / Subtasks

- [ ] Crear el bot en `@BotFather` y obtener el token (AC: #1)
  - [ ] Guardar el token en `.env` / gestor de secretos, agregar `.env` a `.gitignore` si no está ya
  - [ ] Generar un `secret_token` propio (string aleatorio) para el webhook
- [ ] Scaffolding del Bot Service en Node.js + TypeScript con grammY o Telegraf (AC: #2)
  - [ ] Inicializar el proyecto (`package.json`, `tsconfig.json`, estructura de carpetas)
  - [ ] Levantar el servidor HTTP con el endpoint `POST /webhook/telegram`
- [ ] Middleware de validación del `secret_token` (AC: #4)
  - [ ] Leer el header `X-Telegram-Bot-Api-Secret-Token` y compararlo contra el valor configurado
  - [ ] Responder `401` y cortar el procesamiento si no coincide
- [ ] Registrar el webhook contra la API de Telegram (AC: #3)
  - [ ] Llamar `setWebhook` con la URL pública (HTTPS, vía reverse proxy de Epic 0) y el `secret_token`
- [ ] Verificar el registro del webhook (AC: #5)
  - [ ] Llamar `getWebhookInfo` y confirmar ausencia de errores

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** integración ligera (no unit-test puro, ya que el objetivo es validar el registro externo del webhook contra la API real de Telegram) + una prueba unitaria del middleware de validación del `secret_token`.
- **Key scenarios:** el bot existe y responde a `getMe`; el endpoint `POST /webhook/telegram` acepta un update simulado con el `secret_token` correcto; lo rechaza si el header falta o no coincide; `getWebhookInfo` no reporta errores tras `setWebhook`.
- **Per-AC verification:** AC #1 → confirmar manualmente que el token no aparece en el repo (grep del código fuente); AC #2 → request HTTP directo al endpoint desde fuera de la red local; AC #3 → respuesta exitosa de `setWebhook` vía API de Telegram; AC #4 → test unitario del middleware con header ausente/incorrecto/correcto; AC #5 → inspección de la respuesta de `getWebhookInfo`.
- **Fixtures / mocks:** payload de ejemplo de un Telegram `Update` (JSON) para simular el POST; variable de entorno de prueba con un `secret_token` distinto al real para probar el rechazo.
- **Edge cases to cover:** header `X-Telegram-Bot-Api-Secret-Token` ausente; header con valor incorrecto; `setWebhook` apuntando a una URL sin HTTPS (debe fallar/rechazarse); reintento de `setWebhook` si ya había un webhook previo registrado.
