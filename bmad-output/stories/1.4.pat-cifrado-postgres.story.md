# 1.4: PAT cifrado en Postgres vinculado a chat_id

**Story ID:** 1.4
**Epic:** 1 — Autenticación y multi-tenancy
**Slug:** pat-cifrado-postgres
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **desarrollador**,
I want **guardar el PAT de cada usuario cifrado en reposo en Postgres, vinculado a su `chat_id` de Telegram**,
so that **ningún dato sensible (la credencial que da acceso a los datos financieros de un usuario) quede en texto plano en la base de datos, cumpliendo el NFR de seguridad más crítico del sistema**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. La tabla `usuarios_autorizados` (creada en 1.1) se extiende con una columna `pat_cifrado` (y los metadatos de cifrado que hagan falta, ej. IV/nonce si el algoritmo lo requiere) vía una nueva migración — sin modificar ni recrear la migración original de 1.1.
2. Dado un PAT nuevo (entregado por el flujo de alta de 1.3), cuando se guarda, entonces en la base de datos aparece cifrado — una inspección directa de la fila en Postgres nunca muestra el PAT en texto plano.
3. Existe una función de descifrado que, dado un `chat_id`, retorna el PAT en texto plano únicamente en memoria, para uso inmediato por la capa que lo necesite (historia 1.5) — nunca se escribe a disco ni se loguea el resultado descifrado.
4. La clave de cifrado vive fuera del repositorio y fuera de la propia base de datos (variable de entorno / secreto gestionado), de forma que tener acceso de lectura a Postgres no sea suficiente por sí solo para recuperar los PAT.
5. Ningún log de la aplicación (incluyendo logs de error/stack traces) puede contener el PAT en texto plano, cifrado o no — se aplican los mismos criterios de higiene de logs definidos en la Definition of Done del proyecto.

## Tasks / Subtasks

- [ ] Crear migración que agrega la columna `pat_cifrado` (y metadatos de cifrado necesarios) a `usuarios_autorizados` (AC: #1)
- [ ] Implementar módulo de cifrado/descifrado simétrico (algoritmo autenticado, ej. AES-256-GCM vía el módulo `crypto` nativo de Node — no hay una elección explícita en la arquitectura, ver Dev Notes) (AC: #2, #3)
- [ ] Cargar la clave de cifrado desde variable de entorno / gestor de secretos, con validación de arranque (el servicio no debe iniciar si falta la clave) (AC: #4)
- [ ] Extender el repositorio `usuarios.repository.ts` (de 1.1) con `guardarPatCifrado(chatId, pat)` y `obtenerPatDescifrado(chatId)` (AC: #2, #3)
- [ ] Auditar los puntos de logging existentes (whitelist de 1.1, flujo de alta de 1.3) para confirmar que ninguno accidentalmente serializa el objeto de usuario completo (que ahora incluye `pat_cifrado`) (AC: #5)

Esto pasa de 'no aplica' a el requisito no funcional más importante del sistema." El cifrado del PAT es la defensa contra que una fuga de la base de datos (backup mal protegido, acceso no autorizado a Postgres) se traduzca directamente en acceso a los datos financieros de todos los usuarios. [Source: docs/plan/system-design-v2-multiusuario.md#1-requisitos-actualizados]
- La Definition of Done del proyecto es explícita y nombra el PAT directamente: "Si toca datos sensibles (PAT, credenciales), quedaron cifrados/fuera de logs." Esta historia es, literalmente, el cumplimiento de esa cláusula del DoD para el activo más sensible del sistema. [Source: docs/plan/backlog-scrum-completo.md#4-definition-of-done-dod]
- La arquitectura **no especifica** el algoritmo de cifrado concreto ni el mecanismo de gestión de la clave — solo exige que el PAT quede "cifrado en reposo". La elección de AES-256-GCM (autenticado, con nonce por fila) vía el módulo `crypto` nativo de Node, con la clave en una variable de entorno (`PAT_ENCRYPTION_KEY`) inyectada por Docker Compose/el gestor de secretos del host, es una decisión de implementación razonable dado el stack Node/TS + Docker Compose ya elegido, pero no está fijada por ningún documento fuente. [Inference]
- Esta historia **no** decide cómo rotar la clave de cifrado ni cómo re-cifrar PAT existentes ante una rotación — eso corresponde a la historia de rotación de secretos de Epic 8 (HU-33). [Inference — basado en que Epic 8 posee explícitamente "rotación y protección de secretos" como su alcance]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** Unitario para el módulo de cifrado/descifrado (round-trip con distintos PAT de prueba); integración con Postgres de prueba para confirmar que la columna almacenada nunca coincide con el PAT en texto plano; revisión estática/test de humo de los puntos de logging para confirmar que no serializan el campo `pat_cifrado` ni el PAT descifrado.
- **Key scenarios:** cifrar y luego descifrar un PAT devuelve el valor original exacto; dos cifrados del mismo PAT (en momentos distintos) producen ciphertexts distintos si el algoritmo usa nonce aleatorio (evita que un atacante compare valores cifrados entre usuarios); el servicio falla al arrancar si `PAT_ENCRYPTION_KEY` no está configurada; una fila leída directamente de Postgres (sin pasar por la capa de descifrado) no contiene el PAT en texto plano bajo ninguna inspección.
- **Per-AC verification:** AC #1 → test de migración confirma que la columna existe con el tipo esperado y que la migración de 1.1 no fue alterada; AC #2 → test de integración que guarda un PAT de prueba y lee la fila cruda de Postgres, confirmando que el valor no es igual (ni contiene como substring) el PAT original; AC #3 → test de round-trip cifrar→descifrar, y test de que la función de descifrado no escribe a ningún log/archivo; AC #4 → test de arranque que confirma que el servicio falla explícitamente (no silenciosamente) si falta la clave; AC #5 → inspección/test de los logger calls existentes de 1.1 y 1.3, confirmando exclusión explícita de `pat_cifrado` y del PAT descifrado de cualquier objeto logueado.
- **Fixtures / mocks:** PAT de prueba (string dummy, nunca un PAT real); Postgres de prueba (contenedor efímero) para el camino de integración; variable de entorno de clave de cifrado configurada solo en el entorno de test.
- **Edge cases to cover:** PAT vacío o con caracteres especiales; clave de cifrado con longitud incorrecta para el algoritmo elegido; intento de descifrar con la clave equivocada (debe fallar de forma segura, no devolver basura silenciosamente — importante si el algoritmo es autenticado como GCM); `chat_id` sin PAT asociado todavía (usuario dado de alta en Firefly pero el paso de 1.3 aún no completó la entrega del PAT).
