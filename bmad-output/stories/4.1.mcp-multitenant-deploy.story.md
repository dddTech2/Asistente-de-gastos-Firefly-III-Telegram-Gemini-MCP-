## Story

As a **desarrollador**,
I want **desplegar el servidor MCP de Firefly III en modo multi-tenant, aceptando el PAT y la URL de Firefly III como headers por-request en vez de una credencial fija por variable de entorno**,
so that **un solo servicio MCP pueda servir a los ~50 usuarios sin mezclar sus datos, dejando el aislamiento en manos de Firefly III y no de lógica custom**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Antes de escribir cualquier configuración de despliegue, se confirma explícitamente que el MCP server elegido (`@firefly-iii-mcp/server` u otro candidato evaluado) soporta recibir `Authorization: Bearer <PAT>` (y la URL base de Firefly III) como header por-request, no solo como variable de entorno fija al arrancar. Si el candidato NO soporta este patrón, la historia se detiene y se documenta como bloqueada — no se despliega un MCP de un solo tenant.
2. El servidor MCP queda desplegado vía Docker Compose, corriendo como servicio propio, alcanzable desde el host donde correrá el Bot Service (Epic 5), sin exponer su puerto públicamente en Internet.
3. Una llamada de prueba al MCP con el PAT del usuario A en el header devuelve únicamente datos de la cuenta Firefly III del usuario A (verificado manualmente o con `curl`/MCP Inspector, no vía UI final).
4. La misma llamada, repetida con el PAT del usuario B, devuelve únicamente datos de la cuenta del usuario B — confirmando que no hay una credencial compartida ni caché cruzado entre requests.
5. El servicio MCP no persiste ni loguea el valor del PAT recibido en texto plano (revisión de logs de arranque y de request tras la prueba).
6. La configuración de despliegue (docker-compose, variables de entorno del propio MCP que no sean el PAT — ej. puerto, modo de transporte) queda documentada en el repo para que Epic 5 pueda consumir el servicio.

## Dev Notes

- **Este es el detalle técnico crítico que hace viable todo el diseño multi-tenant**: el MCP `@firefly-iii-mcp/server` recomendado soporta recibir el PAT y la URL de Firefly III como headers en cada request (`Authorization: Bearer <PAT>`), en vez de un único PAT fijo por variable de entorno. El Bot Service, al procesar el mensaje del usuario X, le pasa al MCP el PAT propio de X — nunca un token compartido. Firefly III, al recibir esa llamada, solo devuelve/modifica los datos de ese usuario. **La barrera de aislamiento entre usuarios queda adentro de Firefly III, no en lógica custom.** [Source: docs/plan/system-design-v2-multiusuario.md#3-la-pieza-que-hace-viable-la-opción-b-credenciales-por-request-en-el-mcp]
- **Advertencia explícita de la arquitectura**: "si en algún momento cambias de MCP server, verifica que soporte este patrón (credenciales por request). Los que fijan un solo PAT vía variable de entorno al arrancar (como algunas implementaciones en Python que vimos) son de un solo tenant — servirían para la Opción A [una instancia de Firefly III por usuario], no para la B [una instancia compartida]." Esto es exactamente lo que AC #1 obliga a verificar antes de continuar — si el candidato no soporta el patrón, esta historia no es viable tal como está y debe reportarse como bloqueada, no forzarse con un workaround custom. [Source: docs/plan/system-design-v2-multiusuario.md#3-la-pieza-que-hace-viable-la-opción-b-credenciales-por-request-en-el-mcp]
- La decisión de arquitectura previa (Opción B: una sola instancia Firefly III, 50 cuentas dentro) depende enteramente de que este patrón funcione — Firefly III ya aísla datos por `user_id` en cada endpoint de su API, así que la separación no es algo que el Bot Service o el MCP deban programar, siempre que el PAT correcto llegue en cada request. [Source: docs/plan/system-design-v2-multiusuario.md#2-decisión-de-arquitectura-clave-¿un-firefly-iii-por-usuario-o-uno-solo-para-todos]
- Historia de backlog origen: "Como desarrollador, quiero desplegar el MCP de Firefly III en modo multi-tenant (credenciales por request), para que sirva a los 50 usuarios desde un solo servicio." [Source: docs/plan/backlog-scrum-completo.md#épica-4-servidor-mcp]
- Stack: MCP Server recomendado es `@firefly-iii-mcp/server` (Node/TS) o `firefly-iii-mcp-server` (Python) — elegir el que comparta lenguaje con el Bot Service (Node.js + TypeScript) para reducir fricción; el propio plan recomienda Node/TS por esa razón. [Source: docs/plan/backlog-plan-implementacion.md#1-stack-tecnológico-recomendado]
- Infraestructura objetivo: un solo host, Docker Compose, con Postgres y Redis como servicios separados del proceso del bot (piezas independientes que ya deben estar desplegadas por Epic 0). El MCP se suma a ese mismo docker-compose como otro servicio, en la red interna. [Source: docs/plan/system-design-v2-multiusuario.md#6-infraestructura-actualizada]
- El MCP se desarrolla y prueba de forma aislada (story 4.2, con MCP Inspector) **antes** de conectarlo a Gemini (Epic 5) — esta historia (4.1) solo cubre el despliegue del servicio y la verificación de aislamiento por PAT, no la integración con el flujo de lenguaje natural. [Source: bmad-output/epics.md#epic-4-servidor-mcp]
- No exponer el puerto del MCP públicamente: es un servicio interno consumido por el Bot Service dentro de la misma red Docker; no hay caso de uso donde deba ser accesible desde Internet. [Inference]
- El PAT nunca debe quedar en logs, ni en variables de entorno persistentes del contenedor MCP — debe viajar solo dentro del header de cada request y no persistirse en el propio MCP (el MCP es stateless respecto a credenciales). [Inference, reforzado por el requisito de aislamiento estricto: "el usuario A jamás debe poder ver ni un byte de los datos del usuario B... es el requisito no funcional más importante del sistema" — Source: docs/plan/system-design-v2-multiusuario.md#1-requisitos-actualizados]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** Verificación manual/integración dirigida contra un MCP server real desplegado en Docker, apuntando a la instancia Firefly III de desarrollo (Epic 0). No hay lógica de negocio propia que unit-testear en esta historia — el objetivo es confirmar comportamiento de un componente de terceros bajo el patrón de credenciales por-request.
- **Key scenarios:** (a) el MCP arranca sin PAT ni URL fijos por variable de entorno; (b) una request con el PAT del usuario A devuelve solo datos de A; (c) una request con el PAT del usuario B devuelve solo datos de B; (d) una request sin PAT o con PAT inválido es rechazada, no cae de vuelta a ninguna credencial por defecto.
- **Per-AC verification:** AC #1 → revisión documental + prueba de arranque sin credenciales fijas; AC #2 → `docker compose up` + confirmación de que el puerto no está mapeado al host público; AC #3 y #4 → dos llamadas de prueba con PATs distintos, comparando las respuestas; AC #5 → inspección de `docker logs` del contenedor MCP tras las pruebas anteriores buscando el valor del PAT en texto plano; AC #6 → revisión de que el docker-compose/README documenta el modo de transporte y el contrato de headers esperado.
- **Fixtures / mocks:** dos PATs de prueba de dos cuentas Firefly III distintas (pueden ser cuentas de desarrollo creadas manualmente si Epic 1 aún no tiene el flujo de alta automatizado); no se requieren mocks del MCP en sí — se prueba contra el binario/imagen real.
- **Edge cases to cover:** PAT vacío o malformado en el header; URL de Firefly III ausente en el request (si el MCP la requiere como header separado); request concurrente con dos PATs distintos en paralelo, para descartar cualquier estado compartido/caché entre requests.

### AC #1 — INVALIDADO tras verificación empírica: la historia queda BLOQUEADA

**Confirmación inicial errónea:** se dio por satisfecho el AC #1 basándose en
el README público del candidato (`@firefly-iii-mcp/server`,
https://github.com/etnperlong/firefly-iii-mcp, npm v1.4.0), que documenta un
modo "Request Headers (Recommended)" — `Authorization: Bearer <PAT>` +
`X-Firefly-III-Url: <url>` — como forma de pasar credenciales por request.
Sobre esa base se implementó el despliegue completo (Dockerfile, servicio
`mcp-firefly` en compose, `mcp/README.md`).

**Corrección tras leer el código fuente real** (`packages/server/src/app.ts`
y `server.ts` del repo): `pat`/`baseUrl` son obligatorios como argumentos de
arranque (`ServerConfig` los tipa sin `?`, sin ellos el proceso hace
`process.exit(1)`), y las rutas `/mcp` y `/sse` arman el cliente de Firefly
**una sola vez con esos valores fijos** al llamar `createServer()`/
`getServer()` — ningún handler lee `req.headers` buscando `Authorization` ni
`X-Firefly-III-Url`. El README documenta un comportamiento que el código de
esta versión no implementa.

**Confirmado empíricamente en la VPS (2026-09-13):** con el contenedor
arrancado con un PAT real fijo (`FIREFLY_III_PAT`/`FIREFLY_III_BASE_URL`), se
hizo `initialize` → `tools/list` → `tools/call` de `list_account` mandando
`Authorization: Bearer token-invalido-basura` y
`X-Firefly-III-Url: https://url-que-no-existe.invalido` en la request. La
respuesta devolvió una cuenta real de la instancia Firefly III de producción
("almuezo", `current_balance: 60000.00`) — es decir, el header fue
completamente ignorado y se usó el PAT/URL fijo del arranque.

**Conclusión:** este candidato es de un solo tenant. Cualquier despliegue tal
como está (o con cualquier PAT fijo) serviría los datos de una sola cuenta a
los ~50 usuarios — exactamente el escenario que el AC #1 exige evitar. **Por
la propia regla de la historia ("si el candidato no soporta el patrón, la
historia se detiene y se documenta como bloqueada — no se despliega un MCP
de un solo tenant"), la historia queda bloqueada.** No se debe usar el
`docker-compose.yml`/`Dockerfile` de este commit en producción con un PAT
real: quedaron en el repo como referencia técnica (confirman que el
despliegue Docker en sí funciona), pero `mcp/README.md` se actualiza para
advertir explícitamente que este paquete NO logra aislamiento multi-tenant.

**Decisión pendiente (fuera del alcance de esta sesión de dev — es de
planning/producto):** evaluar un candidato alternativo (ej. `daften/
fireflyiii-mcp`, que promociona soporte HTTP/PAT para "headless callers") o
construir un MCP propio mínimo en Node/TS reutilizando `firefly-client.ts`
(3.1/3.2) para garantizar que el aislamiento por-request sea código propio
auditable en vez de depender de un paquete de terceros no verificado.

### Implementación (AC #2, #6)

- **`mcp/Dockerfile` (nuevo, fuera del Owned File/Module Scope original —
  ver "Desviación de alcance" abajo):** `node:20-alpine` +
  `npm install -g @firefly-iii-mcp/server@1.4.0` (versión pineada), expone
  el puerto interno `3000`, arranca con `--logLevel info` (no `debug`, para
  no arriesgar volcar el header `Authorization` en logs — AC #5) y **sin**
  pasar `--pat`/`--baseUrl` ni definir `FIREFLY_III_PAT`/`FIREFLY_III_BASE_URL`.
- **`infra/docker-compose.yml`:** nuevo servicio `mcp-firefly`, `build:
  ../mcp`, sin `env_file` ni variables de credencial fijas, publicado en
  `127.0.0.1:${MCP_FIREFLY_PORT:-3100}:3000` (mismo patrón que
  `bot-postgres`/`bot-redis`: alcanzable desde el Bot Service, proceso pm2 en
  el host, sin exponerse a Internet — AC #2).
- **`infra/.env.example`:** documentada `MCP_FIREFLY_PORT` (default 3100),
  con nota explícita de por qué NO hay variables de PAT/URL de Firefly ahí.
- **`mcp/README.md`:** contrato de headers para Epic 5 (`Authorization`,
  `X-Firefly-III-Url`), modo de transporte (HTTP, no stdio), comando de
  despliegue, y el procedimiento de verificación de aislamiento con curl
  (AC #6).
- Validado localmente que el `docker-compose.yml` resultante parsea
  correctamente y lista `mcp-firefly` entre los servicios (`docker compose
  config --services`) — no se pudo levantar el contenedor real ni generar
  PATs de prueba en este entorno (no hay Docker ni una instancia Firefly III
  accesible localmente); AC #3, #4 y #5 requieren verificación manual contra

### Desviación de alcance documentada: `mcp/Dockerfile`

El Owned File/Module Scope de la historia no menciona un Dockerfile — asume
una imagen ya publicada. El proyecto upstream (`@firefly-iii-mcp/server`) no
