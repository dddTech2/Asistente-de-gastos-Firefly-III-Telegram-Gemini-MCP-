# 5.13: Cablear el orquestador de Gemini al webhook real de Telegram

**Story ID:** 5.13
**Epic:** 5 — Integración con Gemini (conversación en lenguaje natural)
**Slug:** integrar-orquestador-webhook
**Status:** done   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

## Story

As a **usuario**,
I want **que cualquier mensaje de texto libre que le escriba al bot (que no sea /gasto ni /resumen) se procese con el pipeline de Gemini ya construido**,
so that **pueda usar el asistente conversacionalmente, en vez de recibir un eco literal de lo que escribí**.

## Acceptance Criteria

<!-- LOCKED. -->

1. Un mensaje de texto libre que llega por el webhook de Telegram y no matchea `/gasto` ni
   `/resumen` se procesa a través de `messageOrchestrator.procesarMensaje` (historia 5.1) — el
   eco literal de la historia 2.2 queda completamente reemplazado en el flujo real, no en
   paralelo.
2. El proceso principal (`index.ts`) construye el orquestador con sus dependencias reales:
   `geminiClient` (`GEMINI_API_KEY`/`GEMINI_MODEL`), `mcpToolExecutor` (`MCP_FIREFLY_URL`),
   `historyStore` (cliente Redis real vía `REDIS_URL`) y `credentialResolver` (reutilizando el
   `usuariosRepository` ya existente, historia 1.5) — las cuatro variables ya estaban
   documentadas en `.env.example` desde la historia 5.1 pero ningún proceso las leía todavía.
3. Si el usuario autorizado (ya pasó la whitelist) no tiene un PAT propio disponible
   (`CredencialesNoDisponiblesError`, historia 1.5), el bot responde con un mensaje claro
   indicando que falta completar el alta, no con un error técnico ni con silencio.
4. Cualquier otra excepción no controlada durante el procesamiento (falla de red a Gemini o al
   MCP, u otro error no cubierto por el fail-safe propio de `historyStore`) se loggea con
   `chat_id` y se responde al usuario con un mensaje de fallback genérico — nunca se expone un
   stack trace ni se lo deja sin respuesta.
5. El comportamiento de ack inmediato + procesamiento asíncrono (historia 2.3) y el orden de
   precedencia de handlers (whitelist → `/gasto` → `/resumen` → mensaje libre, historias
   3.1/3.2) se preservan sin cambios.

## Dev Agent Record

### Resumen de implementación

Pura composición, tal como anticipaban los Dev Notes: ninguna pieza de lógica de negocio nueva.

- **`src/config/env.ts`:** `GEMINI_API_KEY`, `MCP_FIREFLY_URL`, `REDIS_URL` pasan a `required()`;
  `GEMINI_MODEL` mantiene su default `"gemini-flash-latest"`.
- **`src/lib/redisClient.ts`** (nuevo): cliente `ioredis` compartido por proceso, mismo patrón que
  `src/db/pool.ts`. Nota técnica: `import Redis from "ioredis"` (default) no compila bajo
  `moduleResolution: NodeNext` de este proyecto (`TS2351: not constructable` -- desajuste de tipos
  conocido de `ioredis` en resolución ESM estricta); se usa `import { Redis } from "ioredis"`
  (named export), que sí tipa correctamente y es el mismo valor en runtime.
- **`src/handlers/geminiMessageHandler.ts`** (nuevo): reemplaza a `echoHandler.ts`. Distingue
  `CredencialesNoDisponiblesError` (AC #3) de cualquier otra excepción (AC #4) porque
  `messageOrchestrator.procesarMensaje` no captura la primera internamente.
- **Eliminados:** `src/handlers/echoHandler.ts` y `tests/handlers/echoHandler.test.ts` — su
  propósito (historia 2.2, confirmar que el bot respondía) queda completamente superado; no tenía
  sentido dejarlo como código muerto en el flujo real.
- **`src/webhook/telegramWebhook.ts`:** `createTelegramWebhookHandler` recibe un cuarto parámetro
  `messageOrchestrator`; registra `registerGeminiMessageHandler` en el mismo lugar donde antes
  registraba el eco, preservando el orden `/gasto` → `/resumen` → texto libre.
- **`src/server.ts`:** `ServerOptions.messageOrchestrator`, pasado tal cual a
  `createTelegramWebhookHandler`.
- **`src/index.ts`:** construye el orquestador real: `createGeminiClient` + `createMcpToolExecutor`
  + `createHistoryStore(redis)` + `createCredentialResolver({usuariosRepository, fireflyUrl})`
  (reutilizando el `usuariosRepository` que ya existía para la whitelist).

### ⚠️ Riesgo de seguridad detectado durante esta historia — NO resuelto acá, señalado para decisión del usuario

Al cerrar esta historia se hace alcanzable en producción, por primera vez, el ciclo completo
`messageOrchestrator` → `mcpToolExecutor.ejecutarTool`. Ese ciclo ejecuta **cualquiera de las 140
tools** que Gemini decida llamar, **incluidas las destructivas** (`delete_transaction`,
`delete_account`, etc., clasificadas por `toolClassification.ts` en la historia 4.3) — porque
`solicitarConfirmacion`/`registerConfirmacionCallbackHandler` (también historia 4.3, ya construidos
y probados) **nunca fueron invocados desde `messageOrchestrator.ts`**, exactamente el mismo tipo de
gap que motivó esta historia (5.13), pero sin ninguna historia en el backlog (5.1-5.13) que lo
cubra: se buscó explícitamente y ninguna tiene `confirmacionAccionIrreversible.ts` en su Owned
Scope. Mientras 5.4 ("aclaración de dato inválido") suena como la candidata natural, sus AC (LOCKED)
son sobre errores de validación, no sobre confirmación de acciones irreversibles.

**No se resolvió en esta historia** (cambiaría el ciclo síncrono de `procesarMensaje` a uno que debe
pausarse a esperar una respuesta de botón entre dos webhooks distintos — un cambio de control de
flujo no trivial, fuera del AC de "solo cablear el pipeline de texto libre a un handler real" que
tiene esta historia). Documentado acá y comunicado explícitamente al usuario para que decida
prioridad antes de considerar el bot listo para uso general sin supervisión.
