# 0.1.firefly-docker-compose: Desplegar Firefly III + Postgres/MariaDB con Docker Compose

**Story ID:** 0.1
**Epic:** 0 — Infraestructura base
**Slug:** firefly-docker-compose
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **desarrollador**,
I want **desplegar Firefly III + Postgres/MariaDB con Docker Compose**,
so that **tenga el backend financiero corriendo y accesible como base de todo lo demás**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Dado un servidor limpio con Docker y Docker Compose instalados, cuando se ejecuta `docker compose up -d` sobre el `docker-compose.yml` del proyecto, entonces Firefly III responde en el navegador (HTTP, en el puerto local configurado — HTTPS se resuelve en la historia 0.2). [Source: docs/plan/backlog-scrum-completo.md#épica-0-infraestructura-base]
2. El `docker-compose.yml` define al menos dos servicios: la app de Firefly III y su base de datos (Postgres o MariaDB), con un volumen nombrado persistente para los datos de la base. [Source: docs/plan/backlog-scrum-completo.md#épica-0-infraestructura-base]
3. Los secretos (credenciales de base de datos, `APP_KEY` de Firefly, etc.) viven en un archivo `.env` fuera del control de versiones; el repo solo contiene un `.env.example` con las claves sin valores reales. [Source: docs/plan/backlog-plan-implementacion.md#épica-0-infraestructura-base]
4. Tras `docker compose up -d`, se completa el asistente de instalación de Firefly III (creación de usuario admin) y se genera un Personal Access Token de validación para el desarrollador. [Source: docs/plan/backlog-plan-implementacion.md#4-checklist-para-arrancar-hoy]
5. Al detener y volver a levantar los contenedores (`docker compose down` seguido de `docker compose up -d`), los datos previamente creados en Firefly III siguen presentes (persistencia real, no solo mientras el contenedor vive). [Inference]

- Requisito de origen: HU-01 — "Como desarrollador, quiero desplegar Firefly III + Postgres/MariaDB con Docker Compose, para tener el backend financiero corriendo." [Source: docs/plan/backlog-scrum-completo.md#épica-0-infraestructura-base]
- Elección de base de datos: la tabla de stack tecnológico recomienda **MariaDB** como "la recomendada oficialmente por Firefly III" [Source: docs/plan/backlog-plan-implementacion.md#1-stack-tecnológico-recomendado]. Sin embargo, el backlog actualizado (fuente de verdad) nombra la historia como "Postgres/MariaDB" indistintamente [Source: docs/plan/backlog-scrum-completo.md#épica-0-infraestructura-base] y el diseño v2 usa Postgres para el propio Bot Service (historia 0.3). **Recomendación:** usar MariaDB para la base de datos de Firefly III (sigue la recomendación oficial del proyecto Firefly) y dejar Postgres exclusivamente para el Bot Service en 0.3, evitando correr dos motores de base de datos distintos solo si no hace falta — pero si se prefiere simplificar a un único motor, Postgres es válido porque Firefly III también lo soporta. Esta elección final queda a criterio de implementación; documentarla en el propio repo. [Inference]
- Usar como base el `docker-compose.yml` oficial que distribuye el propio proyecto Firefly III en su documentación, no reescribirlo desde cero. [Source: docs/plan/backlog-plan-implementacion.md#4-checklist-para-arrancar-hoy]
- Infraestructura objetivo: todo el stack corre en **Docker Compose sobre un único VPS**. Para el MVP (v1) 2 vCPU / 4GB alcanza; una vez que se suman Redis/Postgres del Bot Service y colas (historias 0.3 en adelante), el piso recomendado sube a **4 vCPU / 8GB**. [Source: docs/plan/backlog-plan-implementacion.md#1-stack-tecnológico-recomendado] [Source: docs/plan/system-design-v2-multiusuario.md#6-infraestructura-actualizada]
- Definition of Done del proyecto exige que cualquier dato sensible (PAT, credenciales) quede cifrado o fuera de logs — para esta historia eso aplica al `.env` con credenciales de base de datos y `APP_KEY`, que no debe commitearse. [Source: docs/plan/backlog-scrum-completo.md#4-definition-of-done-dod]
- El checklist de arranque documenta el flujo esperado: levantar Firefly III con Docker Compose, crear el usuario admin, generar un Personal Access Token — ese PAT de validación es el mismo mecanismo que luego usará la Épica 3 (comandos directos) antes de existir multi-tenancy. [Source: docs/plan/backlog-plan-implementacion.md#4-checklist-para-arrancar-hoy]
- Firefly III es la **única fuente de verdad** de los datos financieros; ningún otro servicio de este proyecto debe guardar su propia copia del estado de negocio — esta historia es la que materializa esa fuente de verdad. [Source: docs/plan/system-design-asistente-gastos.md#2-high-level-design]
- Esta base de datos de Firefly III es una instancia **distinta** de la que se desplegará para el Bot Service en la historia 0.3 (usuarios/PAT/auditoría) — no reutilizar el mismo contenedor de base de datos para ambos propósitos. [Inference]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** validación manual de infraestructura (no hay lógica de aplicación propia todavía) — checklist de despliegue reproducible, sin suite automatizada de tests unitarios.
- **Key scenarios:** despliegue limpio desde cero; reinicio de contenedores sin pérdida de datos; arranque con `.env` faltante (debe fallar de forma clara, no silenciosa).
- **Per-AC verification:** AC #1 → acceder a la URL local de Firefly III tras `docker compose up -d` y confirmar que carga la pantalla de login/instalación; AC #2 → inspeccionar `docker-compose.yml` y `docker volume ls` para confirmar el volumen nombrado; AC #3 → `git status` no debe listar `.env`, y `.env.example` debe existir con las claves documentadas; AC #4 → completar el wizard y confirmar que el PAT generado funciona contra un endpoint simple de la API (`GET /api/v1/about`); AC #5 → `docker compose down && docker compose up -d` y volver a loguearse con el mismo usuario admin.
- **Fixtures / mocks:** ninguno — es infraestructura real corriendo en un entorno de prueba/staging, no simulada.
- **Edge cases to cover:** puerto ya ocupado en el host; `.env` incompleto (variable faltante); reinicio del host completo (no solo `docker compose down`) para confirmar que los servicios se auto-inician si se configura `restart: unless-stopped`.
