# 3.1: Comando `/gasto` crea una transacción real en Firefly III

**Story ID:** 3.1
**Epic:** 3 — Integración directa con Firefly III (sin IA todavía)
**Slug:** comando-gasto-manual
**Status:** done   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **usuario autorizado del bot (en esta fase, el propio desarrollador)**,
I want **registrar un gasto con un comando simple `/gasto <monto> <concepto>`**,
so that **se valide que el flujo básico Telegram → Firefly III funciona de punta a punta, antes de meter la capa de IA (MCP + Gemini)** [Source: docs/plan/backlog-scrum-completo.md#épica-3-integración-directa-con-firefly-iii-sin-ia-todavía].

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Dado un `chat_id` ya autorizado que envía `/gasto <monto> <concepto>` (ej. `/gasto 20000 almuerzo`), cuando el Bot Service procesa el mensaje, entonces se crea una transacción real en Firefly III vía su API REST usando el PAT del desarrollador, con el monto y la descripción indicados [Source: docs/plan/backlog-scrum-completo.md#épica-3-integración-directa-con-firefly-iii-sin-ia-todavía] [Source: docs/plan/backlog-plan-implementacion.md#épica-2-integración-directa-con-firefly-iii-api-sin-ia-todavía].
2. Dado el comando enviado sin argumentos, con un monto no numérico, o sin concepto, cuando el bot lo recibe, entonces responde con un mensaje de uso correcto (`/gasto <monto> <concepto>`) y NO llama a la API de Firefly III. [Inference]
3. Dado que Firefly III responde con un error (token inválido, validación fallida, timeout de red), cuando se intenta crear la transacción, entonces el bot informa al usuario que la operación falló (sin exponer detalles técnicos internos) y no deja el error en silencio [Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive] (sección "Error handling y reintentos": circuit breaker simple si Firefly no responde).
4. Dado que la transacción se creó con éxito, cuando el bot responde al usuario, entonces confirma el monto y el concepto registrados. [Inference]
5. El PAT usado es fijo, propio del desarrollador, configurado por variable de entorno del Bot Service — NO hay resolución de PAT por-usuario en esta historia (eso es Epic 1/Epic 4) [Source: bmad-output/epics.md#epic-3-integración-directa-con-firefly-iii-sin-ia-todavía] (Architecture touchpoints: "PAT propio del desarrollador (fase de validación, previo a multi-tenancy)").
6. El PAT nunca aparece en logs ni en las respuestas de error mostradas al usuario [Source: docs/plan/backlog-scrum-completo.md#4-definition-of-done-dod] ("Si toca datos sensibles (PAT, credenciales), quedaron cifrados/fuera de logs").

- **Propósito explícito de la épica:** validar el pipeline extremo a extremo (Telegram → Firefly III) con comandos rígidos, ANTES de meter la capa de IA (MCP en Epic 4, Gemini en Epic 5) [Source: bmad-output/epics.md#epic-3-integración-directa-con-firefly-iii-sin-ia-todavía]. Esta historia NO debe introducir MCP ni lenguaje natural — eso está explícitamente fuera de alcance de la épica.
- **PAT del desarrollador, no multi-tenant todavía:** la épica usa el PAT propio del desarrollador como fase de validación, previa al aislamiento multi-tenant que se construye en Epic 1 (PAT cifrado por `chat_id`) y se conecta en Epic 4 (MCP con credenciales por-request) [Source: bmad-output/epics.md#epic-3-integración-directa-con-firefly-iii-sin-ia-todavía] [Source: docs/plan/backlog-plan-implementacion.md#épica-2-integración-directa-con-firefly-iii-api-sin-ia-todavía] (paso previo listado: "Generar Personal Access Token en Firefly III").
- **Llamada directa REST, sin MCP:** para esta épica, el Bot Service llama a la API REST de Firefly III directamente (no a través del servidor MCP, que se introduce recién en Epic 4) [Source: docs/plan/backlog-plan-implementacion.md#épica-2-integración-directa-con-firefly-iii-api-sin-ia-todavía] (ítem: "Comando manual `/gasto 20000 almuerzo` crea una transacción real vía API REST"). El diagrama de secuencia de referencia del proyecto muestra la forma general de esta llamada como `MCP->>Firefly: Llamada REST (POST /transactions)` para el flujo con IA; en esta épica el mismo patrón de llamada REST aplica pero originándose directo en el Bot Service [Source: docs/plan/diagrama-secuencia-flujo-chat.mermaid].
- **Autenticación de la API de Firefly III:** el mecanismo confirmado en la documentación del proyecto es `Authorization: Bearer <PAT>` como header en cada request [Source: docs/plan/system-design-v2-multiusuario.md#3-la-pieza-que-hace-viable-la-opción-b-credenciales-por-request-en-el-mcp]. El prefijo de la API REST es `/api/v1/` (confirmado para el endpoint de administración `POST /api/v1/users`) [Source: docs/plan/system-design-v2-multiusuario.md#5-aprovisionamiento-de-usuarios-nuevo-en-v2]. El endpoint exacto de creación de transacciones (`POST /api/v1/transactions`, siguiendo el mismo prefijo) no está deletreado carácter-a-carácter en la documentación del proyecto — se infiere combinando el prefijo confirmado con la forma abreviada `POST /transactions` del diagrama de secuencia. [Inference]
- **Contrato de alto nivel "Persistencia":** la tabla de contratos clave del proyecto marca la persistencia hacia Firefly III como "REST/OAuth2, ya definido" [Source: docs/plan/system-design-asistente-gastos.md#2-high-level-design]. Para esta épica (pre-MCP), el mecanismo de auth usado es el PAT Bearer descrito arriba, no un flujo OAuth2 interactivo completo — Firefly III soporta ambos, y el PAT es la vía usada en esta fase de validación. [Inference]
- **Manejo de errores:** aplicar circuit breaker simple — si Firefly no responde tras reintentos, contestar "servicio no disponible por ahora" en vez de dejar al usuario esperando o arriesgar una transacción duplicada [Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive] (sección "Error handling y reintentos").
- **Regla de oro de storage:** el Bot Service no debe guardar su propia copia del dato financiero — Firefly III es la única fuente de verdad; esta historia solo hace de puente hacia la API, no persiste el gasto localmente [Source: docs/plan/system-design-asistente-gastos.md#2-high-level-design].
- **Stack:** Node.js + TypeScript, con grammY o Telegraf para el bot (definido en Epic 2, reutilizado aquí como router de comandos) [Source: docs/plan/backlog-plan-implementacion.md#1-stack-tecnológico-recomendado].
- **Latencia objetivo:** la respuesta completa del bot (incluida la ida y vuelta a Firefly) debería idealmente ser < 5s [Source: docs/plan/system-design-asistente-gastos.md#1-requirements-gathering] (No funcionales: "Latencia").
- **Secretos fuera de logs:** requisito de DoD aplicable directamente al PAT que esta historia introduce por primera vez en el código del bot [Source: docs/plan/backlog-scrum-completo.md#4-definition-of-done-dod].
- **Nombre de variables de entorno (`FIREFLY_PAT`, `FIREFLY_BASE_URL`) y estructura de archivos:** no están fijados en ningún documento fuente — son una convención propuesta para esta historia. [Inference]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** unit tests para el parseo/validación del comando y para el cliente `firefly-client.ts` (con el HTTP mockeado, ej. `nock`/`msw`); verificación manual del camino feliz y de un caso de error contra una instancia real o local de Firefly III, tal como exige la DoD del proyecto.
- **Key scenarios:** argumento de monto válido/ inválido; concepto ausente; creación exitosa; Firefly responde error de validación (422); Firefly responde 401 (PAT inválido/expirado); Firefly no responde (timeout).
- **Per-AC verification:** AC #1 → test de integración mockeado que confirma el `POST /api/v1/transactions` con el payload y header `Authorization` correctos; AC #2 → tests unitarios de parseo con montos/argumentos inválidos que confirman que NO se invoca al cliente Firefly; AC #3 → test que simula una respuesta de error/timeout de Firefly y confirma el mensaje genérico al usuario; AC #4 → test que confirma el contenido del mensaje de éxito (monto, concepto); AC #5 → revisión de código/config que confirma que el PAT se lee de variable de entorno y no hay lógica de resolución por-usuario; AC #6 → test/inspección que confirma que ningún log ni mensaje de error incluye el valor del PAT.
- **Fixtures / mocks:** payloads de update de Telegram de ejemplo (`/gasto 20000 almuerzo`, variantes inválidas); respuestas mockeadas de Firefly III (201 con id de transacción, 422 de validación, 401 no autorizado, timeout de red).
- **Edge cases to cover:** monto cero o negativo, monto con decimales/formato inesperado, concepto vacío o solo espacios, concepto muy largo, PAT no configurado al arrancar el servicio, Firefly caído (conexión rechazada).

### Implementación

- **`bot-service/src/services/firefly-client.ts` (nuevo):** `createFireflyClient({
  baseUrl, pat, sourceAccount })` → `crearTransaccion({ monto, concepto })`.
  `POST /api/v1/transactions` con `Authorization: Bearer <PAT>`, `type:
  "withdrawal"`, `source_name` = `sourceAccount`, `destination_name` =
  concepto (Firefly auto-crea/reutiliza la cuenta de gasto). Timeout de 8s
  (`AbortSignal.timeout`) como circuit breaker simple (AC #3). Lanza
  `FireflyClientError` (con `status` cuando aplica) en cualquier fallo —
  nunca incluye el cuerpo de la respuesta de Firefly en el mensaje de error
  (defensa en profundidad más allá del AC #6).
- **`bot-service/src/commands/gasto.ts` (nuevo):** `parsearArgumentosGasto`
  (monto numérico positivo, acepta decimales, + concepto no vacío;
  `null` ante cualquier formato inválido → AC #2) y `registerGastoHandler(bot,
  fireflyClient)` vía `bot.command("gasto", ...)` de grammY. Éxito → mensaje
  con monto/concepto/id (AC #4); fallo → mensaje genérico + log con
  `{chat_id, err}` únicamente, nunca el PAT (AC #3, #6).
- **Endpoint del pipeline (adaptación de nombres):** la historia menciona
  `bot-service/src/bot.ts` como el "router de comandos" a modificar, pero ese
  archivo no existe en este repo — el router real construido en Epic 2 es
  `bot-service/src/webhook/telegramWebhook.ts::createTelegramWebhookHandler`,
  que ya registra `registerEchoHandler(bot)`. Se agregó
  `registerGastoHandler(bot, fireflyClient)` ahí, **antes** del echo (un
  `bot.command` que no llama a `next()` corta la cadena, así `/gasto` no
  dispara también el eco). `createTelegramWebhookHandler` y `createServer`
  (`server.ts`) ahora reciben `fireflyClient` como parámetro adicional;
  `index.ts` lo construye con `createFireflyClient(...)` a partir de `env`.
  Mismo patrón de adaptación de nombres ya documentado en 1.1/1.3.
- **`config/env.ts`:** `fireflyPat`, `fireflyBaseUrl`,
  `fireflySourceAccount` — los tres `required()` (el proceso principal ya usa
  esto para una funcionalidad real, a diferencia de `fireflyAdminBaseUrl`/
  `fireflyAdminToken` de 1.3 que solo usa el script de un solo uso).
- **`.env.example`:** documentadas `FIREFLY_PAT`, `FIREFLY_BASE_URL`,
  `FIREFLY_SOURCE_ACCOUNT`.

### Desviación de alcance documentada: `FIREFLY_SOURCE_ACCOUNT`

Ni el Owned File/Module Scope ni los Dev Notes de la historia mencionan una
cuenta de origen — solo `FIREFLY_PAT`/`FIREFLY_BASE_URL`. Pero la API de
Firefly III exige una cuenta de activo (`source_name`/`source_id`) para
crear cualquier `withdrawal`; sin ella, AC #1 es imposible de cumplir contra
la API real. Se agregó `FIREFLY_SOURCE_ACCOUNT` como tercera variable
requerida, documentada en `.env.example` y el README. [Inference]

### Decisiones de diseño

- **Formato de monto:** acepta decimales (`20000.50`) pero NO interpreta
  separadores de miles al estilo argentino (`20.000` se lee como `20`) — se
  sigue literalmente el formato del ejemplo del propio AC #1
  (`/gasto 20000 almuerzo`), sin agregar parsing de locale que la historia no
  pide. [Inference]
- **Manejo de errores vía excepción tipada** (`FireflyClientError`), no un
  `Result` discriminado — mismo patrón que `firefly-admin-client.ts` de 1.3,
  para mantener consistencia de estilo entre los dos clientes REST de Firefly
  III del repo.
- El `catch` de `registerGastoHandler` colapsa **cualquier** error (no solo
  `FireflyClientError`) al mismo mensaje genérico — mismo criterio fail-safe
  usado en `credential-resolver.ts` (1.5): mejor un mensaje genérico de más
  que arriesgar filtrar un detalle técnico o interno en un caso no previsto.

### Verificado en producción (2026-09-13)

El administrador configuró `FIREFLY_PAT`/`FIREFLY_BASE_URL`/
`FIREFLY_SOURCE_ACCOUNT` en la VPS. Primer intento sin `npm run build` dejó
corriendo el `dist/` compilado viejo (pm2 corre `dist/index.js`, no el
código fuente) — el bot seguía respondiendo el eco. Segundo intento sin las
tres variables configuradas hizo que el proceso no arrancara en absoluto
(comportamiento esperado: `env.ts` falla rápido con configuración
incompleta). Una vez con `npm run build` + variables completas + `pm2
restart`, `/gasto 20000 almuerzo` respondió la confirmación esperada
("Gasto registrado...") contra la instancia real de Firefly III. AC #1, #2,
#4, #5 y #6 verificados en producción (AC #3, el caso de error, no se
verificó explícitamente contra un 4xx/5xx real pero sí implícitamente: la
propia falla de arranque por env var faltante mostró el comportamiento
fail-fast esperado).

**Nota operativa para futuros deploys:** cualquier cambio que toque
`src/index.ts`, `src/server.ts` o el pipeline del webhook requiere `npm run
build` antes de `pm2 restart` — pm2 corre `dist/index.js` compilado, no
`tsx` sobre el código fuente. Se agrega esta nota al README para que no se
repita el primer error de este ciclo de despliegue.
