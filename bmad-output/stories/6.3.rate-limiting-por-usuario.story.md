# 6.3: Limitar mensajes por minuto por chat_id

**Story ID:** 6.3
**Epic:** 6 — Control de costos y concurrencia
**Slug:** rate-limiting-por-usuario
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As an **administrador**,
I want **limitar cuántos mensajes por minuto puede enviar cada usuario**,
so that **se controle el gasto en la API de Gemini**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Cada mensaje entrante se valida contra un límite configurable de N mensajes/minuto por `chat_id` antes de que el worker invoque el pipeline de Gemini.
2. Cuando un usuario supera el límite, el bot le responde con un mensaje explícito pidiéndole que espere, en vez de descartar el mensaje en silencio o dejarlo esperando indefinidamente en la cola.
3. Los contadores de rate limit se guardan en la instancia de Redis compartida, con una ventana (fija o deslizante) que corresponde a la granularidad "mensajes por minuto" y se resetea automáticamente sin limpieza manual.
4. El límite se aplica siempre por `chat_id` individual — una ráfaga de un usuario nunca consume ni afecta la cuota de otro usuario.
5. El valor N por defecto es configurable por variable de entorno, sin requerir un cambio de código ni redeploy del binario.
6. El rate limiting no interfiere con el chequeo de deduplicación de `update_id` (6.1) ni con el ack inmediato del webhook (Epic 2.3): un mensaje descartado por rate limit igual se confirma (ack) a Telegram.

- Objetivo explícito del backlog: "limitar cuántos mensajes por minuto puede enviar cada usuario, para controlar el gasto en la API de Gemini" (HU-25). [Source: docs/plan/backlog-scrum-completo.md#épica-6-control-de-costos-y-concurrencia]
- Motivación de escala: "50 usuarios activos pueden multiplicar por 50 el gasto en tokens de Gemini vs. v1. Ahora sí hace falta control activo, no solo 'usar el modelo barato'." — el rate limiting es, junto con Gemini Flash como default, la segunda pata del control de costo a nivel de arquitectura. [Source: docs/plan/system-design-v2-multiusuario.md#1-requisitos-actualizados]
- `chat_id` es el identificador de usuario de Telegram y la clave de aislamiento y whitelist de acceso en todo el sistema — el rate limit debe usar esa misma clave para mantener consistencia con el resto de la arquitectura (whitelist, aislamiento de datos). [Source: bmad-output/project-context.md#glossary]
- El aislamiento entre usuarios es "el requisito no funcional más importante del sistema" al pasar a 50 usuarios — el rate limit, al aplicarse estrictamente por `chat_id`, no debe convertirse en una forma nueva de que la actividad de un usuario afecte a otro. [Source: docs/plan/system-design-v2-multiusuario.md#1-requisitos-actualizados]
- El rate limit se implementa "en la cola", es decir, sobre la infraestructura que crea 6.2 (BullMQ + Redis) — esta historia no introduce un almacén nuevo, reutiliza la misma instancia de Redis. [Source: docs/plan/system-design-v2-multiusuario.md#4-cambios-en-el-bot-service]
- El texto exacto del mensaje de "espera" al usuario y si se calcula el tiempo restante no está especificado en ningún doc fuente; se infiere que debe ser explícito (no silencio) porque el sistema es conversacional y un mensaje ignorado sin explicación generaría confusión sobre si el bot recibió el gasto o no. ## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** pruebas unitarias de `rateLimiter.ts` contra un cliente Redis simulado o efímero, cubriendo el conteo por ventana y el reseteo; prueba de integración del middleware verificando que el mensaje de rechazo se envía y que el pipeline de Gemini no se invoca cuando el límite se excede.
- **Key scenarios:** mensajes por debajo del límite pasan sin fricción; el mensaje que alcanza exactamente N pasa; el mensaje N+1 dentro de la misma ventana se rechaza con aviso al usuario; la ventana se resetea pasado el minuto y el usuario puede volver a enviar; dos `chat_id` distintos con actividad simultánea no se afectan entre sí.
- **Per-AC verification:** AC #1 → test que confirma que `checkLimit` se evalúa antes de invocar el pipeline de Gemini; AC #2 → test que confirma el envío del mensaje de aviso cuando `allowed=false`; AC #3 → test que confirma que la clave de Redis usada incluye la ventana temporal y tiene TTL/expiración configurada; AC #4 → test con dos `chat_id` en paralelo verificando contadores independientes; AC #5 → test que instancia el limitador con distintos valores de `RATE_LIMIT_MAX_PER_MINUTE` y confirma que el umbral efectivo cambia; AC #6 → test que confirma que el ack del webhook (que ocurre en 6.2 al encolar) no depende del resultado del rate limit.
- **Fixtures / mocks:** cliente Redis simulado/efímero con soporte de `INCR`/`EXPIRE`/`TTL`; reloj controlable (fake timers) para simular el paso de la ventana de un minuto sin esperar en tiempo real; stub del pipeline de Gemini para confirmar que no se invoca cuando el límite se excede.
- **Edge cases to cover:** ráfaga exactamente en el borde de la ventana (mensaje justo al cambiar de minuto); `chat_id` inexistente en el whitelist (no debería llegar aquí, pero si llega no debe romper el limitador); Redis no disponible al momento de chequear el límite.
