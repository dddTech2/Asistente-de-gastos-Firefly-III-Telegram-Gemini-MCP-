# 8.6: Ejecutar la prueba de carga de 50 usuarios y producir el reporte de veredicto

## Story

As an **administrador del sistema**,
I want **ejecutar la prueba de carga de 50 usuarios concurrentes de punta a punta y producir un
reporte con veredicto explícito**,
so that **el equipo sepa, con evidencia, si la arquitectura de instancia única de Firefly III
(Opción B) aguanta antes de invitar a los 50 usuarios reales a producción**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. La prueba ejercita el pipeline de punta a punta: webhook de Telegram (simulado) → cola
   (BullMQ/Redis) → llamada a Gemini → tool call al MCP → Firefly III → respuesta al usuario — no
   un componente aislado — usando el script y las cuentas sintéticas preparadas en 8.5, durante
   una ventana de prueba sostenida (ej. 15-30 minutos) con al menos un escenario de ráfaga.
2. Se capturan y reportan, como mínimo: latencia de respuesta end-to-end (p50/p95/p99), tasa de
   error, profundidad/backlog de la cola de BullMQ durante la ráfaga, y uso de recursos (CPU/RAM,
   conexiones activas) de Postgres, Redis y Firefly III durante la ventana de prueba.
3. El resultado se documenta en un reporte con un veredicto explícito (aguanta / no aguanta)
   contra el objetivo de latencia <5s (p95) definido como NFR del sistema, dejando constancia
   formal de si la Opción B de arquitectura queda validada o invalidada.
4. Si el veredicto es "no aguanta" o "aguanta con reservas", el reporte identifica el cuello de
   botella observado (ej. Firefly III, Postgres, límites de tasa de Gemini, saturación de la
   cola) para informar la siguiente decisión — subir el VPS verticalmente, u optar por la Opción A
   (instancia por usuario) descartada originalmente.
5. Al finalizar, se ejecuta el script de limpieza de 8.5 y se confirma que las cuentas y datos
   sintéticos quedaron purgados.

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** esta historia ES en sí misma una prueba de carga (no unitaria/integración de
  código de producto) — la estrategia de testing es la metodología de la prueba: carga sostenida +
  ráfaga contra un entorno equivalente a producción, con métricas capturadas de cada capa del
  pipeline.
- **Key scenarios:** carga sostenida moderada (50 usuarios enviando mensajes espaciados durante la
  ventana completa); ráfaga concentrada (los 50 usuarios virtuales enviando dentro de una ventana
  de segundos, el caso "todos después de almorzar"); mezcla de mensajes de registro de gasto y de
  consulta.
- **Per-AC verification:** AC #1 → verificar en logs/trazas que una muestra de mensajes atraviesa
  las 5 etapas del pipeline, no solo que el webhook respondió; AC #2 → el reporte contiene series
  de tiempo o snapshots de cada métrica listada, no solo un promedio agregado que esconda picos;
  AC #3 → el reporte declara explícitamente el número (p95 medido) contra el umbral (<5s) y un
  veredicto en texto claro; AC #4 → si el veredicto no es "aguanta" limpio, el reporte nombra el
  componente específico que se saturó primero con el dato que lo respalda (ej. "conexiones de
  Postgres al 95% de su pool a partir del minuto 8"); AC #5 → confirmar post-purga que las cuentas
  sintéticas ya no responden a llamadas de la API de Firefly III.
- **Fixtures / mocks:** ninguno — reutiliza las 50 cuentas sintéticas y el script de 8.5; no
  mocks, esta prueba necesita el sistema real de punta a punta para que el resultado sea válido.
- **Edge cases to cover:** qué pasa si Gemini empieza a devolver rate-limit errors bajo la carga
  (el reintento con backoff de Epic 6 debería absorberlo — esta prueba confirma si lo hace); qué
  pasa si la cola de BullMQ acumula backlog más rápido de lo que los workers lo procesan
  (crecimiento no acotado); comportamiento cuando la ráfaga termina — tiempo de recuperación a
  latencia normal, no solo el pico.
