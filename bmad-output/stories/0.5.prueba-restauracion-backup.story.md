# 0.5.prueba-restauracion-backup: Probar una restauración completa desde backup

**Story ID:** 0.5
**Epic:** 0 — Infraestructura base
**Slug:** prueba-restauracion-backup
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As an **administrador**,
I want **haber probado una restauración completa desde backup al menos una vez**,
so that **confíe en que el backup funciona cuando realmente lo necesite, en vez de descubrirlo en una emergencia**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Dado un backup reciente generado por el mecanismo de la historia 0.4, cuando se restaura en un entorno de prueba aislado (no producción), entonces los datos restaurados coinciden con los del origen. [Source: docs/plan/backlog-scrum-completo.md#épica-0-infraestructura-base]
2. La restauración cubre ambas bases de datos respaldadas en 0.4: la de Firefly III y la Postgres del Bot Service. [Inference, consistente con AC #2 de 0.4]
3. Existe un documento corto (runbook) con los pasos exactos de restauración, de forma que el proceso sea repetible sin tener que redescubrirlo bajo presión en un incidente real. [Source: docs/plan/system-design-asistente-gastos.md#4-scale-and-reliability]
4. El entorno de prueba usado para la restauración está completamente aislado del entorno de producción (docker-compose separado o red distinta), de forma que la prueba no pueda dañar datos reales. [Inference]
5. Se deja registrado, aunque sea informalmente, cuánto tardó el proceso de restauración de punta a punta, como referencia para un incidente real futuro. [Inference]

<!-- Keep to ~3-7. More than ~7 means the story is too big — split it. -->

## Tasks / Subtasks

- [ ] Preparar un entorno de prueba aislado para la restauración (AC: #4)
  - [ ] Crear un `docker-compose` de prueba/restauración separado del de producción (mismas imágenes de base de datos, sin conexión a los servicios reales)
- [ ] Ejecutar la restauración con un backup real (AC: #1, #2)
  - [ ] Descargar el backup más reciente generado por 0.4 desde el almacenamiento externo
  - [ ] Restaurar la base de datos de Firefly III en el entorno de prueba
  - [ ] Restaurar la base de datos Postgres del Bot Service en el entorno de prueba
- [ ] Verificar integridad de los datos restaurados (AC: #1)
  - [ ] Comparar un conjunto de registros conocidos (cuentas, transacciones de prueba) entre origen y restaurado
  - [ ] Confirmar que Firefly III arranca correctamente contra la base de datos restaurada
- [ ] Documentar el procedimiento (AC: #3, #5)
  - [ ] Escribir el runbook paso a paso en `infra/backups/restore-runbook.md`
  - [ ] Anotar el tiempo total que tomó la restauración
- [ ] Limpiar el entorno de prueba tras la validación (AC: #4)

- Justificación explícita de por qué esta prueba es indispensable y no opcional: "Probar la restauración al menos una vez (un backup que nunca restauraste no es un backup, es una promesa)." [Source: docs/plan/system-design-asistente-gastos.md#4-scale-and-reliability]
- Esta historia es el segundo de los dos pasos que el diseño marca como prioridad ante el riesgo real del sistema: "El verdadero riesgo no es la disponibilidad, es la pérdida de datos. Prioriza: 1. [Source: docs/plan/system-design-asistente-gastos.md#4-scale-and-reliability]
- La Definition of Done del proyecto exige probar manualmente "el camino feliz y al menos un caso de error" — para esta historia el camino feliz es la restauración exitosa con datos coincidentes; un caso de error razonable a ejercitar es un backup corrupto o incompleto (ver Testing, edge cases). [Source: docs/plan/backlog-scrum-completo.md#4-definition-of-done-dod]
- Alcance de "toda la base de datos" heredado de la historia 0.4: como el backup de 0.4 cubre tanto la base de datos de Firefly III como la del Bot Service, la prueba de restauración de esta historia debe validar ambas, no solo una. [Inference, consistente con docs/plan/backlog-scrum-completo.md#épica-0-infraestructura-base]
- El entorno de prueba debe estar aislado de producción — no está enunciado como AC explícito en el backlog original, pero se desprende directamente de la propia redacción de HU-05 ("lo restauro en un entorno de prueba") y es una práctica elemental para no arriesgar sobrescribir datos reales durante la prueba. [Inference]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** ejercicio operativo manual, no automatizado — es en sí mismo un simulacro de recuperación ante desastres (disaster recovery drill), no una suite de tests de código.
- **Key scenarios:** restauración completa desde el backup más reciente; restauración desde un backup de varios días atrás (para confirmar que backups históricos también son válidos); comportamiento ante un archivo de backup corrupto o truncado.
- **Per-AC verification:** AC #1 → comparar recuento de registros y algunos valores puntuales (montos, fechas) entre la base original y la restaurada; AC #2 → repetir la comparación para ambas bases de datos por separado; AC #3 → otra persona (o el mismo autor días después) debe poder seguir el runbook sin tener que adivinar pasos no escritos; AC #4 → confirmar que el entorno de prueba usa una red/volúmenes distintos a los de producción antes de empezar; AC #5 → el runbook o un log debe indicar la marca de tiempo de inicio y fin del proceso.
- **Fixtures / mocks:** el backup real más reciente generado por 0.4 (no datos sintéticos) para que la prueba sea representativa; un `docker-compose` de restauración aislado, descartable al terminar.
- **Edge cases to cover:** backup incompleto o corrupto (el proceso debe fallar de forma clara, no restaurar datos parciales silenciosamente); versión de la imagen de base de datos en el entorno de prueba distinta a la de producción (puede afectar compatibilidad del dump); espacio en disco insuficiente en el entorno de prueba para el volumen restaurado.
