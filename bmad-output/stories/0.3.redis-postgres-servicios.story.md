# 0.3.redis-postgres-servicios: Redis y Postgres como servicios separados del bot

**Story ID:** 0.3
**Epic:** 0 — Infraestructura base
**Slug:** redis-postgres-servicios
**Status:** done   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **desarrollador**,
I want **desplegar Redis y Postgres como servicios separados del proceso del Bot Service**,
so that **el bot tenga estado compartido (historial, colas) y almacenamiento de usuarios sin depender de un archivo local embebido**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Dado el `docker-compose.yml` del proyecto, cuando se levantan los servicios, entonces existe un contenedor Postgres dedicado al Bot Service (distinto del de Firefly III de la historia 0.1) alcanzable por variables de entorno (`DATABASE_URL`). [Source: docs/plan/backlog-scrum-completo.md#épica-0-infraestructura-base]
2. Dado el mismo `docker-compose.yml`, cuando se levantan los servicios, entonces existe un contenedor Redis alcanzable por variable de entorno (`REDIS_URL`). [Source: docs/plan/backlog-scrum-completo.md#épica-0-infraestructura-base]
3. Ambos servicios corren como contenedores independientes del proceso del futuro Bot Service — no embebidos ni acoplados a su ciclo de vida — de forma que puedan escalar, reiniciarse o migrarse de host de forma independiente. [Source: docs/plan/system-design-v2-multiusuario.md#4-cambios-en-el-bot-service]
4. El contenedor Postgres persiste datos en un volumen nombrado, distinto del volumen de la base de datos de Firefly III (historia 0.1). [Inference]
5. Ninguno de los dos servicios queda expuesto públicamente — solo son alcanzables dentro de la red Docker interna del proyecto. [Inference]

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.
     Cite every fact: [Source: prd.md#anchor] / [Source: architecture.md#anchor] /

- Requisito de origen: HU-03 — "Como desarrollador, quiero desplegar Redis y Postgres como servicios separados del bot, para soportar estado compartido y colas." Criterio: "Dado el docker-compose, cuando levanto los servicios, entonces el bot puede conectarse a ambos por variables de entorno." [Source: docs/plan/backlog-scrum-completo.md#épica-0-infraestructura-base]
- Cambio de arquitectura v1 → v2 que motiva esta historia: el **historial de conversación** pasa de SQLite a **Redis** (TTL corto, soporta escritura concurrente sin bloquear), y **usuarios + PAT** pasan de una tabla simple en SQLite a **Postgres**, con el PAT cifrado en reposo. [Source: docs/plan/system-design-v2-multiusuario.md#4-cambios-en-el-bot-service]
- Motivo explícito de separar estos servicios del proceso del bot: "Sigue siendo un solo host [...] pero ahora con Postgres y Redis como piezas separadas (no embebidas en el proceso del bot), para poder mover servicios a hosts distintos después sin rediseño, solo cambiando variables de conexión." [Source: docs/plan/system-design-v2-multiusuario.md#6-infraestructura-actualizada]
- Impacto en el dimensionamiento del VPS: sumar Postgres + Redis (además de PHP-FPM de Firefly y Node del bot) sube el piso recomendado a **4 vCPU / 8GB**, por la carga concurrente extra. [Source: docs/plan/system-design-v2-multiusuario.md#6-infraestructura-actualizada]
- Uso futuro de cada servicio (no implementado en esta historia, solo se deja la infraestructura lista): Postgres almacenará `usuarios_autorizados` (con PAT cifrado, Épica 1) y `log_auditoria_ia` (Épica 8); Redis servirá tanto para `historial_conversacion` con TTL corto (Épica 5) como para la cola BullMQ de procesamiento asíncrono (Épica 6). [Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive] [Source: docs/plan/system-design-v2-multiusuario.md#6-infraestructura-actualizada]
- Esta historia **no** crea el esquema de tablas (`usuarios_autorizados`, `log_auditoria_ia`) ni configura BullMQ — solo despliega los contenedores y deja la conectividad lista por variables de entorno; el esquema y su uso concreto son responsabilidad de las historias de Épica 1 (PAT cifrado), Épica 5 (memoria de conversación) y Épica 6 (cola). [Inference, alineado con el "Out of scope" de la épica 0 en `bmad-output/epics.md`]
- Este Postgres es una instancia **distinta** de la desplegada en la historia 0.1 para Firefly III — no deben compartir contenedor ni volumen, para mantener la separación de responsabilidades y evitar que un problema en una base de datos afecte a la otra. [Inference]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** validación manual de conectividad de infraestructura — no hay lógica de aplicación propia todavía que testear con unit tests.
- **Key scenarios:** ambos servicios arrancan sanos (`healthcheck` si se define); son alcanzables desde otro contenedor en la misma red Docker por su nombre de servicio; no son alcanzables desde fuera del host; Postgres persiste datos entre reinicios de contenedor.
- **Per-AC verification:** AC #1 → desde un contenedor auxiliar en la misma red, `psql $DATABASE_URL -c 'select 1;'` debe responder; AC #2 → `redis-cli -u $REDIS_URL ping` debe responder `PONG`; AC #3 → `docker compose stop bot-postgres redis` y volver a `docker compose start` no debe requerir reiniciar ningún otro servicio; AC #4 → escribir un registro de prueba en Postgres, hacer `docker compose down && docker compose up -d`, confirmar que el registro sigue ahí; AC #5 → intentar conectar a los puertos de Postgres/Redis desde fuera del host (o sin estar en la red Docker) debe fallar.
- **Fixtures / mocks:** un contenedor auxiliar temporal (p. ej. `postgres:16-alpine` o `redis:7-alpine` en modo cliente) para probar conectividad sin depender todavía del Bot Service real, que no existe hasta Épica 2.
- **Edge cases to cover:** variable de entorno mal formada (`DATABASE_URL`/`REDIS_URL` con typo); colisión de nombre de red/volumen con los servicios de Firefly III de la historia 0.1; falta de memoria si el VPS de prueba está por debajo del piso recomendado de 4 vCPU/8GB.

## Dev Agent Record

<!-- LEFT EMPTY by planning. The external dev tool fills this in during implementation. -->

**Desviación explícita del AC #5 ("no expuesto públicamente"):** el Dev Notes de esta historia cita "no expuesto públicamente" como [Inference], y las Tasks describen validar conectividad "desde un contenedor temporal en la misma red" — una lectura literal implicaría no publicar ningún puerto al host en absoluto. Eso rompería el sistema real: el Bot Service (historias 2.1+) corre como proceso `pm2` directo en el host, no dentro de este `docker-compose.yml`, así que necesita alcanzar Postgres/Redis por `localhost`. Se aplicó el mismo patrón ya verificado en producción para Firefly III en la historia 0.1 (`127.0.0.1:${PUERTO}:...`, nunca `0.0.0.0`): satisface la intención real del AC #5 ("no expuesto públicamente" = no alcanzable desde fuera del servidor) sin dejar la infraestructura inutilizable. Puertos elegidos no estándar (`5433`, `6380` en vez de `5432`/`6379`) para minimizar choque con otros Postgres/Redis que ya puedan correr en esta VPS de ~10 proyectos. [Inference]

**Archivos:**
- `infra/docker-compose.yml` — agregados `bot-postgres` (postgres:16-alpine) y `bot-redis` (redis:7-alpine), volúmenes nombrados `bot_postgres_data`/`bot_redis_data`, mismo `firefly-iii-net` que Firefly (no se creó una red nueva — no hay tráfico inter-contenedor real que aislar en un proyecto solo-dev de este tamaño).
- `infra/.env.example` — `BOT_DB_DATABASE`, `BOT_DB_USERNAME`, `BOT_DB_PASSWORD`, `BOT_DB_PORT` (default 5433), `BOT_REDIS_PORT` (default 6380).
- `bot-service/.env.example` — `DATABASE_URL`, `REDIS_URL` (no estaban en el Owned File/Module Scope original de esta historia ni en el de 1.1, pero son la forma en que el proceso del Bot Service —fuera de este compose— consume la infraestructura que esta historia levanta; omitirlos habría dejado la conexión sin documentar en ningún lado). [Inference]
- `infra/README.md` — sección nueva con comandos de verificación por AC.

**Verificado localmente (sin levantar el stack — regla del proyecto: Docker/compose de Firefly solo corre en la VPS remota):** `docker compose config` (con un `.env` temporal a partir de `.env.example`, nunca commiteado, borrado inmediatamente después) valida que el YAML resuelve sin errores — sintaxis, interpolación de variables, y que `bot-postgres`/`bot-redis` renderizan con los puertos/volúmenes/healthchecks esperados. Sin unit tests (consistente con la Testing Strategy de esta historia: "no hay lógica de aplicación propia todavía que testear").

**Verificado en producción (2026-09-12):** usuario desplegó (`git pull && docker compose up -d bot-postgres bot-redis`) y confirmó los tres AC pendientes:
- AC #1/#2 (conectividad) → `psql ... -c "select 1;"` devolvió `1` y `redis-cli -h bot-redis ping` devolvió `PONG` desde un contenedor auxiliar en `firefly-iii-net`.
- AC #5 (aislamiento) → `ss -tlnp | grep -E '5433|6380'` mostró ambos puertos bindeados a `127.0.0.1`, no a `0.0.0.0`/`:::` — no alcanzables desde fuera del servidor.
- AC #4 (persistencia) → `docker compose down && docker compose up -d` sin pérdida de datos.
