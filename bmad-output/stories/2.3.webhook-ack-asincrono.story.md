# 2.3: Confirmar webhook a Telegram inmediatamente y procesar de forma asíncrona

**Story ID:** 2.3
**Epic:** 2 — Bot de Telegram (esqueleto)
**Slug:** webhook-ack-asincrono
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **desarrollador del sistema**,
I want **que el Bot Service confirme el webhook a Telegram inmediatamente al recibirlo y procese el mensaje de forma asíncrona (fuera del ciclo de request/response del webhook)**,
so that **Telegram nunca reciba un timeout aunque lleguen varios mensajes de distintos usuarios al mismo tiempo, y el sistema quede preparado para picos de concurrencia**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. El endpoint `POST /webhook/telegram` responde `200 OK` a Telegram de forma inmediata (antes de completar cualquier lógica de procesamiento del mensaje, como llamar a Firefly/Gemini/el eco).
2. El procesamiento real del update (eco de 2.2, y en el futuro lógica de negocio) ocurre de forma desacoplada del ciclo de request/response HTTP del webhook — no bloquea la respuesta al endpoint.
3. Dado un pico de mensajes llegando al mismo tiempo (de uno o varios `chat_id`), Telegram nunca recibe un timeout ni un error 5xx por parte del Bot Service — corresponde a la AC original de HU-13. [Source: docs/plan/backlog-scrum-completo.md#épica-2-bot-de-telegram-esqueleto]
4. Si el procesamiento asíncrono de un mensaje falla, el fallo no afecta el ack ya enviado a Telegram (Telegram no reintenta un webhook ya confirmado con 200), y el fallo queda registrado (log) para diagnóstico.
5. El mecanismo de desacople elegido (ej. cola en memoria, `setImmediate`/microtask, o una cola liviana) no introduce una dependencia de infraestructura nueva no contemplada en Epic 2 (una cola persistente tipo BullMQ/Redis es explícitamente de Epic 6, fuera de alcance acá).

<!-- Keep to ~3-7. More than ~7 means the story is too big — split it. -->

## Tasks / Subtasks

- [ ] Separar el ack HTTP del procesamiento del update en el handler del webhook (AC: #1, #2)
  - [ ] Mover la lógica de eco/procesamiento (de 2.2) fuera del código que precede a `res.status(200).send()`
  - [ ] Responder `200 OK` tan pronto el payload se valida y se acepta (después de la verificación del `secret_token` de 2.1)
- [ ] Implementar el mecanismo de procesamiento asíncrono desacoplado (AC: #2, #5)
  - [ ] Encolar/disparar el procesamiento del update de forma no bloqueante (ej. `setImmediate`, cola en memoria simple, o equivalente liviano)
  - [ ] Documentar explícitamente que esto es un mecanismo provisional/in-process, no la cola BullMQ+Redis de Epic 6
- [ ] Manejo de errores del procesamiento asíncrono (AC: #4)
  - [ ] Envolver el procesamiento en try/catch de forma que una excepción no vuelva a tocar la respuesta HTTP ya enviada
  - [ ] Loggear el error con suficiente contexto (`chat_id`, `update_id`, mensaje de error)
- [ ] Prueba de carga simulada / concurrencia (AC: #3)
  - [ ] Simular varios updates llegando en paralelo y confirmar que todos reciben `200` sin degradación del tiempo de respuesta del ack

- Requisito de origen: "Como desarrollador, quiero que el bot confirme el webhook a Telegram inmediatamente y procese el mensaje de forma asíncrona, para evitar timeouts con múltiples usuarios simultáneos. Dado un pico de mensajes, cuando llegan al mismo tiempo, entonces Telegram nunca recibe un timeout." [Source: docs/plan/backlog-scrum-completo.md#épica-2-bot-de-telegram-esqueleto] (HU-13)
- NFR de la épica: "Concurrencia: ack inmediato + procesamiento asíncrono" es explícitamente el NFR que cubre esta historia. [Source: bmad-output/epics.md#epic-2-bot-de-telegram-esqueleto]
- El contrato de webhook ya establece `POST /webhook/telegram` como el endpoint — esta historia no crea un endpoint nuevo, modifica el comportamiento del existente (de 2.1/2.2) para separar ack de procesamiento. [Source: docs/plan/system-design-asistente-gastos.md#2-high-level-design]
- El diseño base señala explícitamente que, al volumen actual (decenas de mensajes/día), **"no hace falta cola"** — una cola persistente (BullMQ + Redis) recién se vuelve necesaria en la Épica 6 (control de costos y concurrencia). Esta historia debe resolver el ack asíncrono con un mecanismo liviano in-process, no adelantar la infraestructura de colas de Epic 6. [Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive]
- Idempotencia (descarte de updates duplicados por `update_id`) es una historia separada de Epic 6 (6.1 webhook-dedup-update-id) — está relacionada pero no es parte del alcance de esta historia; no implementar deduplicación acá. [Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive]
- Reintentos con backoff ante fallos de Gemini/Firefly también son de Epic 6 (6.4) — el manejo de errores de esta historia se limita a que un fallo en el procesamiento asíncrono no rompa el ack ya enviado, no a implementar una estrategia de reintentos. [Source: bmad-output/epics.md#epic-6-control-de-costos-y-concurrencia]
- Stack: Node.js + TypeScript, grammY o Telegraf (mismo Bot Service de 2.1/2.2). [Source: docs/plan/backlog-plan-implementacion.md#1-stack-tecnológico-recomendado]
- El mecanismo concreto de desacople (`setImmediate`, `queueMicrotask`, una cola en memoria tipo array+worker loop, etc.) no está prescrito por ninguna fuente — es una decisión de implementación con la única restricción explícita de no requerir Redis/BullMQ todavía. [Inference]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** tests de integración del endpoint del webhook midiendo el tiempo de respuesta del ack independientemente del tiempo que tarde el procesamiento simulado; test unitario del manejo de errores del procesamiento asíncrono.
- **Key scenarios:** el ack HTTP se responde antes de que termine un procesamiento simulado lento (ej. handler con delay artificial); varios updates concurrentes reciben cada uno su `200` sin bloquearse entre sí; una excepción lanzada durante el procesamiento asíncrono no afecta una respuesta HTTP ya enviada y queda logueada.
- **Per-AC verification:** AC #1 → test de integración que mide que la respuesta HTTP llega antes de que el handler de procesamiento (con un delay simulado) termine; AC #2 → inspección del código/flujo confirmando que el ack no depende del resultado del procesamiento; AC #3 → test de carga ligera enviando N requests concurrentes al endpoint y verificando que todos reciben `200` dentro de un tiempo aceptable; AC #4 → test unitario forzando una excepción en el handler de procesamiento y verificando que no se propaga a la respuesta HTTP, y que se genera un log de error; AC #5 → revisión de que no se introdujo ninguna dependencia de Redis/BullMQ en esta historia.
- **Fixtures / mocks:** handler de procesamiento simulado con delay artificial (para probar que el ack no espera); mock/stub que fuerza una excepción para probar el manejo de errores; script o herramienta simple para disparar N requests concurrentes contra el endpoint local.
- **Edge cases to cover:** ráfaga de mensajes del mismo `chat_id` en simultáneo; ráfaga de mensajes de distintos `chat_id` en simultáneo; el proceso del Bot Service se reinicia mientras hay procesamiento asíncrono pendiente (se documenta como limitación conocida del mecanismo in-process, no se resuelve acá — la persistencia de la cola es de Epic 6).
