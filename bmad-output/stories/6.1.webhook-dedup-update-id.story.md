# 6.1: Descartar webhooks duplicados usando update_id

**Story ID:** 6.1
**Epic:** 6 — Control de costos y concurrencia
**Slug:** webhook-dedup-update-id
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **desarrollador**,
I want **descartar webhooks duplicados de Telegram usando el `update_id`**,
so that **no se dupliquen transacciones cuando Telegram reintenta la entrega de un mensaje**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Cada webhook entrante de Telegram se valida contra un almacén de `update_id` ya procesados antes de ejecutar cualquier lógica de negocio (enqueue, IA, Firefly).
2. Si el `update_id` ya fue procesado, el handler responde 200 OK inmediatamente a Telegram sin volver a invocar el procesamiento (no vuelve a encolar ni a llamar Gemini/Firefly).
3. Si el `update_id` es nuevo, se registra en el almacén como parte del manejo del webhook y el procesamiento normal continúa.
4. Las entradas del almacén de deduplicación expiran automáticamente (TTL) para no crecer sin límite.
5. Dos entregas concurrentes del mismo `update_id` (reintento de Telegram mientras la primera sigue en vuelo) no producen doble procesamiento — la verificación es segura ante condiciones de carrera.
6. Si el almacén de deduplicación (Redis) no está disponible, el sistema no deja de responder a Telegram: degrada de forma explícita (ver Dev Notes) y deja rastro en logs.

- [ ] Integrar la verificación en el handler del webhook, antes de cualquier otro procesamiento (AC: #1, #2, #3)
  - [ ] Modificar `bot-service/src/telegram/webhookHandler.ts` (creado en Epic 2.3) para llamar `dedup.isDuplicate()` como primer paso
  - [ ] Si es duplicado: responder 200 OK y salir sin más efectos secundarios
- [ ] Manejar la caída de Redis sin bloquear el webhook (AC: #6)
  - [ ] Envolver la llamada a `isDuplicate` en try/catch; si Redis falla, loguear el error y tratar el mensaje como nuevo (fail-open) para no dejar de responder a los usuarios por una caída de infraestructura — ver nota de riesgo en Dev Notes
- [ ] Cubrir con pruebas unitarias los escenarios de AC #1-#6 (AC: #1, #2, #3, #4, #5, #6)

- Idempotencia: usar el `update_id` de Telegram para descartar webhooks duplicados, porque Telegram reintenta la entrega si el bot no responde a tiempo. [Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive]
- Objetivo explícito del backlog: "descartar webhooks duplicados de Telegram usando el `update_id`, para no duplicar transacciones" (HU-27). [Source: docs/plan/backlog-scrum-completo.md#épica-6-control-de-costos-y-concurrencia]
- El historial de conversación del Bot Service vive en Redis con TTL corto y soporta escritura concurrente sin bloquear — el mismo patrón (Redis + TTL corto) es el que corresponde usar para el almacén de deduplicación de `update_id`, ya que es el mismo tipo de estado efímero, no de negocio. [Source: docs/plan/system-design-v2-multiusuario.md#4-cambios-en-el-bot-service] [Inference: se reutiliza el mismo mecanismo de storage, no está explícitamente prescrito para dedup]
- Redis y Postgres quedan provistos como servicios separados del bot desde Epic 0 (story 0.3), así que esta historia puede asumir que hay una instancia de Redis alcanzable al construirse — no necesita levantarla ella misma. [Source: bmad-output/epics.md#epic-0-infraestructura-base]
- Esta historia solo necesita el esqueleto del bot (Epic 2) para existir — no depende de que el resto de la Épica 6 (cola, rate limiting, reintentos) esté construido, y puede adelantarse en el orden de desarrollo real aunque en `epics.md` aparezca numerada dentro de la Épica 6. [Source: bmad-output/epics.md#epic-6-control-de-costos-y-concurrencia]
- El webhook ya debe responder con ack inmediato y procesar de forma asíncrona (establecido en Epic 2, story 2.3) — la verificación de `update_id` debe ejecutarse como el primer paso de ese handler, antes de cualquier encolado o llamada a IA. [Source: bmad-output/epics.md#epic-2-bot-de-telegram-esqueleto]
- Decisión de degradación ante caída de Redis (fail-open: tratar como no-duplicado y loguear) no está especificada en ningún documento fuente; se elige fail-open porque dejar de responder a todos los usuarios por una caída puntual de Redis es peor que el riesgo acotado de una posible duplicación durante esa ventana — a revisar cuando exista el circuit breaker de la historia 6.4. ## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** pruebas unitarias del módulo `dedup.ts` con un cliente Redis simulado (mock/fake), más una prueba de integración ligera del `webhookHandler` verificando que la ruta de duplicado no llega a invocar el resto del pipeline.
- **Key scenarios:** `update_id` nuevo se registra y deja pasar el procesamiento; `update_id` repetido se descarta sin reprocesar; dos llegadas concurrentes del mismo `update_id` resuelven a exactamente un procesamiento; expiración por TTL; Redis caído no bloquea la respuesta al webhook.
- **Per-AC verification:** AC #1 → test que confirma que `isDuplicate` se invoca antes de cualquier otro efecto; AC #2 → test que confirma 200 OK y cero llamadas downstream en el camino de duplicado; AC #3 → test que confirma el registro del `update_id` nuevo; AC #4 → test que confirma el TTL configurado en el comando `SET`; AC #5 → test con dos invocaciones concurrentes simuladas sobre el mismo `update_id`, solo una debe ganar el `SET NX`; AC #6 → test que simula un error del cliente Redis y confirma que el webhook igual responde 200 OK y se loguea el fallo.
- **Fixtures / mocks:** cliente Redis simulado (ej. `ioredis-mock` o un stub propio de `SET`/`EXISTS` con soporte de NX/EX); payloads de webhook de Telegram de ejemplo con `update_id` fijo para poder repetirlos en los tests.
- **Edge cases to cover:** `update_id` ausente o malformado en el payload; ráfaga de más de dos duplicados del mismo `update_id`; Redis lento (timeout) vs. Redis caído (conexión rechazada).
