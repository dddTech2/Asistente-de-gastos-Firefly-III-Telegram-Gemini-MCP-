# 5.1: Armar prompt con historial + tools del MCP y llamar a Gemini

**Story ID:** 5.1
**Epic:** 5 — Integración con Gemini (conversación en lenguaje natural)
**Slug:** prompt-tools-gemini
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **desarrollador**,
I want **que el Bot Service arme el prompt (system prompt + historial corto + tool declarations traducidas del MCP) y llame a Gemini con function calling habilitado, ejecutando el ciclo completo tool-call → MCP → resultado → respuesta final**,
so that **quede la infraestructura base que habilita la conversación en lenguaje natural para el resto de las historias de la Épica 5**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. El Bot Service arma un prompt compuesto por: system prompt (persona + instrucciones de cuándo usar tools, en español), el historial corto de la conversación (últimos N mensajes leídos desde `historyStore`) y las `functionDeclarations` derivadas de las tools del MCP, y lo envía a Gemini usando el modelo `gemini-flash-latest`.
2. Las tools que expone el MCP de Firefly III (JSON Schema) se traducen automáticamente al formato `functionDeclarations` de Gemini en cada llamada — sin definiciones de tools hardcodeadas por fuera de esa traducción.
3. Cuando Gemini responde con un `functionCall`, el Bot Service invoca la tool correspondiente en el MCP Server vía `@modelcontextprotocol/sdk`, pasando el PAT propio del usuario (credenciales por-request, ya provisto por la Épica 4) — nunca un token compartido — y devuelve el resultado de la tool a Gemini para que arme la respuesta final en lenguaje natural.
4. Cuando Gemini responde directamente con texto (no necesita tool), el Bot Service devuelve ese texto al usuario sin intentar ninguna llamada a tool.
5. Cada intercambio (mensaje del usuario, tool call si hubo, parámetros, resultado) se loguea en formato estructurado, dejando la data mínima necesaria para que la Épica 8 (HU-31, tabla de auditoría) pueda construirse sobre esos logs sin tener que rediseñar el flujo.
6. Existe un módulo `historyStore` respaldado en Redis que expone lectura/escritura de los últimos N mensajes por `chat_id` (TTL corto) — el comportamiento fino de continuidad conversacional multi-turno se valida y ajusta en 5.5, pero la lectura/escritura básica ya funciona acá.

## Tasks / Subtasks

<!-- Every task maps to one or more ACs via (AC: #N). A task with no AC mapping is a smell. -->

- [ ] Crear `geminiClient.ts`: wrapper del SDK de Gemini configurado con `gemini-flash-latest` y function calling habilitado (AC: #1)
  - [ ] Inyectar la fecha/hora actual en el system prompt para que las referencias temporales relativas se resuelvan bien más adelante (5.3) (AC: #1)
- [ ] Crear `promptBuilder.ts`: compone system prompt + historial (vía `historyStore`) + tool declarations en un único payload para Gemini (AC: #1, #6)
- [ ] Crear `toolDeclarationsAdapter.ts`: traduce el JSON Schema de las tools del MCP a `functionDeclarations` de Gemini (AC: #2)
- [ ] Crear `mcpToolExecutor.ts`: ejecuta la tool solicitada por Gemini contra el MCP Server vía `@modelcontextprotocol/sdk`, propagando el PAT del usuario como header por-request (AC: #3)
- [ ] Crear `historyStore.ts`: cliente Redis con `getRecentMessages(chatId, n)` / `appendMessage(chatId, mensaje)`, TTL corto configurable (AC: #6)
- [ ] Crear `messageOrchestrator.ts`: orquesta el ciclo completo — recibe mensaje → arma prompt → llama Gemini → si hay `functionCall`, ejecuta tool y reenvía resultado a Gemini → devuelve respuesta final; si no hay `functionCall`, devuelve el texto directo (AC: #3, #4)
- [ ] Agregar logging estructurado del intercambio (mensaje, tool, parámetros, resultado) en cada paso del orquestador (AC: #5)
- [ ] Tests unitarios de `promptBuilder`, `toolDeclarationsAdapter` y `messageOrchestrator` con dobles de Gemini y del MCP client (AC: #1, #2, #3, #4)

- Historial de conversación: v2 lo mueve de SQLite a **Redis** (TTL corto, soporta escritura concurrente sin bloquear) porque el Bot Service debe ser stateless para poder correr 2+ réplicas. [Source: docs/plan/system-design-v2-multiusuario.md#4-cambios-en-el-bot-service]
- Modelo de datos original de `historial_conversacion` (rol, contenido, timestamp, TTL corto ~purgar >24h) sirve de referencia de forma aunque el backend pase de SQLite a Redis. [Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive]

- El control de costos/rate limiting de Gemini es explícitamente fuera de alcance de la Épica 5 (se resuelve en la Épica 6). [Source: bmad-output/epics.md#epic-5-integración-con-gemini-conversación-en-lenguaje-natural]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** unitario para `promptBuilder`, `toolDeclarationsAdapter` y `historyStore` (con Redis en memoria/mock); integración liviana para `messageOrchestrator` con dobles (mocks) de Gemini y del MCP client — sin llamadas reales a Gemini ni a un MCP real en esta historia.
- **Key scenarios:** armado de prompt con historial vacío vs. con mensajes previos; traducción correcta de una tool JSON Schema de ejemplo a `functionDeclaration`; ciclo completo con `functionCall` → ejecución MCP → respuesta final; ciclo sin `functionCall` (respuesta directa de texto).
- **Per-AC verification:** AC #1 → test de `promptBuilder` verifica que el payload enviado a Gemini incluye system prompt, historial y tools; AC #2 → test de `toolDeclarationsAdapter` compara el JSON Schema de entrada contra el `functionDeclaration` esperado; AC #3 → test de `messageOrchestrator` con un mock de Gemini que devuelve un `functionCall`, verificando que `mcpToolExecutor` se invoca con el PAT correcto y que el resultado se reenvía a Gemini; AC #4 → test con un mock de Gemini que devuelve texto directo, verificando que no se llama a `mcpToolExecutor`; AC #5 → test que verifica que el logger recibe el registro estructurado esperado en cada paso; AC #6 → test de `historyStore` sobre `getRecentMessages`/`appendMessage` con TTL simulado.
- **Fixtures / mocks:** JSON Schema de ejemplo de una tool del MCP (p.ej. `create_transaction`); respuestas mock de Gemini (con y sin `functionCall`); cliente MCP mockeado (`@modelcontextprotocol/sdk`); Redis mock/in-memory para `historyStore`.
- **Edge cases to cover:** historial vacío (primera interacción del usuario); Gemini devuelve un `functionCall` a una tool inexistente en las declaraciones (debe manejarse sin crashear, ver 5.4 para la ruta de aclaración formal); resultado del MCP con error inesperado (se comporta como excepción no capturada específicamente en esta historia, la clasificación fina de errores es de 5.4); Redis no disponible (la historia no necesita resolverlo del todo, pero no debe tirar la app entera — dejar como nota para 5.5/Épica 6).
