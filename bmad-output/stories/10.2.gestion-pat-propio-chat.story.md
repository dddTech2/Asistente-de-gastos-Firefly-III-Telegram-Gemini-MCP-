## Story

As a **usuario**,
I want **listar mis Personal Access Tokens de Firefly III (sin ver su valor), crear uno nuevo, y revocar uno existente, desde el chat**,
so that **pueda gestionar mis propios tokens (ej. para conectar Waterfly III, historia 7.1) sin entrar a la web**.

## Acceptance Criteria

<!-- LOCKED. -->

1. Un comando de listado muestra los PATs existentes del usuario por nombre/fecha de creación — **nunca** el valor del token en sí, que Firefly III no vuelve a exponer después de la creación (mismo comportamiento confirmado por el spike 1.2).
2. Un comando de creación (ej. `/nuevotoken Waterfly`) crea un PAT nuevo y lo entrega al usuario **una sola vez**, en un mensaje que dice explícitamente que no se puede recuperar después y que lo guarde en un lugar seguro.
3. Un comando de revocación (ej. `/revocartoken Waterfly`) pide confirmación explícita antes de ejecutar (AC #3 de 4.3, mismo criterio aunque esta historia no pasa por el MCP) — revocar un token que otra app está usando la deja sin acceso de inmediato.
4. Todas las operaciones usan el PAT de sesión del propio usuario (resuelto por `chat_id`) para autenticarse contra la API de administración de tokens de Firefly III.
5. El valor de un PAT (nuevo o existente) nunca aparece en un log de la aplicación, solo en el mensaje directo al usuario que lo generó.

<!-- Keep to ~3-7. -->

## Tasks / Subtasks

- [ ] Crear el cliente REST de gestión de PATs (listar, crear, revocar) reutilizando el patrón de `firefly-client.ts` (AC: #1, #2, #3)

- [ ] Auditar que el valor del PAT nuevo/existente nunca se loguea (AC: #5)

## Testing

<!-- LOCKED. -->

- **Approach:** Unitario con el cliente REST de PATs mockeado y `credential-resolver.ts` mockeado.
- **Key scenarios:** listado sin valores de token expuestos; creación con el mensaje de advertencia de "solo se muestra una vez"; revocación con y sin confirmación; revocación de un token inexistente.
- **Per-AC verification:** AC #1 → listado sin ningún campo de valor de token; AC #2 → mensaje de creación incluye la advertencia explícita; AC #3 → confirmación requerida antes de revocar; AC #4 → credenciales resueltas por `chat_id` antes de cualquier llamada; AC #5 → inspección de logs sin ningún valor de PAT (nuevo o existente).
- **Fixtures / mocks:** mock del cliente REST de PATs; mock de `credential-resolver.ts`.
- **Edge cases to cover:** nombre de token duplicado; revocar el único token que el usuario tiene; crear un token con un nombre vacío.
