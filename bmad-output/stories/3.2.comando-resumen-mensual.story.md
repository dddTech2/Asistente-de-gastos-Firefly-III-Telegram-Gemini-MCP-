# 3.2: Comando de resumen mensual de transacciones

**Story ID:** 3.2
**Epic:** 3 — Integración directa con Firefly III (sin IA todavía)
**Slug:** comando-resumen-mensual
**Status:** review   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **usuario autorizado del bot (en esta fase, el propio desarrollador)**,
I want **pedir un resumen de mis transacciones del mes con un comando simple (ej. `/resumen`)**,
so that **se verifique que la consulta a Firefly III también funciona, completando la validación del pipeline extremo a extremo antes de meter la capa de IA** [Source: docs/plan/backlog-scrum-completo.md#épica-3-integración-directa-con-firefly-iii-sin-ia-todavía].

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Dado un `chat_id` ya autorizado que envía el comando de resumen (ej. `/resumen`), cuando el Bot Service lo procesa, entonces consulta a Firefly III las transacciones del mes calendario en curso vía su API REST usando el PAT del desarrollador [Source: docs/plan/backlog-scrum-completo.md#épica-3-integración-directa-con-firefly-iii-sin-ia-todavía] [Source: docs/plan/backlog-plan-implementacion.md#épica-2-integración-directa-con-firefly-iii-api-sin-ia-todavía] (ítem: "Comando `/resumen` lista transacciones del mes").
2. Dado que existen transacciones en el mes en curso, cuando el bot responde, entonces el usuario recibe una lista o resumen legible de esas transacciones (al menos fecha, monto y descripción/concepto de cada una). [Inference]
3. Dado que NO existen transacciones en el mes en curso, cuando el bot responde, entonces informa claramente que no hay movimientos registrados este mes, en vez de devolver una lista vacía sin contexto o un error. [Inference]
4. Dado que Firefly III responde con un error (token inválido, timeout, 5xx), cuando se intenta obtener el resumen, entonces el bot informa al usuario que la consulta falló, sin exponer detalles técnicos internos ni el PAT [Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive] (sección "Error handling y reintentos").
5. El PAT usado es el mismo PAT fijo del desarrollador configurado en la historia 3.1 (misma variable de entorno) — no se introduce una resolución de PAT por-usuario en esta historia [Source: bmad-output/epics.md#epic-3-integración-directa-con-firefly-iii-sin-ia-todavía].

## Tasks / Subtasks

- [ ] Extender `firefly-client.ts` (creado en 3.1) con una función `listTransactions(desde, hasta)` que llame `GET /api/v1/transactions` con los parámetros de rango de fechas del mes en curso y el header `Authorization: Bearer <PAT>` (AC: #1)

## Dev Notes

- **Propósito explícito de la épica:** validar el pipeline extremo a extremo (Telegram → Firefly III) con comandos rígidos, ANTES de meter la capa de IA (MCP en Epic 4, Gemini en Epic 5). Este comando de resumen es la mitad "consulta" de esa validación — la mitad "escritura" la cubre 3.1 [Source: bmad-output/epics.md#epic-3-integración-directa-con-firefly-iii-sin-ia-todavía].
- **Prioridad relativa:** en el backlog original este ítem tiene prioridad 🟡 media (vs. 🔴 alta de `/gasto`) — es la historia menos crítica de la épica, aunque igual de necesaria para cerrar el checkpoint de validación [Source: docs/plan/backlog-scrum-completo.md#épica-3-integración-directa-con-firefly-iii-sin-ia-todavía] (HU-15, prioridad 🟡).
- **PAT del desarrollador, no multi-tenant todavía:** mismo PAT fijo por variable de entorno que introduce 3.1; esta historia NO agrega resolución de PAT por-usuario (eso vive en Epic 1/Epic 4) [Source: bmad-output/epics.md#epic-3-integración-directa-con-firefly-iii-sin-ia-todavía].
- **Llamada directa REST, sin MCP:** igual que 3.1, la consulta se hace directo desde el Bot Service a la API REST de Firefly III, sin pasar por el servidor MCP (que llega en Epic 4) [Source: docs/plan/backlog-plan-implementacion.md#épica-2-integración-directa-con-firefly-iii-api-sin-ia-todavía].
- **Autenticación y prefijo de API:** mismo mecanismo que 3.1 — header `Authorization: Bearer <PAT>` [Source: docs/plan/system-design-v2-multiusuario.md#3-la-pieza-que-hace-viable-la-opción-b-credenciales-por-request-en-el-mcp], prefijo `/api/v1/` confirmado en la documentación del proyecto para el endpoint administrativo `POST /api/v1/users` [Source: docs/plan/system-design-v2-multiusuario.md#5-aprovisionamiento-de-usuarios-nuevo-en-v2]. El endpoint exacto de listado de transacciones (`GET /api/v1/transactions`, con parámetros de rango de fechas) no está deletreado en la documentación del proyecto — se infiere por el mismo prefijo confirmado y por ser la operación REST estándar equivalente al `POST /transactions` del diagrama de secuencia de referencia [Source: docs/plan/diagrama-secuencia-flujo-chat.mermaid]. [Inference]
- **Caching mencionado en la arquitectura:** el documento base sugiere cachear en memoria listados de cuentas/categorías/presupuestos (cambian poco) con TTL de minutos [Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive] (sección "Caching"). Esto NO aplica directamente a listar transacciones (que cambian todo el tiempo) — no se recomienda cachear el resultado de este comando. [Inference]
- **Manejo de errores:** mismo patrón de circuit breaker simple que 3.1 — si Firefly no responde, contestar que el servicio no está disponible por ahora en vez de dejar al usuario esperando [Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive] (sección "Error handling y reintentos").
- **Regla de oro de storage:** el Bot Service no guarda su propia copia de los datos financieros — este comando solo lee de Firefly III y formatea la respuesta, no persiste nada localmente [Source: docs/plan/system-design-asistente-gastos.md#2-high-level-design].
- **Stack:** Node.js + TypeScript, grammY/Telegraf, reutilizando el router de comandos de Epic 2 [Source: docs/plan/backlog-plan-implementacion.md#1-stack-tecnológico-recomendado].
- **Definición de "mes en curso", nombre del comando (`/resumen`) y formato exacto de la respuesta:** no están fijados en el detalle en los documentos fuente más allá de "lista transacciones del mes" — se proponen como convención razonable para esta historia. [Inference]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** unit tests para el cálculo del rango de fechas del mes en curso y para el formateo de la respuesta; unit/integration tests mockeados para la nueva función `listTransactions` en `firefly-client.ts`; verificación manual del camino feliz y de un caso de error contra una instancia real/local de Firefly III.
- **Key scenarios:** mes con varias transacciones; mes sin transacciones; Firefly responde error (401/5xx); Firefly responde timeout; respuesta paginada con más de una página de resultados.
- **Per-AC verification:** AC #1 → test que confirma el `GET /api/v1/transactions` con el rango de fechas del mes en curso y el header `Authorization` correcto; AC #2 → test que confirma que la respuesta al usuario incluye fecha/monto/concepto de cada transacción devuelta; AC #3 → test con respuesta vacía de Firefly que confirma el mensaje de "sin movimientos"; AC #4 → test que simula error/timeout de Firefly y confirma el mensaje genérico de fallo, sin fuga del PAT; AC #5 → revisión de código/config que confirma que se reutiliza la misma variable de entorno de PAT que 3.1, sin lógica nueva de resolución por-usuario.
- **Fixtures / mocks:** respuestas mockeadas de `GET /api/v1/transactions` (lista con varias transacciones, lista vacía, respuesta paginada, error 401, error 500, timeout).
- **Edge cases to cover:** primer día del mes (rango de un solo día), transacciones justo en el límite de medianoche del mes, volumen alto de transacciones que fuerza paginación, zona horaria del servidor vs. zona horaria del usuario.
