# 2.2: El bot responde algo al usuario para confirmar que funciona

**Story ID:** 2.2
**Epic:** 2 — Bot de Telegram (esqueleto)
**Slug:** bot-echo-response
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **usuario del bot**,
I want **que el bot me responda algo cuando le escribo un mensaje**,
so that **sepa que el sistema está funcionando de punta a punta, antes de que tenga lógica de negocio real**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Cuando un usuario envía cualquier mensaje de texto al bot por Telegram, el bot responde con un mensaje de confirmación (echo del texto recibido o un mensaje fijo tipo "recibido: {texto}").
2. La respuesta llega al chat correcto (`chat_id` del remitente), usando la API de Telegram (`sendMessage`).
3. El bot responde solo a mensajes de texto; otros tipos de update (ej. stickers, fotos) no rompen el proceso — como mínimo no deben generar una excepción no controlada.
4. La respuesta se envía usando el mismo Bot Service y token configurados en 2.1 (bot-botfather-webhook) — no se crea un bot ni configuración nueva.

<!-- Keep to ~3-7. More than ~7 means the story is too big — split it. -->

## Tasks / Subtasks

- [ ] Parsear el `Update` de Telegram recibido en `POST /webhook/telegram` (AC: #1, #3)
  - [ ] Extraer `message.text` y `message.chat.id` del payload
  - [ ] Ignorar (sin error) updates sin `message.text` (stickers, fotos, etc.)
- [ ] Implementar el handler de eco (AC: #1)
  - [ ] Construir el mensaje de respuesta (echo o mensaje fijo de confirmación)
- [ ] Enviar la respuesta vía `sendMessage` de la API de Telegram (AC: #2, #4)
  - [ ] Usar el cliente grammY/Telegraf ya configurado en 2.1 para llamar `sendMessage` con el `chat_id` correcto
- [ ] Manejo defensivo de tipos de update no soportados (AC: #3)
  - [ ] Envolver el handler en try/catch para que un update inesperado no tumbe el proceso

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** unit tests del handler de parseo/eco con payloads simulados de Telegram; prueba manual end-to-end enviando un mensaje real al bot desde Telegram.
- **Key scenarios:** mensaje de texto simple produce una respuesta al `chat_id` correcto; update sin `message.text` (ej. sticker) no genera excepción ni respuesta rota; múltiples chats reciben cada uno su propia respuesta sin cruzarse.
- **Per-AC verification:** AC #1 → test unitario del handler con un `Update` de texto de ejemplo, verificar que se llama `sendMessage` con el contenido esperado; AC #2 → verificar que el `chat_id` usado en `sendMessage` coincide con el del update entrante; AC #3 → test unitario con un `Update` de tipo sticker/foto, verificar que no lanza excepción; AC #4 → prueba manual real contra el bot creado en 2.1.
- **Fixtures / mocks:** payloads JSON de ejemplo de `Update` de Telegram (mensaje de texto, sticker, foto); mock del cliente de la API de Telegram (`sendMessage`) para no hacer llamadas reales en los tests unitarios.
- **Edge cases to cover:** mensaje vacío o solo espacios; `Update` malformado (sin `message`); usuario que no está en la whitelist de Epic 1 (fuera de alcance de esta historia pero no debe romperse — se resuelve en 1.1).
