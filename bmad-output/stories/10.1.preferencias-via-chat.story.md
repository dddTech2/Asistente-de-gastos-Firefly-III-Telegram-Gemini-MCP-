## Story

As a **usuario**,
I want **ver y cambiar mis preferencias de Firefly III (moneda default, cuenta default, idioma) con un comando del bot**,
so that **no tenga que entrar a la web de Firefly III para un ajuste de configuración simple**.

## Acceptance Criteria

<!-- LOCKED. -->

1. Un comando (ej. `/preferencias`) sin argumentos muestra las preferencias actuales del usuario (moneda default, cuenta default, idioma) leídas de su cuenta real de Firefly III.
2. El mismo comando con un argumento válido (ej. `/preferencias moneda ARS`) cambia esa preferencia puntual y confirma el nuevo valor.
3. Un argumento inválido (moneda inexistente, cuenta que no le pertenece al usuario) es rechazado con un mensaje claro, sin llamar a la API de Firefly III con un dato que sabemos inválido de antemano cuando sea verificable localmente (ej. formato de moneda).
4. La operación usa el PAT del propio usuario (resuelto por `chat_id` vía `credential-resolver.ts` de la historia 1.5) — nunca el PAT del desarrollador ni uno compartido.
5. Ningún log ni mensaje de error expone el PAT del usuario.

<!-- Keep to ~3-7. -->

## Tasks / Subtasks

- [ ] Crear el cliente REST de preferencias de Firefly III (GET/PUT sobre el endpoint de preferencias) reutilizando el patrón de `firefly-client.ts` (AC: #1, #2, #3)
- [ ] Implementar el comando `/preferencias` (sin argumentos: mostrar; con argumentos: cambiar) (AC: #1, #2, #3)
- [ ] Resolver las credenciales del usuario vía `credential-resolver.ts` antes de cualquier llamada (AC: #4)
- [ ] Auditar los logs del comando para confirmar que no incluyen el PAT (AC: #5)

## Testing

<!-- LOCKED. -->

- **Approach:** Unitario con el cliente REST de preferencias mockeado (mismo patrón que `firefly-client.test.ts` de 3.1) y con `credential-resolver.ts` mockeado.
- **Key scenarios:** consulta sin argumentos; cambio válido de una preferencia; argumento inválido rechazado sin llamar a Firefly; chat_id sin credenciales disponibles (corta antes de llamar, mismo patrón que 1.5).
- **Per-AC verification:** AC #1 → preferencias actuales mostradas correctamente; AC #2 → cambio aplicado y confirmado; AC #3 → validación local rechaza formato inválido sin llamada de red; AC #4 → `credential-resolver.getUserCredentials` invocado con el `chat_id` correcto antes de cualquier llamada a Firefly; AC #5 → inspección de logs sin PAT.
- **Fixtures / mocks:** mock del cliente REST de preferencias; mock de `credential-resolver.ts` con PAT de prueba distinto por chat_id.
- **Edge cases to cover:** usuario sin PAT todavía configurado (1.4 en curso); cuenta default que no le pertenece al usuario (rechazar); moneda que Firefly no reconoce.
