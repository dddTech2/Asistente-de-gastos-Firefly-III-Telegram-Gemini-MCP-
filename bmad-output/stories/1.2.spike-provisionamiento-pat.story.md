# 1.2: Spike — provisionamiento de PAT (¿API admin o login manual?)

**Story ID:** 1.2
**Epic:** 1 — Autenticación y multi-tenancy
**Slug:** spike-provisionamiento-pat
**Status:** done   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

> **Nota de tipo de historia:** esta es una historia **SPIKE** (investigación con time-box), no una historia de construcción. Su entregable es una **decisión documentada**, no una feature. Los criterios de aceptación describen qué debe quedar respondido y documentado, no comportamiento de producto.

## Story

As a **desarrollador**,
I want **confirmar, con evidencia concreta contra la API de Firefly III, si el Personal Access Token (PAT) de un usuario nuevo se puede generar vía el endpoint admin (`POST /api/v1/users`) o si requiere que el usuario inicie sesión manualmente en `/profile`**,
so that **el flujo de alta de usuarios (historia 1.3) se diseñe sobre un hecho confirmado y no sobre un supuesto, evitando construir un flujo automatizado que en realidad es inviable (o renunciar a automatizar algo que sí era posible)**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Se documenta, con evidencia reproducible (respuesta real de la API contra una instancia de Firefly III de prueba, o cita textual de la documentación oficial de la API si la prueba en vivo no es posible), si `POST /api/v1/users` (ejecutado con un token de rol "owner") permite obtener el PAT del usuario recién creado en la misma respuesta o en una llamada de seguimiento inmediata.
2. Si la respuesta a #1 es negativa, se investiga y documenta si existe algún otro endpoint administrativo capaz de generar un PAT en nombre de otro usuario (p. ej. bajo el namespace de OAuth/personal access tokens de la API), o si queda confirmado que el PAT solo se genera manualmente desde `/profile` estando logueado como ese usuario.
3. El hallazgo se entrega como un documento corto y autocontenido (`docs/plan/spike-provisionamiento-pat-findings.md`) con: la pregunta original, la evidencia recolectada, la conclusión, y el flujo recomendado para la historia 1.3 (automático vs. semi-manual).
4. La conclusión indica explícitamente cuál de las dos variantes descritas en `system-design-v2-multiusuario.md §5` aplica, de forma que la historia 1.3 pueda implementarse sin ambigüedad.
5. Si la evidencia es inconclusa dentro del time-box de esta historia (ej. no hay acceso a una instancia de prueba), el documento lo declara explícitamente como riesgo abierto y recomienda tratar 1.3 con la variante semi-manual (la más conservadora) hasta resolverlo, en vez de bloquear el resto de la épica indefinidamente.

**Entregable:** [docs/plan/spike-provisionamiento-pat-findings.md](../../docs/plan/spike-provisionamiento-pat-findings.md)

**Método usado:** en vez de una prueba en vivo contra `POST /api/v1/users` (que habría requerido pegar el PAT owner en el chat — descartado por seguridad), se auditó directamente el código fuente oficial de Firefly III (rama `main`): `app/Api/V1/Controllers/System/UserController.php`, `app/Transformers/UserTransformer.php`, `routes/api.php`, `routes/web.php` y `app/Http/Controllers/Profile/OAuthController.php`. El AC #1 contempla explícitamente esta alternativa ("cita textual de la documentación oficial ... si la prueba en vivo no es posible") y esta evidencia es más fuerte que un único request porque describe el comportamiento determinista del código, no de una configuración particular.

**Hallazgo (AC #1 y #2):** `POST /api/v1/users` nunca devuelve un PAT (el `UserTransformer` solo serializa `id/created_at/updated_at/email/blocked/blocked_code/role/links`), y no existe ningún endpoint en `routes/api.php` para generar tokens en nombre de otro usuario. La generación de PAT (`POST /oauth/personal-access-tokens`) vive solo en `routes/web.php` bajo middleware de sesión web (`user-full-auth`) y usa `$request->user()->createToken(...)` — atado al usuario autenticado por sesión, sin parámetro de impersonación. Conclusión: **el PAT solo puede generarlo el propio usuario, logueado, desde `/profile`.**

**Conclusión y recomendación (AC #3, #4):** aplica la variante **(b) semi-manual** de `system-design-v2-multiusuario.md §5`. La historia 1.3 debe automatizar la creación de la cuenta vía `POST /api/v1/users`, pero incluir un paso explícito donde el usuario genera su propio PAT en `/profile` → OAuth → Personal Access Tokens y lo entrega al bot/admin.

**Riesgo abierto (AC #5):** ninguno de bloqueo — hallazgo conclusivo por evidencia de código fuente. Riesgo menor no bloqueante: revalidar esta conclusión si Firefly III cambia su mecanismo de tokens en una actualización mayor futura.
