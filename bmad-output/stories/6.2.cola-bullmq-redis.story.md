# 6.2: Cola de procesamiento BullMQ + Redis para mensajes entrantes

**Story ID:** 6.2
**Epic:** 6 — Control de costos y concurrencia
**Slug:** cola-bullmq-redis
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As an **administrador**,
I want **una cola de procesamiento (BullMQ + Redis) para los mensajes entrantes**,
so that **el sistema absorbe ráfagas de mensajes de varios usuarios sin bloquear el bot**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Todo mensaje entrante que pase el chequeo de deduplicación (6.1) se encola como un job de BullMQ en lugar de procesarse en línea dentro del handler del webhook.
2. Un proceso worker separado consume jobs de la cola y ejecuta el pipeline de interpretación (Gemini + tools de Firefly vía MCP, de Epic 5) por cada job.
3. La cola y el worker usan la instancia de Redis compartida provista en Epic 0 (story 0.3), a través de una configuración de conexión dedicada.
4. La concurrencia del worker (cuántos jobs procesa en paralelo) es configurable por variable de entorno, sin requerir cambios de código.
5. El estado de cada job (esperando, activo, completado, fallido) queda accesible a través de los mecanismos nativos de BullMQ, como base para la política de reintentos de la historia 6.4.
6. Bajo una ráfaga de webhooks concurrentes, el handler del webhook sigue respondiendo (ack) dentro del tiempo esperado por Telegram, independientemente de la profundidad de la cola.

Si procesás todo síncrono con 50 usuarios en ráfaga, arriesgás el timeout del webhook de Telegram." [Source: docs/plan/system-design-v2-multiusuario.md#4-cambios-en-el-bot-service]
- Objetivo explícito del backlog: "una cola de procesamiento (BullMQ + Redis) para los mensajes entrantes, para absorber ráfagas de varios usuarios sin bloquear el bot" (HU-24). [Source: docs/plan/backlog-scrum-completo.md#épica-6-control-de-costos-y-concurrencia]
- Con volumen de un solo usuario no hacía falta cola; se vuelve necesaria al escalar a varios usuarios concurrentes, para no bloquear el procesamiento y poder reintentar sin perder eventos si Gemini o Firefly están caídos en ese momento — la necesidad de la cola crece con la concurrencia, no es una decisión aislada de esta historia. [Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive]
- Infraestructura: Redis y Postgres quedan como piezas separadas del proceso del bot desde Epic 0, precisamente para soportar, entre otras cosas, esta cola. El tamaño de VPS recomendado (4 vCPU / 8GB) ya contempla la carga concurrente extra de los workers de la cola. [Source: docs/plan/system-design-v2-multiusuario.md#6-infraestructura-actualizada]
- La cola de trabajo (BullMQ) da, de forma nativa, el mecanismo de reintentos que se necesita para errores de Gemini/Firefly — la historia 6.4 configurará esas opciones de reintento sobre la cola que esta historia crea, en vez de reimplementar un loop de reintentos propio. [Source: docs/plan/system-design-v2-multiusuario.md#6-infraestructura-actualizada]
- El worker ejecuta el pipeline de Gemini + tools de Firefly vía MCP construido en Epic 5; si esta historia se implementa antes de que Epic 5 esté terminado, el job handler puede apoyarse en un stub del pipeline hasta que esté disponible. [Source: bmad-output/epics.md#epic-6-control-de-costos-y-concurrencia] [Inference: la secuencia exacta de stub vs. integración real no está prescrita en ningún doc]
- Stack: Node.js + TypeScript para el Bot Service, empaquetado con Docker Compose junto al resto del stack. [Source: docs/plan/backlog-plan-implementacion.md#1-stack-tecnológico-recomendado]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** pruebas unitarias de `messageQueue.ts` y `messageWorker.ts` contra una instancia de Redis en memoria/efímera (o `ioredis-mock` cuando BullMQ lo soporte, si no, un Redis real de test vía contenedor); prueba de integración del webhook confirmando que el ack ocurre antes de que termine el procesamiento del job.
- **Key scenarios:** un mensaje válido se encola y luego el worker lo procesa exactamente una vez; el ack al webhook ocurre sin esperar el resultado del job; varios mensajes concurrentes no bloquean el handler del webhook; el nivel de concurrencia del worker respeta el valor configurado.
- **Per-AC verification:** AC #1 → test que confirma que el handler llama a `queue.add` en vez de invocar el pipeline directamente; AC #2 → test que confirma que el worker invoca el pipeline de Gemini/MCP por cada job consumido; AC #3 → test/inspección de que `connection.ts` usa la config de Redis compartida; AC #4 → test que arranca el worker con distintos valores de `QUEUE_CONCURRENCY` y verifica el límite de jobs simultáneos; AC #5 → test que verifica que un job fallido queda en estado `failed` y uno exitoso en `completed`; AC #6 → prueba de carga ligera simulando ráfaga de N webhooks concurrentes midiendo el tiempo de respuesta del ack.
- **Fixtures / mocks:** Redis de test (contenedor efímero o mock compatible con BullMQ); stub del pipeline de Gemini/MCP de Epic 5 para no depender de credenciales reales en el test del worker; payloads de webhook de ejemplo.
- **Edge cases to cover:** cola vacía; worker caído mientras hay jobs pendientes (deben quedar disponibles al reiniciar); job que lanza una excepción no controlada dentro del pipeline; Redis no disponible al momento de encolar.
