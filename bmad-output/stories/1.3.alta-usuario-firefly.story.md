# 1.3: Flujo controlado de alta de cuentas Firefly III

**Story ID:** 1.3
**Epic:** 1 — Autenticación y multi-tenancy
**Slug:** alta-usuario-firefly
**Status:** done   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

> **Advertencia de dependencia:** el diseño concreto de esta historia (qué tan automatizada puede ser) **depende del resultado de 1.2 (spike de provisionamiento de PAT)**. Los criterios de aceptación de abajo cubren ambas variantes posibles; el dev tool debe implementar la que 1.2 haya confirmado como correcta, no ambas a la vez, salvo que 1.2 haya quedado inconclusa (ver AC #5 de 1.2, que recomienda la variante semi-manual como fallback conservador).

## Story

As a **administrador (el propio desarrollador)**,
I want **un flujo controlado para dar de alta a un usuario nuevo del bot**,
so that **cada uno de los ~50 usuarios tenga su propia cuenta Firefly III separada, aislada de las demás, sin tener que improvisar el proceso cada vez**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Dado un usuario nuevo (nombre, email, `chat_id` de Telegram), cuando el administrador ejecuta el flujo de alta, entonces existe una cuenta Firefly III separada para él, creada vía `POST /api/v1/users` con el token admin de rol "owner".
2. **Variante automática** (si 1.2 confirmó que el PAT se puede generar vía API admin): el flujo obtiene el PAT del usuario nuevo en el mismo proceso, sin que el usuario tenga que iniciar sesión manualmente en ningún momento.
3. **Variante semi-manual** (si 1.2 confirmó que el PAT requiere login del propio usuario): el flujo crea la cuenta vía API y luego guía explícitamente al administrador con los pasos a seguir (o un mensaje/instrucciones para reenviar al usuario) para que el usuario genere su PAT desde `/profile` y se lo entregue al administrador por un canal fuera del bot (no Telegram en texto plano — ver Dev Notes).
4. Como parte del mismo flujo (independientemente de la variante), el `chat_id` del usuario nuevo queda registrado en la tabla `usuarios_autorizados` (creada en 1.1) con `activo = true`, de forma que el usuario queda automáticamente habilitado por la whitelist de 1.1 al terminar el alta.
5. El PAT obtenido por cualquiera de las dos variantes se entrega en memoria/tránsito a la capa de cifrado y persistencia de la historia 1.4 — en ningún paso intermedio del flujo el PAT queda escrito en disco, en un log, o en una tabla en texto plano.
6. El flujo deja constancia (log mínimo, sin el PAT) de qué administrador ejecutó el alta, para qué `chat_id`, y cuándo — útil para la auditoría de Epic 8.

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** Integración contra una instancia de Firefly III de prueba (misma que usó el spike 1.2 si sigue disponible) para el flujo end-to-end de creación de cuenta; unitario para la lógica de orquestación (qué rama ejecutar, qué se le pasa a 1.1 y a 1.4) con el cliente de Firefly mockeado.
- **Key scenarios:** alta exitosa de un usuario nuevo (variante que corresponda según 1.2); intento de alta con `chat_id` ya existente (debe fallar o ser idempotente, a definir); fallo de la API de Firefly III a mitad del flujo (¿queda una cuenta huérfana sin `chat_id` registrado? debe manejarse explícitamente).
- **Per-AC verification:** AC #1 → test de integración que confirma que `POST /api/v1/users` crea la cuenta y devuelve un id de usuario válido; AC #2/#3 → test específico de la variante implementada (mock de la respuesta de la API para la automática, o test del punto de entrada manual para la semi-manual); AC #4 → test de que el repositorio de 1.1 recibe el `chat_id` con `activo = true` tras un alta exitosa; AC #5 → test/inspección de que el PAT nunca se escribe a disco/log en ningún paso intermedio (ej. grep de logs de test en busca de patrones de PAT); AC #6 → test de que el log de auditoría del alta se emite con los campos esperados y sin el PAT.
- **Fixtures / mocks:** cliente de Firefly III mockeado con respuestas de éxito y error de `POST /api/v1/users`; instancia de prueba de Firefly III para el camino de integración; PAT de prueba (dummy) para validar que no se filtra en logs.
- **Edge cases to cover:** falla la creación en Firefly pero ya se intentó registrar el `chat_id` (orden de operaciones: crear en Firefly primero, registrar whitelist después, solo si el alta fue exitosa); usuario con `chat_id` duplicado; timeout de la API de Firefly III durante el alta.

## Dev Agent Record

<!-- LEFT EMPTY by planning. The external dev tool fills this in during implementation. -->

**Variante implementada:** semi-manual (AC #3), conforme a la conclusión del spike 1.2
(`docs/plan/spike-provisionamiento-pat-findings.md`): Firefly III no tiene forma de generar
un PAT en nombre de otro usuario vía API admin — el usuario debe generarlo él mismo desde
`/profile` → OAuth → Personal Access Tokens y entregárselo al administrador.

**Archivos creados/modificados:**
- `bot-service/src/provisioning/firefly-admin-client.ts` — envuelve `POST /api/v1/users` con
  el token owner. No envía `role` en el body (el usuario nuevo no debe heredar privilegios de
  owner). Nunca intenta leer un token de la respuesta (el spike confirmó que el endpoint no
  puede devolver uno).
- `bot-service/src/provisioning/alta-usuario.ts` — orquestador con dos funciones:
  `ejecutarAltaUsuario` (AC #1, #4: crea la cuenta en Firefly y, solo si eso tuvo éxito,
  registra el `chat_id` en la whitelist con `activo=true`; devuelve las instrucciones de la
  variante semi-manual para el AC #3) y `entregarPatUsuario` (AC #5: recibe el PAT que el
  admin obtuvo del usuario y lo pasa directo a un `PatSink` inyectado — nunca lo persiste ni
  lo loggea — sin depender de que 1.4 exista todavía).
- `bot-service/src/db/usuarios.repository.ts` — se agregó el método `crear()` (INSERT
  parametrizado); coordinado con 1.1 que ya tenía `findByChatId()`.
- `bot-service/scripts/alta-usuario.ts` (**desviación del Owned File/Module Scope original**,
  que solo listaba `src/provisioning/*`): CLI de dos subcomandos (`crear`, `completar-pat`)
  necesaria porque sin un punto de entrada ejecutable el AC #1 ("cuando el administrador
  ejecuta el flujo de alta") no tiene forma real de correr — mismo patrón que
  `scripts/migrate.ts` de la historia 1.1. `completar-pat` usa un `PatSink` placeholder que
  imprime una advertencia y descarta el PAT en memoria (1.4 todavía no existe): cumple AC #5
  al no escribirlo nunca a disco/log, y dejará de ser un placeholder cuando 1.4 provea el sink
  real de cifrado/persistencia.
- `bot-service/src/config/env.ts` / `.env.example` — `FIREFLY_ADMIN_BASE_URL` y
  `FIREFLY_ADMIN_TOKEN`, deliberadamente **no** `required()` en el `env` compartido: solo los
  usa el script de alta, el proceso principal del webhook no debe depender de ese secreto.
- `bot-service/package.json` — script `alta-usuario`.

**Logging (AC #6):** `ejecutarAltaUsuario` loggea `{administrador, chat_id, firefly_user_id}`
sin el PAT (no participa en ese paso). `entregarPatUsuario` loggea `{administrador, chat_id}`
sin el PAT — verificado también que `logger.ts` (historia 8.1) redacta la clave `pat` como
barrera adicional.

**Decisión de diseño — chat_id duplicado:** `ejecutarAltaUsuario` **falla explícitamente**
(no es idempotente) si el `chat_id` ya está en la whitelist, antes de siquiera llamar a
Firefly. Elegido sobre la alternativa idempotente porque un alta duplicada casi seguro indica
un error del administrador (chat_id mal copiado) — fallar rápido evita crear una segunda
cuenta Firefly innecesaria para el mismo usuario.

**Edge case — cuenta huérfana:** orden de operaciones confirmado por test: Firefly primero,
whitelist después. Si Firefly tiene éxito pero el registro en la whitelist falla (ej. Postgres
caído en ese instante), la cuenta de Firefly queda huérfana sin `chat_id` asociado. A la
escala de esta historia (alta manual, ~10-50 usuarios) esto se repara a mano vía el log de
auditoría del intento fallido — no se construyó un mecanismo de rollback/saga automático
(fuera de scope de un dev-day, ver Dev Notes de la propia historia).

**Verificación local:** suite completa de `bot-service` (`npm test`): 51 passed, 2 skipped (los
2 skipped son la suite de integración de Postgres de 1.1, gated por Docker, sin relación con
esta historia). `npx tsc --noEmit`: sin errores. Nuevos tests: 5 en
`tests/provisioning/firefly-admin-client.test.ts` + `tests/db/usuarios.repository.test.ts`
(caso `crear`), 7 en `tests/provisioning/alta-usuario.test.ts` (AC #1, #3, #4, #5, #6, alta
duplicada, orden de operaciones en ambos sentidos de falla).

**No se construyó una prueba de integración en vivo contra Firefly III real:** la única
instancia disponible es la de producción (`firefly.nyoholding.com`); el spike 1.2 nunca llegó
a probarla en vivo (concluyó por auditoría de código fuente) y no existe una instancia de
staging separada. Automatizar un test que cree usuarios reales contra producción es un riesgo
mayor que el valor que aporta a esta escala — se cubre en cambio con tests unitarios
exhaustivos del cliente HTTP (`fetch` mockeado, request shape + casos de error) y del
orquestador (dependencias mockeadas). La verificación end-to end real queda para cuando el
administrador ejecute el script contra la VPS (ver instrucciones de despliegue).

**Verificado en producción (2026-09-12):** el usuario corrió ambos pasos contra la VPS real
(`firefly.nyoholding.com` + `bot-postgres`):
- `npm run alta-usuario -- crear ...` con un `chat_id` de prueba (`999000001`, no un chat real
  de Telegram — el comando no envía nada a Telegram) creó la cuenta en Firefly III (`id=2`),
  habilitó el `chat_id` en `usuarios_autorizados`, e imprimió las instrucciones de la variante
  semi-manual. El log estructurado confirmado en producción:
  `{"administrador":"dazad","chat_id":999000001,"firefly_user_id":"2","msg":"Alta de usuario
  ejecutada..."}` — sin PAT.
- `npm run alta-usuario -- completar-pat ...` con un PAT falso de prueba confirmó que el valor
  nunca aparece en el log ni en ningún archivo (AC #5) — solo la advertencia de que 1.4 todavía
  no existe.
- Datos de prueba limpiados después: fila de `usuarios_autorizados` borrada, cuenta
  `prueba@ejemplo.com` (id=2) borrada a mano desde `/admin/users`.

Todos los AC verificados (#1, #3, #4, #5, #6). AC #2 no aplica (variante automática descartada
por el spike 1.2).
