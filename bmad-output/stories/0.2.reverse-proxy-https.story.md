# 0.2.reverse-proxy-https: Reverse proxy con HTTPS automático

**Story ID:** 0.2
**Epic:** 0 — Infraestructura base
**Slug:** reverse-proxy-https
**Status:** done   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **desarrollador**,
I want **un reverse proxy con HTTPS automático delante de Firefly III**,
so that **exponga los servicios de forma segura, con certificados válidos que se renuevan solos**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Dado un dominio propio (o subdominio) apuntando al servidor, cuando se accede a Firefly III por HTTPS, entonces el certificado TLS es válido (emitido por una CA confiable) y el navegador no muestra advertencias. [Source: docs/plan/backlog-scrum-completo.md#épica-0-infraestructura-base]
2. El certificado se renueva automáticamente sin intervención manual antes de su expiración (renovación gestionada por el propio reverse proxy vía Let's Encrypt). [Source: docs/plan/backlog-scrum-completo.md#épica-0-infraestructura-base]
3. El reverse proxy (Nginx Proxy Manager o Traefik) se agrega como servicio en el `docker-compose.yml` existente y enruta el tráfico HTTPS hacia el contenedor de Firefly III de la historia 0.1. [Source: docs/plan/backlog-plan-implementacion.md#1-stack-tecnológico-recomendado]
4. El puerto interno de Firefly III no queda expuesto directamente al exterior — solo es alcanzable a través del reverse proxy. [Inference]
5. Las solicitudes HTTP (puerto 80) redirigen automáticamente a HTTPS (puerto 443). [Inference]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** validación manual de infraestructura de red/TLS — no aplica testing unitario; se verifica con el navegador y herramientas de línea de comandos (`curl`, `openssl s_client`).
- **Key scenarios:** emisión inicial de certificado contra un dominio real; renovación automática (verificar configuración de renovación, no esperar la expiración real); acceso HTTP redirige a HTTPS; acceso directo al puerto interno de Firefly III falla desde fuera de la red Docker.
- **Per-AC verification:** AC #1 → `curl -vI https://<dominio>` sin errores de certificado, o inspección visual en navegador; AC #2 → revisar la configuración/logs del proxy para confirmar que el job de renovación ACME está programado (no requiere esperar la expiración real); AC #3 → inspeccionar `docker-compose.yml` y confirmar que el proxy enruta al servicio de Firefly definido en 0.1; AC #4 → `curl` directo al puerto interno desde fuera del host debe fallar (conexión rechazada/timeout); AC #5 → `curl -I http://<dominio>` debe devolver un redirect 301/308 a HTTPS.
- **Fixtures / mocks:** ninguno — requiere un dominio real (o subdominio) resoluble por DNS apuntando al servidor de prueba/staging.
- **Edge cases to cover:** dominio mal apuntado (DNS no resuelve todavía); puerto 80/443 bloqueado por firewall del proveedor de VPS; fallo silencioso de renovación (verificar que el proxy deje evidencia en logs si la renovación falla).

## Dev Agent Record

- **2026-09-11/12 — Desviación deliberada de tecnología (Update, no re-planeación completa):**
  el Dev Notes original recomendaba Nginx Proxy Manager o Traefik como contenedor nuevo. Al
  implementar se descubrió que la VPS destino ya aloja ~10 proyectos previos con los puertos
  80/443 tomados por un **nginx instalado directo en el sistema operativo** (no containerizado)
  — el mismo patrón que ya usa `nyoholding-contact-api` (bindeado a `127.0.0.1`). Un contenedor
  NPM/Traefik intentando publicar 80:80/443:443 habría fallado por puerto ya en uso. Se optó por
  agregar un server block al nginx del host + `certbot --nginx`, replicando el patrón existente,
  en vez de introducir un reverse proxy containerizado nuevo. AC #1-#5 se cumplen igual con este
  enfoque; solo cambió el mecanismo, no el resultado.
- **Dominio usado:** `firefly.nyoholding.com`, DNS A confirmado apuntando a `163.245.216.230`
  antes de emitir el certificado.
- AC #1/#2 — verificado: `https://firefly.nyoholding.com` responde con certificado válido
  (emitido por `certbot --nginx`, sin advertencias en `curl`); renovación automática delegada al
  timer/cron de certbot ya existente en el sistema (compartido por todos los dominios de la VPS).
- AC #3 — verificado: server block de nginx enruta `firefly.nyoholding.com` → `127.0.0.1:8081`
  → contenedor `firefly-iii-app:8080`.
- AC #4 — verificado: `firefly-iii-app` se rebindeó de `0.0.0.0:8081` a `127.0.0.1:8081` en
  `docker-compose.yml`; `http://163.245.216.230:8081` ya no responde desde afuera del servidor
  (connection refused).
- AC #5 — verificado: `http://firefly.nyoholding.com` → `301` a `https://firefly.nyoholding.com`.
- **Bug encontrado y resuelto durante la implementación:** tras fijar `APP_URL=https://...` y
  limpiar el config-cache de Laravel, el login seguía redirigiendo a `http://` (sin “s”). Causa:
  Laravel no confía en el header `X-Forwarded-Proto` de un proxy no declarado como confiable, y
  genera URLs con el esquema de la conexión interna (HTTP, entre nginx y el contenedor) en vez
  del esquema real de la request del usuario. Fix: `TRUSTED_PROXIES=**` agregado al `.env` y al
  `docker-compose.yml` — seguro en este caso porque el puerto de Firefly solo es alcanzable desde
  `127.0.0.1`, nada externo puede falsear ese header.
- **Secuencia de despliegue real** (para no perder acceso a mitad de camino): 1) crear server
  block + `certbot --nginx` con Firefly aún en `0.0.0.0:8081` como fallback, 2) confirmar HTTPS
  funcionando, 3) recién ahí `git pull` + `docker compose up -d` para rebindear a `127.0.0.1` y
  cerrar el puerto directo.
