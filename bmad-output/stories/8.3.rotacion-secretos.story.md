# 8.3: Rotación y protección de secretos

**Story ID:** 8.3
**Epic:** 8 — Observabilidad y hardening
**Slug:** rotacion-secretos
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As an **administrador del sistema**,
I want **rotar y proteger todos los secretos (tokens, API keys, credenciales de base de datos, clave de cifrado) fuera del control de versiones**,
so that **se reduzca el riesgo de que una fuga de código o de un log exponga datos financieros de los 50 usuarios**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Ningún secreto (token del bot de Telegram, API key de Gemini, credenciales de Postgres/Redis, PAT admin de Firefly III, clave de cifrado usada para los PAT de usuario) está hardcodeado en el código fuente ni committeado en el repositorio — todos se cargan vía variables de entorno o un mecanismo de secretos equivalente.
2. Existe un `bot-service/.env.example` versionado que documenta cada variable de secreto requerida (nombre y propósito, sin valores reales), mientras que el `.env` real está excluido vía `.gitignore`.
3. El Bot Service falla rápido y con un mensaje claro al arrancar si falta alguna variable de secreto requerida, en vez de arrancar en un estado parcialmente configurado.
4. Existe un procedimiento documentado (runbook) para rotar cada tipo de secreto (API key de Gemini, token de Telegram, clave de cifrado de PAT, credenciales de Postgres/Redis) sin downtime no planeado del servicio.
5. La clave de cifrado usada para proteger los PAT de usuario en reposo (Postgres) es un secreto propio, distinto de cualquier otra credencial del sistema, y su rotación está contemplada en el runbook del AC #4 (incluye el paso de re-cifrar los PAT existentes con la clave nueva).

## Dev Notes

- Requisito original: "Como administrador, quiero rotar y proteger todos los secretos fuera del control de versiones, para reducir el riesgo de una fuga" (HU-33, prioridad 🔴 alta). [Source: docs/plan/backlog-scrum-completo.md#épica-8-observabilidad-y-hardening]
- Requisito no funcional de seguridad del sistema base: "datos financieros personales → TLS en tránsito, tokens con el menor alcance posible, todo self-hosted." Fundamenta por qué los secretos (tokens de alcance limitado) deben protegerse activamente y no solo confiarse a la infraestructura. [Source: docs/plan/system-design-asistente-gastos.md#1-requirements-gathering]
- Definition of Done del proyecto, aplicable a cualquier historia que toque datos sensibles: "Si toca datos sensibles (PAT, credenciales), quedaron cifrados/fuera de logs." Esta historia es la que formaliza ese principio a nivel de todo el sistema, no solo de una feature puntual. [Source: docs/plan/backlog-scrum-completo.md#4-definition-of-done-dod]
- El diseño v2 especifica explícitamente que el PAT de cada usuario debe quedar "cifrado en reposo" en Postgres, a diferencia del v1 que lo tenía en una tabla simple de SQLite sin ese requisito. Esto es lo que fundamenta el AC #5 (la clave de cifrado en sí es un secreto de primera clase que también necesita rotación). [Source: docs/plan/system-design-v2-multiusuario.md#4-cambios-en-el-bot-service]
- La arquitectura v2 introduce varias piezas de infraestructura nuevas con sus propias credenciales — Postgres y Redis como servicios separados del proceso del bot — cada una con su propio secreto de conexión que cae dentro del alcance de esta historia. [Source: docs/plan/system-design-v2-multiusuario.md#6-infraestructura-actualizada]
- El detalle de "sin downtime no planeado" del AC #4 y el mecanismo concreto de validación al arranque (AC #3) no están especificados en ningún documento de planeación — son decisiones de implementación razonables dado que el sistema corre en un solo VPS sin equipo de operaciones ("Sin equipo de operaciones — todo debe ser lo bastante simple para que lo mantengas solo" [Source: docs/plan/system-design-asistente-gastos.md#1-requirements-gathering]), por lo que un runbook simple y accionable por una sola persona es preferible a un mecanismo de secretos sofisticado (ej. Vault) que agregaría complejidad operativa no justificada para este volumen. [Inference]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** revisión estática/manual del repositorio (no hay "lógica de negocio" per se que testear con unit tests, salvo la validación de configuración al arranque); test unitario de la validación de variables de entorno requeridas.
- **Key scenarios:** arranque del Bot Service con todas las variables presentes (arranca normalmente); arranque con una variable de secreto faltante (falla con mensaje claro indicando cuál falta); intento de commitear un `.env` con valores reales (debe ser bloqueado por `.gitignore`, verificado con una inspección del árbol de git, no con un hook automatizado obligatorio a menos que el dev tool decida agregar un pre-commit hook como mejora).
- **Per-AC verification:** AC #1 → búsqueda manual/grep documentada sobre el árbol del repo confirmando ausencia de secretos en texto plano (esta historia documenta el procedimiento de auditoría, no ejecuta un escaneo automatizado como parte del testing de esta historia salvo que el dev tool decida incorporar una herramienta tipo `gitleaks` como mejora); AC #2 → revisión de que `bot-service/.env.example` cubre exactamente el mismo conjunto de variables que el esquema de validación del AC #3, sin desincronización; AC #3 → test unitario que instancia el validador de config con un objeto de entorno incompleto y verifica que lanza un error descriptivo antes de que el proceso intente conectarse a cualquier servicio; AC #4 y #5 → revisión del runbook contra una lista de chequeo de "¿este paso requiere detener el bot?" para cada tipo de secreto, y verificación de que el paso de re-cifrado de PAT queda descrito con su pre-condición (backup antes de re-cifrar) y su verificación post-rotación.
- **Fixtures / mocks:** objeto de variables de entorno de prueba con combinaciones completas/incompletas para el test de validación de arranque.
- **Edge cases to cover:** variable de entorno presente pero vacía (`""`) debe tratarse igual que ausente; rotación de la clave de cifrado de PAT con usuarios activos en ese momento (el runbook debe indicar una ventana de mantenimiento o un mecanismo de re-cifrado sin downtime, según lo que decida el dev tool); secretos que además de en `.env` podrían quedar expuestos en logs si 8.1 no está bien implementada — este AC #1 depende en la práctica de que la redacción de 8.1 funcione, aunque son historias independientes en su alcance de archivos.
