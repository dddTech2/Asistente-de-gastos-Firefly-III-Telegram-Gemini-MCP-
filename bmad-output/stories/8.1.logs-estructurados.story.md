# 8.1: Logs estructurados

**Story ID:** 8.1
**Epic:** 8 — Observabilidad y hardening
**Slug:** logs-estructurados
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As an **administrador del sistema (el propio desarrollador solo-dev)**,
I want **logs estructurados (JSON) de todo lo que hace el Bot Service — mensajes entrantes, llamadas a Gemini, llamadas a tools del MCP, errores**,
so that **pueda depurar problemas rápido sin tener que adivinar qué pasó en producción**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. El Bot Service emite logs en formato estructurado (JSON, un objeto por línea) en vez de `console.log` de texto libre, para todo evento relevante: webhook recibido, mensaje encolado/desencolado, llamada a Gemini (inicio/fin/error), llamada a tool del MCP (inicio/fin/error), y cualquier excepción no controlada.
2. Cada línea de log incluye como mínimo: `timestamp`, `level`, `chat_id` (cuando aplica), `update_id` de Telegram (cuando aplica, para correlacionar con la deduplicación de HU-27), y un `message`/`event` descriptivo.
3. El nivel de log (`debug`/`info`/`warn`/`error`) es configurable vía variable de entorno (`LOG_LEVEL`), sin requerir cambios de código ni redeploy.
4. Ningún log contiene el PAT de Firefly III de un usuario, la API key de Gemini, el token del bot de Telegram, ni cualquier otro secreto en texto plano — se redactan o se omiten explícitamente antes de escribir el log.
5. Los logs se emiten a `stdout`/`stderr` (no a un archivo propio), de forma que Docker los capture con el driver de logging estándar, sin infraestructura adicional (nada de ELK/Loki — ver Dev Notes sobre alcance).

## Tasks / Subtasks

- [ ] Elegir e instalar la librería de logging estructurado para el Bot Service (Node.js + TypeScript) (AC: #1, #3)
  - [ ] Evaluar `pino` (preferido por overhead bajo) vs. alternativas; documentar la elección con un comentario breve en `src/lib/logger.ts`
  - [ ] Configurar el logger para leer `LOG_LEVEL` desde `process.env` con un default seguro (`info`)
- [ ] Implementar redacción de secretos (AC: #4)
  - [ ] Configurar la lista de paths/campos a redactar (`pat`, `token`, `authorization`, `apiKey`, etc.) usando la opción de redacción nativa del logger elegido
  - [ ] Escribir un test unitario que confirme que un objeto con un campo `pat` no aparece en texto plano en la salida
- [ ] Instrumentar los puntos de entrada/salida clave con logging estructurado (AC: #1, #2)
  - [ ] Handler del webhook de Telegram: log al recibir (`update_id`, `chat_id`) y al responder
  - [ ] Cliente MCP: log antes y después de cada `tool_call`, incluyendo nombre de la tool y resultado (éxito/error), sin loguear el PAT usado en el header
  - [ ] Cliente de Gemini: log de inicio/fin de cada llamada, incluyendo duración
  - [ ] Manejador global de errores no controlados: log con `level: error` y stack trace
- [ ] Verificar que los logs van a stdout/stderr sin configuración adicional de Docker (AC: #5) (AC: #5)

La tabla `log_auditoria_ia` de la historia 8.2 es un registro de negocio distinto — auditoría de qué escribió el usuario y qué tool ejecutó la IA, persistida en base de datos, no en logs de proceso. ## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** unit tests para el logger y su configuración de redacción; test de integración ligero que ejercite el webhook handler y capture la salida de log para verificar forma/campos.
- **Key scenarios:** log de un webhook entrante válido; log de un error no controlado; log de una llamada a tool del MCP con un parámetro que contiene un PAT simulado (debe salir redactado); cambio de `LOG_LEVEL` vía variable de entorno afecta qué niveles se emiten.
- **Per-AC verification:** AC #1 → inspección de la salida de log tras simular cada evento (webhook, Gemini, tool MCP, error) y confirmar que es JSON parseable; AC #2 → aserciones sobre las claves presentes (`timestamp`, `level`, `chat_id`, `update_id`, `message`); AC #3 → test parametrizado que instancia el logger con distintos `LOG_LEVEL` y confirma qué niveles pasan; AC #4 → test de redacción con un payload que incluye `pat`/`token`/`apiKey` y assert de que el valor no aparece en texto plano en la salida serializada; AC #5 → verificación manual/documental de que no se escribe a ningún archivo (el dev tool no necesita levantar Docker para esto, solo confirmar que el logger apunta a stdout/stderr).
- **Fixtures / mocks:** payload de webhook de Telegram de ejemplo (`update_id`, `chat_id`, texto); respuesta simulada de una tool call del MCP con un header `Authorization` de ejemplo para probar la redacción; mock del cliente de Gemini para simular duración de llamada.
- **Edge cases to cover:** `chat_id`/`update_id` ausentes (ej. un error que ocurre antes de parsear el webhook) no deben romper el logger; un objeto de error sin `message` ni `stack`; un `LOG_LEVEL` inválido en la variable de entorno debe caer a un default seguro en vez de crashear el proceso al arrancar.
