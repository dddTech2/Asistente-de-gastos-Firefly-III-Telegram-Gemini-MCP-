# 4.4: Auditoría de cobertura de tools del MCP frente al catálogo completo de Firefly III

**Story ID:** 4.4
**Epic:** Epic 4 — Servidor MCP
**Slug:** auditoria-cobertura-tools-mcp
**Status:** backlog   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

> **`# COURSE-CORRECTION 2026-09-13`:** historia agregada íntegramente por la
> corrección de rumbo del 2026-09-13 (ver `bmad-output/decision-log.md`). El
> usuario pidió que ninguna función de Firefly III quede fuera del alcance del
> bot. Esta historia es un spike — análogo a 1.2 — para no asumir qué trae el
> MCP server elegido "de fábrica" antes de comprometer el diseño de las
> historias de Epic 5 que dependen de él.

## Story

As a **desarrollador**,
I want **auditar, contra una instancia real del MCP de Firefly III ya desplegada (4.1), qué funciones del catálogo completo de Firefly III (transacciones avanzadas, cuentas/pasivos, categorías/tags, presupuestos/piggy banks, automatización/bills/reglas, multi-moneda, reportes/insights) ya vienen cubiertas por sus tools "de fábrica" y cuáles no**,
so that **las historias de Epic 5 (5.6-5.12) sepan exactamente qué tools consumir tal cual, y cuáles requieren una extensión propia del MCP o un cliente REST directo (como el patrón de Epic 3) antes de poder escribir su implementación**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Contra el MCP real desplegado en 4.1 y ya explorado en 4.2, se ejecuta `tools/list` y se clasifica cada tool devuelta según a cuál de los 7 grupos funcionales de Firefly III pertenece (transacciones avanzadas, cuentas/pasivos, categorías/tags, presupuestos/piggy banks, automatización, multi-moneda, reportes/insights).
2. Para cada uno de los 7 grupos, el resultado de la auditoría dice explícitamente: **cubierto** (el MCP ya trae una o más tools suficientes), **cubierto parcialmente** (cubre algo del grupo pero no todo — se detalla qué falta), o **no cubierto** (ninguna tool del MCP atiende ese grupo).
3. Para cada grupo marcado como "no cubierto" o "cubierto parcialmente", el resultado de la auditoría recomienda explícitamente una de dos rutas: extender el MCP server (si es open-source y viable) o construir un cliente REST directo en el Bot Service (mismo patrón que `firefly-client.ts` de la historia 3.1) para ese grupo específico.
4. El resultado queda documentado en un único artefacto (`mcp/cobertura-firefly.md` o equivalente) que las historias 5.6-5.12 puedan citar directamente como su fuente de Dev Notes, evitando que cada una tenga que re-explorar el MCP por separado.
5. Ninguna de las conclusiones de la auditoría se basa en la documentación del MCP server únicamente — se verifica contra la instancia real vía MCP Inspector (mismo criterio que 1.2 aplicó para el spike de PAT: "confirmado por código/comportamiento real, no por lo que dice la documentación").

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** Exploratorio, igual que el spike 1.2 — sin lógica de negocio propia que unit-testear. La "prueba" de esta historia es la verificación manual contra el MCP real vía MCP Inspector, documentada en el artefacto de salida.
- **Key scenarios:** cada uno de los 7 grupos queda con un veredicto explícito (cubierto/parcial/no cubierto); para cada tool relevante se registra al menos un ejemplo de invocación real y su respuesta; los grupos no cubiertos tienen una recomendación concreta (extender MCP vs. REST directo), no solo "falta esto".
- **Per-AC verification:** AC #1 → el `tools/list` real queda capturado y clasificado; AC #2 → cada uno de los 7 grupos tiene un veredicto explícito en el artefacto de salida; AC #3 → cada grupo no-cubierto/parcial tiene una recomendación de ruta; AC #4 → `mcp/cobertura-firefly.md` existe y las historias 5.6-5.12 pueden citarlo; AC #5 → cada conclusión cita una invocación real (captura de MCP Inspector), no solo la documentación del MCP server.
- **Fixtures / mocks:** ninguno — es exploración contra la instancia real de Firefly III de desarrollo, con datos de prueba (nunca datos reales de un usuario) para probar cada tool.
- **Edge cases to cover:** una tool cuyo nombre sugiere pertenecer a un grupo pero cuyo comportamiento real (probado) no lo cubre del todo (ej. "listar cuentas" que no incluye pasivos) — documentar la discrepancia explícitamente; tools que el MCP expone pero que la clasificación de 4.2 ya había marcado como fuera de alcance por otro motivo (ej. administrativas) — no las incluyas en los 7 grupos, anotarlas aparte.
