# 5.5: Recordar contexto de los últimos mensajes

**Story ID:** 5.5
**Epic:** 5 — Integración con Gemini (conversación en lenguaje natural)
**Slug:** memoria-conversacion-corta
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **usuario**,
I want **que el bot recuerde el contexto de los últimos mensajes de la conversación**,
so that **no tenga que repetir información ya dada dentro de la misma conversación**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. `historyStore` (Redis, creado en 5.1) persiste los últimos N mensajes (turnos usuario/modelo) por `chat_id`, con TTL corto por inactividad, tal como lo define la arquitectura v2 del Bot Service.
2. Un mensaje de seguimiento que omite un dato ya dado en un turno reciente (ej. usuario dice "y también 5 mil en transporte" después de haber dado fecha/contexto en el turno anterior) se resuelve correctamente porque Gemini recibe ese historial reciente inyectado en el prompt.
3. El historial inyectado en cada llamada a Gemini está acotado a una ventana de tamaño N (no crece sin límite), para controlar el consumo de tokens/costo por mensaje.
4. Tras expirar el TTL por inactividad, el historial se limpia y el siguiente mensaje del usuario se trata como el inicio de una conversación nueva, sin arrastrar contexto obsoleto (stale) de una conversación anterior.
5. Escrituras concurrentes al mismo `chat_id` (ej. el usuario escribe varios mensajes seguidos muy rápido) no corrompen ni entrelazan mal el orden de los mensajes en el historial.

[Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive] [Inference]
- El control de costos de tokens de Gemini por mensaje (AC #3, ventana acotada) se relaciona con "Costo real de Gemini por usuario/mes" como métrica a trackear, y con el control de costos formal que la Épica 6 implementa a nivel de rate limiting — esta historia solo acota el tamaño del historial inyectado, no implementa rate limiting ni control de costo agregado (eso es explícitamente fuera de alcance de la Épica 5). - La primitiva Redis exacta (lista con `RPUSH`/`LTRIM`, o Redis Streams, u otra estructura) tampoco está fijada en los docs — se recomienda una estructura que garantice orden y evite condiciones de carrera bajo escritura concurrente del mismo `chat_id`, sin especificar la API exacta. [Inference]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** unitario para `historyStore` y `historyWindow` contra un Redis real de test (o `redis-mock`/contenedor efímero) para validar TTL y concurrencia de forma realista, dado que la corrección de condiciones de carrera es difícil de simular con un mock puro en memoria.
- **Key scenarios:** conversación de varios turnos donde un mensaje posterior omite un dato dado antes; historial que excede la ventana N (debe recortarse, conservando los mensajes más recientes); TTL que expira por inactividad (el siguiente mensaje no debe ver historial viejo); múltiples escrituras casi simultáneas al mismo `chat_id`.
- **Per-AC verification:** AC #1 → test de `historyStore` confirma que `getRecentMessages` devuelve los últimos N mensajes persistidos y que el TTL se resetea en cada `appendMessage`; AC #2 → test de flujo multi-turno con un mock de Gemini que resuelve correctamente un dato omitido gracias al historial inyectado; AC #3 → test de `historyWindow` con más de N mensajes en Redis confirma que el prompt final solo incluye los últimos N; AC #4 → test simula el paso del TTL (reloj controlado/mock de tiempo) y confirma que `getRecentMessages` devuelve vacío tras la expiración; AC #5 → test de escritura concurrente (varias llamadas a `appendMessage` en paralelo para el mismo `chat_id`) confirma que el orden final es consistente y no se pierden ni duplican mensajes.
- **Fixtures / mocks:** Redis real de test (contenedor efímero o instancia de test dedicada) para los casos de TTL/concurrencia; reloj controlado para simular expiración de TTL sin esperar el tiempo real; fixtures de conversación multi-turno con datos parcialmente omitidos en turnos posteriores.
- **Edge cases to cover:** primer mensaje de una conversación nueva (historial vacío, no debe fallar); historial exactamente en el límite N (no debe recortar de más ni de menos); Redis momentáneamente no disponible (esta historia no necesita implementar failover completo — Épica 6 endurece resiliencia — pero no debe crashear el proceso del Bot Service; dejar nota para retomar en Épica 6).
