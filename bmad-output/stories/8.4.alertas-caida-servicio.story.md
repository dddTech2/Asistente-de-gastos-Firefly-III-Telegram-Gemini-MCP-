# 8.4: Alertas de caída de servicio

**Story ID:** 8.4
**Epic:** 8 — Observabilidad y hardening
**Slug:** alertas-caida-servicio
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As an **administrador del sistema**,
I want **recibir una alerta si el Bot Service o Firefly III se caen**,
so that **me entere del problema antes que los usuarios y pueda actuar sin depender de que alguien me lo reporte**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Uptime Kuma está desplegado como servicio adicional en el mismo `infra/docker-compose.yml` del stack, sin requerir infraestructura nueva fuera del VPS existente.
2. El Bot Service expone un endpoint de salud (`GET /health` o equivalente) que responde `200 OK` solo cuando el proceso está listo para atender tráfico (incluye, como mínimo, verificar que puede alcanzar Postgres y Redis).
3. Uptime Kuma tiene configurado un monitor para el endpoint de salud del Bot Service y otro para el endpoint web de Firefly III, con un intervalo de chequeo razonable (ej. cada 1-5 minutos) para un sistema sin SLA contractual.
4. Cuando un monitor detecta una caída (según el umbral configurado en Uptime Kuma), se dispara una notificación a un canal donde el administrador la vea razonablemente rápido (ej. Telegram o email) — no basta con que quede solo visible en el dashboard de Uptime Kuma.
5. El procedimiento de configuración de los monitores y del canal de notificación queda documentado, de forma que sea reproducible si el VPS se reconstruye.

<!-- Keep to ~3-7. More than ~7 means the story is too big — split it. -->

## Tasks / Subtasks

- [ ] Agregar Uptime Kuma al `infra/docker-compose.yml` (AC: #1)

- [ ] Implementar el endpoint de salud en el Bot Service (AC: #2)
  - [ ] Verificar conectividad a Postgres y a Redis dentro del handler, devolviendo `503` si alguna falla en vez de un `200` optimista
- [ ] Configurar los monitores en Uptime Kuma (AC: #3)
  - [ ] Monitor HTTP para `GET /health` del Bot Service
  - [ ] Monitor HTTP para el endpoint web de Firefly III
- [ ] Configurar el canal de notificación (Telegram o email) en Uptime Kuma y probar que la alerta llega (AC: #4)
- [ ] Documentar el procedimiento de configuración de monitores y notificaciones en un runbook (AC: #5) (AC: #5)

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** test unitario del endpoint de salud (mockeando Postgres/Redis arriba/abajo); verificación manual/documentada de la configuración de Uptime Kuma (no hay lógica de negocio propia que testear ahí, es configuración de una herramienta de terceros).
- **Key scenarios:** endpoint de salud responde `200` cuando Postgres y Redis están disponibles; responde `503` (o el código que se decida) cuando alguno de los dos no responde; un monitor de Uptime Kuma detecta una caída simulada (deteniendo el contenedor correspondiente en un entorno de prueba, no en producción) y dispara la notificación configurada dentro del umbral esperado.
- **Per-AC verification:** AC #1 → `docker compose config` (validación estática del compose file) confirma que el servicio de Uptime Kuma está definido correctamente, sin necesidad de levantar producción; AC #2 → tests unitarios del handler de salud con mocks de Postgres/Redis en ambos estados (up/down); AC #3 → inspección de la configuración exportada/documentada de Uptime Kuma confirmando que ambos monitores existen con el intervalo esperado; AC #4 → prueba manual en un entorno no productivo: detener temporalmente el Bot Service o Firefly III y confirmar que la notificación llega al canal configurado dentro del umbral; AC #5 → revisión del runbook contra los pasos reales necesarios para recrear la configuración desde cero.
- **Fixtures / mocks:** cliente de Postgres y de Redis mockeados para simular ambos estados en el test del endpoint de salud.
- **Edge cases to cover:** Postgres disponible pero Redis caído (o viceversa) — el endpoint debe reportar `503` igual, no solo cuando ambos fallan; caída intermitente (flapping) que podría generar alertas repetidas — documentar en el runbook cómo Uptime Kuma maneja reintentos antes de marcar "down" para evitar ruido; el propio contenedor de Uptime Kuma cayéndose no tiene quién lo monitoree a él — se documenta como limitación conocida y aceptada dado el alcance del proyecto, no se resuelve con un segundo nivel de monitoreo (sobre-ingeniería para este tamaño).
