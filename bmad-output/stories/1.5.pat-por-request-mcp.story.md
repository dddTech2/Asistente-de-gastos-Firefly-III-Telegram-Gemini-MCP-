# 1.5: Cada llamada al MCP usa el PAT del usuario que escribió el mensaje

**Story ID:** 1.5
**Epic:** 1 — Autenticación y multi-tenancy
**Slug:** pat-por-request-mcp
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

> **Historia crítica de seguridad — no negociable.** Esta historia implementa el mecanismo que hace viable todo el diseño de arquitectura elegido (Opción B: una sola instancia de Firefly III para 50 usuarios). Un fallo aquí no es un bug cualquiera: es una fuga de datos financieros entre usuarios. [Source: docs/plan/backlog-scrum-completo.md#épica-1-autenticación-y-multi-tenancy]

## Story

As a **desarrollador**,
I want **que cada llamada al MCP de Firefly III use el PAT del usuario que escribió el mensaje — resuelto por `chat_id` en el momento de la llamada, nunca un token compartido ni cacheado entre usuarios**,
so that **el aislamiento de datos entre los 50 usuarios quede garantizado por Firefly III mismo a nivel de credencial, no por lógica custom mía que podría implementar mal**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Dado un mensaje entrante identificado por un `chat_id`, el Bot Service resuelve y descifra el PAT correspondiente (vía la capa de 1.4) **antes** de invocar cualquier tool del MCP para ese mensaje.
2. Existe un módulo/interfaz reutilizable (ej. una función `getUserCredentials(chatId)`) que retorna las credenciales listas para ir en la llamada al MCP (`Authorization: Bearer <PAT>` + URL de la instancia de Firefly III), consumible tanto por el cliente MCP del Bot Service como por pruebas aisladas (MCP Inspector, Epic 4).
3. Bajo ninguna circunstancia el PAT resuelto para un `chat_id` queda cacheado, reutilizado o expuesto en el contexto de ejecución de otro `chat_id` — el aislamiento es **por-request**, no por-proceso ni por-instancia del cliente MCP.
4. Si no existe un PAT válido para el `chat_id` que dispara la llamada (usuario no aprovisionado, o borrado de la whitelist), la ejecución se corta antes de contactar al MCP y se retorna un error claro al usuario — nunca se hace fallback a un PAT compartido, de otro usuario, o de un usuario "por defecto".
5. Pruebas automatizadas (unitarias, con el cliente MCP mockeado) demuestran que dos `chat_id` distintos, resueltos de forma concurrente en la misma ejecución del proceso, obtienen credenciales distintas y correctas sin cruce entre ellas.

## Tasks / Subtasks

- [ ] Implementar `credential-resolver.ts`: dado un `chat_id`, llama a la capa de descifrado de 1.4 y arma el objeto de credenciales `{ pat, fireflyUrl }` (AC: #1, #2)
- [ ] Integrar el resolver como paso obligatorio antes de cualquier invocación de tool del MCP en el pipeline del Bot Service (AC: #1)
- [ ] Diseñar el resolver como función pura sin estado compartido entre invocaciones (sin variables de módulo cacheando el último PAT resuelto) (AC: #3)
- [ ] Manejar el caso de `chat_id` sin PAT válido: cortar antes de la llamada al MCP y devolver un mensaje de error explícito al usuario, sin fallback (AC: #4)
- [ ] Escribir tests de concurrencia simulada: dos (o más) `chat_id` resueltos "al mismo tiempo" (invocaciones intercaladas/paralelas del resolver) deben devolver siempre las credenciales correctas para cada uno (AC: #5)
- [ ] Documentar en el propio módulo (comentario/README breve) que este es el punto de integración que Epic 4 (despliegue del MCP multi-tenant) y Epic 5 (Gemini) deben usar, para que no se reimplemente resolución de credenciales en otro lugar (AC: #2) [Inference]

## Dev Notes

- Esta es la pieza arquitectónica central que hace viable toda la decisión de usar una sola instancia de Firefly III para 50 usuarios (Opción B): "el MCP `@firefly-iii-mcp/server`... soporta recibir el **PAT y la URL de Firefly III como headers en cada request** (`Authorization: Bearer <PAT>`), en vez de tener un único PAT fijo por variable de entorno. Esto significa que **el Bot Service, al procesar el mensaje del usuario X, le pasa al MCP el PAT propio del usuario X** — nunca un token compartido. El propio Firefly III, al recibir esa llamada, solo devuelve/modifica los datos de ese usuario. La barrera de seguridad entre usuarios queda en el lugar correcto: adentro de Firefly III, no en lógica custom tuya que podrías implementar mal." [Source: docs/plan/system-design-v2-multiusuario.md#3-la-pieza-que-hace-viable-la-opción-b-credenciales-por-request-en-el-mcp]
- Advertencia explícita de la arquitectura que condiciona cualquier decisión futura de cambiar de MCP server: "si en algún momento cambias de MCP server, verifica que soporte este patrón (credenciales por request). Los que fijan un solo PAT vía variable de entorno al arrancar... son de un solo tenant." Esta historia (y su módulo `credential-resolver.ts`) asume y depende de que el MCP elegido soporte credenciales por-request — si Epic 4 evalúa un MCP alternativo, debe validarse contra este mismo requisito antes de adoptarlo. [Source: docs/plan/system-design-v2-multiusuario.md#3-la-pieza-que-hace-viable-la-opción-b-credenciales-por-request-en-el-mcp]
- Requisito equivalente en el backlog (HU-10), marcado explícitamente como la historia más crítica de seguridad de todo el proyecto: "Como desarrollador, quiero que cada llamada al MCP use el PAT del usuario que escribió el mensaje, para garantizar aislamiento total de datos entre usuarios. Dado el usuario A y el usuario B, cuando ambos usan el bot en paralelo, entonces ninguno ve datos del otro bajo ninguna circunstancia. 🔴 · 5 pts — **crítica de seguridad, no negociable**." [Source: docs/plan/backlog-scrum-completo.md#épica-1-autenticación-y-multi-tenancy]
- El readiness check confirma que esta es la decisión arquitectónica más sólida del proyecto y la razón por la que el NFR de aislamiento multiusuario está completamente cubierto: "Aislamiento multiusuario | Addressed | Credenciales por-request en el MCP (el PAT del usuario viaja en cada llamada, aislamiento lo hace Firefly III, no código propio) | Es la decisión arquitectónica más sólida del documento — bien justificada y con plan de validación (HU-34)." [Source: docs/plan/readiness-report-asistente-gastos-2026-09-11.md]
- **Alcance explícito de esta historia dentro de Epic 1:** el mapa de épicas marca como fuera de alcance de Epic 1 "el uso del PAT en llamadas MCP reales (Epic 4)" — el servidor MCP en sí todavía no está desplegado (eso es Epic 4.1/4.2). Esta historia construye y prueba el **mecanismo de resolución de credenciales** en el Bot Service (la mitad que le corresponde a Epic 1), de forma aislada con el cliente MCP mockeado; la integración end-to-end contra un MCP real ocurre en Epic 4 (que depende de esta historia según el cruce de dependencias del mapa de épicas: "Blocks: Epic 4 (el MCP multi-tenant depende de 1.4/1.5)"). [Source: bmad-output/epics.md — bloque de Epic 1, "Out of scope" y "Cross-epic dependencies"]
- El aislamiento debe ser **por-request**, no por sesión de proceso ni por instancia singleton del cliente MCP — cualquier patrón de caché de credenciales (incluso con buenas intenciones de rendimiento) reintroduce el riesgo que esta historia existe para eliminar. [Inference, derivado directamente de la cita de system-design-v2 §3 sobre "nunca un token compartido"]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** Unitario puro para el resolver de credenciales (con la capa de descifrado de 1.4 mockeada); pruebas de concurrencia simulada (invocaciones intercaladas/`Promise.all` con distintos `chat_id`) para demostrar ausencia de cruce; sin integración real contra el MCP en esta historia (eso es Epic 4.2, MCP Inspector) — sí contra un doble/mock del cliente MCP que registre qué credenciales recibió en cada llamada.
- **Key scenarios:** resolver credenciales para un `chat_id` válido devuelve el PAT y URL correctos; resolver para un `chat_id` sin PAT corta antes de llamar al MCP y no genera ninguna llamada saliente; dos resoluciones concurrentes para `chat_id` distintos no se cruzan (cada una recibe exactamente sus propias credenciales); no existe ningún estado de módulo que sobreviva entre invocaciones y pueda filtrar credenciales de una llamada anterior.
- **Per-AC verification:** AC #1 → test que confirma el orden de operaciones (resolver credenciales antes de invocar la tool) usando un espía/mock que registra la secuencia de llamadas; AC #2 → test de contrato de la función `getUserCredentials(chatId)` (forma del objeto retornado, incluye lo necesario para el header `Authorization`); AC #3 → test que ejecuta el resolver muchas veces con distintos `chat_id` en el mismo proceso y verifica ausencia de estado compartido (ej. usando `chat_id` aleatorios y aserciones de que la salida solo depende del input); AC #4 → test de `chat_id` sin PAT válido, confirmando que el mock del cliente MCP nunca recibe una llamada y que el usuario recibe un mensaje de error; AC #5 → test de concurrencia simulada con al menos 2-3 `chat_id` intercalados, aserta que cada resultado corresponde exactamente a su `chat_id` de origen.
- **Fixtures / mocks:** mock de la capa de descifrado de 1.4 (devuelve PAT distintos por `chat_id` de prueba); mock del cliente MCP que captura los headers/credenciales recibidos por invocación; conjunto de `chat_id` + PAT de prueba (dummy, nunca reales) que sea fácil de distinguir en las aserciones (ej. PAT que incluye el propio `chat_id` como parte del valor dummy, para detectar cruces de forma obvia en los tests).
- **Edge cases to cover:** `chat_id` que existía pero fue desactivado en la whitelist (1.1) entre la resolución y el uso (condición de carrera — decidir si se revalida); PAT presente pero corrupto/no descifrable (la capa de 1.4 debe fallar de forma segura y esta historia debe propagar ese fallo como "sin credenciales", no como excepción no manejada); alta concurrencia sintética (más `chat_id` simultáneos que los usados en el escenario básico) para dar más confianza sobre la ausencia de estado compartido, sin llegar a ser la prueba de carga formal de Epic 8 (HU-34).

- La función de descifrado de 1.4 (`obtenerPatDescifrado(chatId)`) es la dependencia directa de esta historia — confirmar su firma exacta y su comportamiento ante `chat_id` sin PAT (¿retorna `null`/`undefined` o lanza excepción?) antes de implementar el resolver, para que el manejo del AC #4 sea consistente con lo que 1.4 realmente expone (from 1.4).
