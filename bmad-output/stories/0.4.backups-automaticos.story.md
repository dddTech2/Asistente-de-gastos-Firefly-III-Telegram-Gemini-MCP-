# 0.4.backups-automaticos: Backups automáticos diarios de toda la base de datos

**Story ID:** 0.4
**Epic:** 0 — Infraestructura base
**Slug:** backups-automaticos
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As an **administrador**,
I want **backups automáticos diarios de toda la base de datos**,
so that **no pierda información financiera real de los usuarios**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Dado un cron (o contenedor programado) configurado, cuando pasa la medianoche, entonces aparece un backup nuevo en almacenamiento externo (no solo en el disco del VPS). [Source: docs/plan/backlog-scrum-completo.md#épica-0-infraestructura-base]
2. El proceso de backup cubre la base de datos de Firefly III (historia 0.1) **y** la base de datos Postgres del Bot Service (historia 0.3) — "toda la base de datos" incluye ambas instancias desplegadas hasta este punto de la épica. [Source: docs/plan/backlog-scrum-completo.md#épica-0-infraestructura-base]
3. El backup se sube a almacenamiento externo (S3, Backblaze B2 o equivalente) usando restic o `mysqldump`/`pg_dump` + cron, no queda únicamente en el disco local. [Source: docs/plan/backlog-plan-implementacion.md#1-stack-tecnológico-recomendado]
4. Cada corrida de backup deja evidencia de éxito o fallo (log o notificación) de forma que un fallo silencioso sea detectable. [Inference]
5. Las credenciales del almacenamiento externo (claves de acceso S3/B2) se manejan como secretos vía `.env`, nunca commiteadas al repositorio. [Source: docs/plan/backlog-scrum-completo.md#4-definition-of-done-dod]

## Tasks / Subtasks

- [ ] Elegir mecanismo de backup y agregarlo a la infraestructura (AC: #1, #3)
  - [ ] Definir script(s) de backup (`mysqldump`/`pg_dump` por base de datos, o `restic` si se prefiere backup incremental cifrado)
  - [ ] Agregar servicio/contenedor programado (cron dentro de un contenedor, o `cron` del host) en `infra/docker-compose.yml` / `infra/backups/`
- [ ] Cubrir ambas bases de datos (AC: #2)
  - [ ] Respaldar la base de datos de Firefly III (0.1)
  - [ ] Respaldar la base de datos Postgres del Bot Service (0.3)
- [ ] Configurar destino externo (AC: #1, #3, #5)
  - [ ] Configurar credenciales de S3/Backblaze B2 vía variables de entorno nuevas en `.env.example`
  - [ ] Confirmar que el backup sube exitosamente al bucket/destino remoto
- [ ] Logging y visibilidad de fallos (AC: #4)
  - [ ] El script registra resultado (éxito/error) con timestamp
  - [ ] Definir dónde queda ese log accesible para revisión manual (se conecta con Épica 8 — logs estructurados — pero esta historia solo necesita un log básico local)
- [ ] Programar la ejecución diaria (AC: #1)
  - [ ] Configurar cron (o el scheduler del contenedor) para correr a una hora fija fuera de horario pico

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** validación manual de infraestructura/operaciones — ejecución forzada del script de backup fuera de horario (sin esperar la medianoche real) para confirmar comportamiento, más revisión de logs.
- **Key scenarios:** ejecución programada dispara correctamente a la hora configurada; el archivo de backup aparece en el almacenamiento externo con timestamp correcto; un fallo de conexión al destino externo queda registrado y no se pierde silenciosamente; el backup incluye ambas bases de datos.
- **Per-AC verification:** AC #1 → forzar una ejecución manual del script/cron y confirmar que aparece un archivo nuevo en el bucket remoto; AC #2 → verificar que el backup contiene un dump identificable de cada una de las dos bases de datos (Firefly y Bot Service); AC #3 → confirmar en la consola del proveedor (S3/Backblaze) que el archivo subido no depende del disco local; AC #4 → simular un fallo (p. ej. credenciales inválidas temporalmente) y confirmar que el log deja constancia del error; AC #5 → `git status` no debe listar el `.env` con las credenciales reales, solo `.env.example` con las claves.
- **Fixtures / mocks:** un bucket/destino de prueba en el proveedor de almacenamiento externo (no el de producción) para no mezclar backups de prueba con los reales.
- **Edge cases to cover:** el destino externo no responde (red caída) — el script no debe fallar de forma que corrompa el backup local; el disco del VPS se queda sin espacio antes de subir el backup; el cron no corre porque el contenedor se reinició justo antes de la hora programada.
