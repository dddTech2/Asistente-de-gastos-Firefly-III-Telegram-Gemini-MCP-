# 1.1: El bot solo responde a chat_id registrados (whitelist)

**Story ID:** 1.1
**Epic:** 1 — Autenticación y multi-tenancy
**Slug:** whitelist-chat-id
**Status:** in-progress   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **usuario del sistema (dueño de la instancia)**,
I want **que el bot solo responda a `chat_id` de Telegram previamente registrados**,
so that **nadie ajeno pueda usar mi instancia ni intentar acceder a datos financieros a través del bot**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Existe una tabla `usuarios_autorizados` en Postgres con al menos `chat_id` (clave), `activo` (boolean) y timestamps de creación — sin columna de PAT todavía (esa la agrega la historia 1.4). [Source: docs/plan/system-design-v2-multiusuario.md#4-cambios-en-el-bot-service]
2. Dado un `chat_id` **no** registrado (o registrado con `activo = false`), cuando escribe al bot, entonces recibe un mensaje de "no autorizado" y ninguna otra lógica del bot se ejecuta para ese mensaje. [Source: docs/plan/backlog-scrum-completo.md#épica-1-autenticación-y-multi-tenancy]
3. Dado un `chat_id` registrado con `activo = true`, cuando escribe al bot, entonces el mensaje pasa el middleware de whitelist y continúa hacia el resto del pipeline (echo/eco de Epic 2 por ahora, ya que la lógica de negocio real todavía no existe).
4. La verificación de whitelist ocurre **antes** de cualquier llamada a Firefly III, Gemini o al MCP (cuando esas piezas existan), de forma que un `chat_id` no autorizado nunca dispara costo ni tráfico hacia ellas.
5. El intento de acceso no autorizado queda registrado (log estructurado mínimo: `chat_id`, timestamp, resultado) sin exponer datos de otros usuarios.

- [ ] Seed manual/documentado para dar de alta el primer `chat_id` (el del propio desarrollador) mientras 1.3 no existe todavía (AC: #3) [Inference]

- **Approach:** Unitario para el repositorio y el middleware (mockeando la conexión a Postgres); integración ligera con una base de datos de prueba (contenedor efímero) para validar la migración y la consulta real.
- **Key scenarios:** middleware bloquea `chat_id` desconocido; middleware bloquea `chat_id` con `activo = false`; middleware deja pasar `chat_id` activo; la migración crea la tabla con las columnas esperadas y es idempotente (no falla si se corre dos veces).
- **Per-AC verification:** AC #1 → test de migración/esquema (columnas y tipos correctos); AC #2 → test de middleware con `chat_id` inexistente e inactivo, verificando el mensaje de respuesta y que no se invoque el siguiente handler; AC #3 → test de middleware con `chat_id` activo, verificando que el pipeline continúa; AC #4 → test de orden de middlewares (whitelist registrado antes que cualquier handler de negocio); AC #5 → test de que el logger se invoque con `chat_id` + resultado y sin datos adicionales sensibles.
- **Fixtures / mocks:** Postgres de prueba con datos sembrados (`chat_id` activo, `chat_id` inactivo); mock del objeto de mensaje entrante de Telegram (grammY/Telegraf) con distintos `chat_id`.
- **Edge cases to cover:** `chat_id` con formato inesperado (string vs número); tabla vacía (ningún usuario dado de alta todavía); fallo de conexión a Postgres (¿el bot debe fallar cerrado — negar acceso — o abierto? recomendado fallar cerrado dado que el aislamiento es el NFR crítico) [Inference].

## Dev Agent Record

<!-- LEFT EMPTY by planning. The external dev tool fills this in during implementation. -->

**Adaptación de rutas:** el Owned File/Module Scope usa `bot-service/test/...` (singular) y nombres con punto (`whitelist.middleware.ts`); el proyecto real usa `bot-service/tests/` (como el resto de historias 2.x/8.1) y camelCase sin puntos (`whitelistMiddleware.ts`, consistente con `verifySecretToken.ts`, `echoHandler.ts`). Se siguió la convención real del repo, no la del Owned Scope original. [Inference]

**Diseño del middleware (AC #2, #3, #4):** se implementó como middleware nativo de grammY (`bot.use(createWhitelistMiddleware(bot, repo))`), registrado en `telegramWebhook.ts` ANTES de `registerEchoHandler` — en grammY, si un middleware no llama a `next()`, el resto de la cadena (echo, futura lógica de negocio) simplemente no corre para ese update. Esto da AC #2/#3/#4 gratis sin tener que orquestar manualmente un "pipeline" propio: grammY ya es ese pipeline.

**Bug encontrado y corregido durante el desarrollo:** la primera versión usaba `ctx.reply(...)` para el mensaje de "no autorizado", y los tests fallaban con `GrammyError: Call to 'sendMessage' failed! (401)` — investigando, `Bot.handleUpdate` de grammY crea una instancia de `Api` **nueva** por cada update (no reutiliza `bot.api`), así que `ctx.api`/`ctx.reply` no comparten cliente con lo que el resto del código ya usa. Se corrigió usando `sendTelegramMessage(bot, chatId, texto)` (el mismo wrapper de `src/telegram/sendMessage.ts` que ya usa `echoHandler.ts` desde la historia 2.2, exactamente por este motivo). Documentado en un comentario en el propio middleware para que no se repita el error en historias futuras que también necesiten responderle al usuario.

**Fail closed (edge case de Testing):** si `repository.findByChatId` lanza (Postgres caído/mal configurado), el middleware loggea `level: error` y **no** llama a `next()` — niega el acceso en vez de dejarlo pasar, tal como recomienda el Dev Notes ("el aislamiento es el NFR crítico").

**Repositorio (AC #1, #3):** `createUsuariosRepository(db: QueryableDb)` — `QueryableDb` es un subconjunto de `pg.Pool` (solo `.query`), para poder pasarle también un `pg.Client` suelto en el test de integración sin pelear con el tipado completo de `Pool`. `findByChatId` usa un parámetro `$1` (nunca interpolación de string) y castea `chat_id` (que Postgres/node-postgres devuelven como string para `BIGINT`, por precisión) de vuelta a `number`, consistente con cómo el resto del código ya trata `chat_id` (grammY lo tipa `number`).

**Migración (AC #1):** un solo archivo `CREATE TABLE IF NOT EXISTS` (idempotente). Se agregó `scripts/migrate.ts` (no estaba en el Owned Scope original) porque aplicar la migración a mano vía `psql` en cada deploy es más propenso a error que un `npm run migrate` — mismo patrón ya establecido con `npm run set-webhook`. Sin tabla de control de migraciones aplicadas: con un solo archivo no hace falta; si la carpeta crece lo suficiente, ese es el momento de sumar una (no antes). [Inference]

**`DATABASE_URL` ahora requerida:** se agregó a `src/config/env.ts` con `required(...)` — el proceso no arranca sin ella, consistente con que la whitelist es la primera barrera de seguridad del sistema, no una feature opcional.

**Verificado localmente:** `npm run build` limpio; `npm test` → 39/39 en verde + 2 tests de integración con Postgres real **skippeados** (no hay daemon Docker alcanzable en este entorno — `docker info` falla). Cobertura:
- `tests/db/usuarios.repository.test.ts` (4 tests, Postgres mockeado): AC #1 (columnas correctas vía shape del row), AC #2/#3 (activo/inactivo/inexistente), consulta parametrizada (sin riesgo de SQL injection).
- `tests/db/usuarios.repository.integration.test.ts` + `testPostgresContainer.ts` (2 tests, se saltan automáticamente sin Docker vía `describe.skipIf(!isDockerAvailable())` — corren completos en cualquier entorno con daemon Docker activo, p. ej. la VPS): AC #1 (la migración crea las columnas esperadas y es idempotente, corrida dos veces), AC #2/#3 (`findByChatId` contra datos reales sembrados).
- `tests/auth/whitelistMiddleware.test.ts` (6 tests, con un `Bot` real de grammY + `bot.handleUpdate()`, no una `ctx` fabricada a mano): AC #2 (chat_id inexistente e inactivo → bloqueado + mensaje), AC #3 (chat_id activo → pasa al siguiente handler), AC #4 (el handler downstream nunca se invoca si no autorizado), AC #5 (log con `chat_id`+`autorizado`, nunca el texto del mensaje), y dos edge cases (fail closed ante excepción de Postgres; update sin `chat_id` identificable no rompe ni consulta el repositorio).
- Los tests existentes de 2.1/2.2/2.3/8.1 (`telegramWebhook.integration.test.ts`, `webhookLogging.integration.test.ts`) se actualizaron para pasar un repositorio fake que autoriza todo (`tests/helpers/fakeUsuariosRepository.ts`) — no ejercitan la whitelist en sí, así que no cambiaron sus aserciones.
- `npm audit`: `pg` no agrega vulnerabilidades nuevas (mismas 7 preexistentes, dev-only + `qs` transitivo ya triagado en 2.1).
