## Story

As a **usuario**,
I want **que el bot me pida confirmación explícita antes de ejecutar una acción irreversible sobre mis datos de Firefly III (borrar una cuenta, borrar una transacción, reconciliar una cuenta, borrar una regla)**,
so that **puedo usar el chat para absolutamente todo lo que ofrece Firefly III, sin el riesgo de que una mala interpretación del lenguaje natural por parte de la IA me borre datos sin que yo lo haya pedido a propósito**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. A partir del catálogo de tools documentado en la historia 4.2, se clasifica cada tool en **irreversible** (borrado de cualquier entidad, reconciliación, cualquier operación que no tenga un "deshacer" razonable dentro de Firefly III) o **reversible** (todo lo demás: lectura, creación, edición) — con el criterio de clasificación documentado explícitamente.
2. El MCP server expone el catálogo **completo** de tools (ninguna se bloquea a nivel de protocolo) — a diferencia del alcance original de esta historia, no hay allowlist ni preset restrictivo aplicado en el MCP mismo.
3. El Bot Service intercepta toda invocación de una tool clasificada como irreversible **antes** de que su resultado se ejecute contra Firefly III, y le pide al usuario una confirmación explícita en el chat (ej. botón inline "Sí, borrar" / "Cancelar", o una respuesta de texto inequívoca) — la tool solo se ejecuta si el usuario confirma.
4. Si el usuario no confirma (cancela, ignora, o responde algo ambiguo), la acción irreversible NUNCA se ejecuta contra Firefly III, y el bot informa que quedó cancelada.
5. El mensaje de confirmación es específico y legible por humano (qué se va a borrar/reconciliar y de qué cuenta/transacción), nunca un JSON crudo de la tool ni el PAT del usuario.
6. La lista final de tools clasificadas como irreversibles/reversibles, junto con el criterio usado, queda documentada para que Epic 5 (Gemini) y Epic 8 (auditoría) sepan qué tools requieren el paso de confirmación.

El usuario, en la corrección de rumbo del 2026-09-13, priorizó cobertura completa sobre restricción — el mecanismo de seguridad pasa de "bloquear a nivel de protocolo" a "confirmar a nivel de conversación". [Source: bmad-output/decision-log.md#2026-09-13-course-correction]
- El catálogo de tools con su clasificación, producido en la historia 4.2, es el insumo directo de esta historia — no se debe re-explorar el catálogo desde cero aquí. [Source: bmad-output/epics.md#epic-4-servidor-mcp, secuencia ordenada de historias 4.2 → 4.3]
- **Por qué confirmación y no un segundo control técnico (ej. undo/soft-delete):** Firefly III no expone un mecanismo de papelera/soft-delete genérico para todas sus entidades vía API — confirmar ANTES de ejecutar es más simple y más seguro que depender de poder deshacer después. [Inference]
- El criterio "irreversible" es más angosto que el "destructiva/administrativa" original: una edición (ej. cambiar el monto de una transacción) es reversible (se puede volver a editar), mientras que un borrado o una reconciliación no lo son en la práctica. [Inference]
- Epic 5 (integración con Gemini) consumirá el catálogo completo de tools como schema de function-calling — el paso de confirmación vive en el Bot Service (esta historia), no en el prompt de Gemini ni en el MCP: no se depende de que el modelo "decida pedir permiso", el control es determinístico en código. [Inference, mismo principio de "la barrera de seguridad en el lugar correcto" que ya usa el proyecto para el aislamiento por-PAT — Source: docs/plan/system-design-v2-multiusuario.md#3-la-pieza-que-hace-viable-la-opción-b-credenciales-por-request-en-el-mcp]
- Fuera de alcance de esta historia: la integración real con Gemini y su prompt de sistema (Epic 5) — aquí solo se define la clasificación y el mecanismo de confirmación en el Bot Service, verificado con MCP Inspector simulando la tool call. [Source: bmad-output/epics.md#epic-4-servidor-mcp]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** Unitario para la lógica de clasificación (irreversible/reversible) y para el flujo de confirmación del Bot Service (con el cliente MCP mockeado, sin pegarle a un MCP real); verificación manual con MCP Inspector para confirmar que el catálogo expuesto por el MCP en sí sigue completo (sin restricción de protocolo).
- **Key scenarios:** una tool reversible se ejecuta directo, sin pedir confirmación; una tool irreversible dispara el mensaje de confirmación y NO se ejecuta hasta la respuesta; el usuario confirma → se ejecuta; el usuario cancela/ignora/responde ambiguo → nunca se ejecuta; el mensaje de confirmación nunca contiene el PAT ni un JSON crudo.
- **Per-AC verification:** AC #1 → revisión de la tabla de clasificación contra el catálogo completo de 4.2; AC #2 → `tools/list` contra el MCP real (vía MCP Inspector) confirma que el catálogo sigue completo, sin reducción; AC #3 → test que confirma el orden de operaciones (confirmación antes de ejecución) con un mock de tool irreversible; AC #4 → test de cancelación/no-respuesta que confirma que la tool nunca se invoca; AC #5 → test/inspección del contenido del mensaje de confirmación (sin PAT, sin JSON crudo); AC #6 → revisión de que la documentación quedó actualizada con la clasificación final.
- **Fixtures / mocks:** cliente MCP mockeado que registra si una tool irreversible fue invocada o no; catálogo de tools de prueba con al menos una reversible y una irreversible; simulación de respuestas del usuario (confirmar, cancelar, ambigua, sin respuesta/timeout).
- **Edge cases to cover:** una tool ambigua que combina lectura y escritura parcial — decidir explícitamente si cuenta como reversible o irreversible y documentar el porqué; el usuario confirma una acción pero el mensaje original ya no es válido (ej. la transacción que iba a borrar ya no existe) — la ejecución debe fallar de forma segura, no en silencio; múltiples confirmaciones pendientes simultáneas para el mismo `chat_id` (no cruzar cuál confirmación corresponde a cuál acción).
