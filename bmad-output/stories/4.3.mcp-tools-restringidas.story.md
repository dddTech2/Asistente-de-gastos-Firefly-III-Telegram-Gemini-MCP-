# 4.3: Limitar el set de tools expuestas por el MCP

**Story ID:** 4.3
**Epic:** Epic 4 — Servidor MCP
**Slug:** mcp-tools-restringidas
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **administrador**,
I want **limitar el set de tools que el servidor MCP expone**,
so that **la IA (Gemini, en Epic 5) no pueda ejecutar acciones destructivas o irreversibles (ej. borrar cuentas) contra los datos financieros de los usuarios**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. A partir del catálogo de tools documentado en la historia 4.2, se clasifica cada tool como permitida o bloqueada, con criterio explícito: tools de lectura y de creación/edición de transacciones quedan permitidas; tools de borrado (cuentas, transacciones, categorías, presupuestos) y cualquier tool administrativa (ej. gestión de usuarios, configuración global de Firefly III) quedan bloqueadas.
2. El MCP server se configura para exponer únicamente el subconjunto permitido — usando el mecanismo nativo del servidor (ej. preset de tools tipo `budget`/`basic` si existe, o allowlist explícita de nombres de tools) en vez de depender de que Gemini "decida no usar" una tool peligrosa.
3. Una llamada `tools/list` contra el MCP tras aplicar la restricción (verificable con MCP Inspector, reutilizando el procedimiento de 4.2) devuelve solo el subconjunto permitido — ninguna tool de borrado ni administrativa aparece en el listado.
4. Un intento directo de invocar una tool bloqueada por nombre (ej. vía MCP Inspector, simulando qué pasaría si Gemini de alguna forma la solicitara) es rechazado por el MCP con un error, no ejecutado.
5. La lista final de tools permitidas y bloqueadas, junto con el criterio de clasificación usado, queda documentada para que Epic 5 sepa con qué function-calling schema trabajará Gemini y para que futuras auditorías (Epic 8) puedan revisar la decisión.

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** Verificación de configuración con MCP Inspector como cliente de prueba, sobre el MCP ya desplegado (4.1) y ya explorado (4.2). No hay lógica de negocio propia que unit-testear — se valida que la configuración de restricción del MCP server de terceros efectivamente reduce el catálogo expuesto y bloquea invocaciones directas.
- **Key scenarios:** (a) `tools/list` antes de aplicar la restricción muestra el catálogo completo (línea base, ya cubierta por 4.2); (b) `tools/list` después de aplicar la restricción muestra solo el subconjunto permitido; (c) invocar por nombre una tool bloqueada devuelve un error explícito, no un resultado silencioso ni un crash; (d) invocar una tool permitida (lectura y escritura) sigue funcionando igual que en 4.2, confirmando que la restricción no rompió el flujo legítimo.
- **Per-AC verification:** AC #1 → revisión de la tabla de clasificación (permitida/bloqueada + criterio) contra el catálogo completo de 4.2; AC #2 → inspección de la configuración aplicada (preset o allowlist) en `infra/docker-compose.yml`/config del MCP; AC #3 → comparación del `tools/list` restringido contra la tabla de clasificación, confirmando 0 tools bloqueadas presentes; AC #4 → intento de invocación directa de una tool bloqueada y captura del error devuelto; AC #5 → revisión de que la documentación quedó actualizada con la lista final y el criterio.
- **Fixtures / mocks:** ninguno adicional a los ya usados en 4.1/4.2 (PATs de prueba, instancia Firefly III de desarrollo); no se mockea el MCP — se prueba la configuración real aplicada al servicio real.
- **Edge cases to cover:** una tool ambigua que combina lectura y escritura parcial (ej. "actualizar" una transacción existente) — decidir explícitamente si cuenta como permitida o bloqueada y documentar el porqué; el caso de que el MCP server no soporte ningún mecanismo de restricción nativo ni allowlist (si así fuera, marcarlo como concern de viabilidad, análogo al AC #1 de la historia 4.1, y no forzar un filtrado custom fuera del MCP que reintroduzca lógica de seguridad no confiable).
