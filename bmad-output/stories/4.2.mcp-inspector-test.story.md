# 4.2: Probar el MCP de forma aislada con MCP Inspector

**Story ID:** 4.2
**Epic:** Epic 4 — Servidor MCP
**Slug:** mcp-inspector-test
**Status:** done   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **desarrollador**,
I want **probar el servidor MCP de Firefly III de forma aislada con MCP Inspector, incluyendo el envío del PAT por-request**,
so that **pueda confirmar que las tools responden correctamente y que el aislamiento por credencial funciona antes de conectar el MCP a Gemini (Epic 5), donde un fallo sería más difícil de diagnosticar**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. MCP Inspector (`npx @modelcontextprotocol/inspector`) se conecta exitosamente al servidor MCP desplegado en la historia 4.1, usando el modo de transporte configurado (stdio o HTTP según lo documentado en 4.1).
2. Desde MCP Inspector, se configura el PAT de un usuario de prueba en el header/campo correspondiente por-request (no como variable de entorno del propio Inspector), replicando cómo lo hará el Bot Service en Epic 5.
3. El listado de tools (`tools/list`) expuesto por el MCP se revisa y se documenta: qué tools existen, qué parámetros esperan, y cuáles corresponden a operaciones de lectura vs. escritura vs. potencialmente destructivas — este inventario alimenta directamente la historia 4.3.
4. Al menos una tool de lectura (ej. listar cuentas o transacciones) y una tool de escritura (ej. crear transacción) se ejecutan desde MCP Inspector contra la cuenta del usuario de prueba, confirmando que el flujo de invocación y la respuesta JSON-RPC son correctos.
5. Repetir la tool de lectura cambiando el PAT en Inspector por el de un segundo usuario de prueba confirma que la respuesta cambia de acuerdo al usuario (mismo control de aislamiento que 4.1, ahora validado a través de la herramienta que efectivamente ejercita el protocolo MCP completo, no solo `curl`).
6. Los hallazgos de esta sesión de prueba (tools disponibles, comportamiento ante errores, particularidades del transporte) quedan anotados en la documentación del servicio MCP para que Epic 5 y la historia 4.3 los reutilicen sin repetir la exploración.

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** Prueba exploratoria/manual guiada con MCP Inspector como cliente de protocolo real, contra el MCP desplegado en 4.1 y una instancia Firefly III de desarrollo. No es testing automatizado de código propio — es validación de comportamiento de un componente de terceros bajo el contrato esperado (headers por-request, catálogo de tools).
- **Key scenarios:** (a) Inspector se conecta y completa el handshake; (b) `tools/list` devuelve un catálogo no vacío y coherente con la documentación de Firefly III; (c) una tool de lectura y una de escritura ejecutan correctamente con el PAT del usuario A; (d) la misma tool de lectura, con el PAT del usuario B, devuelve datos distintos; (e) una tool invocada con parámetros inválidos devuelve un error JSON-RPC legible, no un crash del servidor.
- **Per-AC verification:** AC #1 → captura de la conexión exitosa en Inspector; AC #2 → confirmación visual en Inspector de que el header `Authorization` está seteado por request y no por entorno; AC #3 → tabla de tools documentada (nombre, tipo de operación, parámetros); AC #4 → comparación de la respuesta de la tool de escritura contra el estado real en Firefly III (vía UI de Firefly o la propia tool de lectura); AC #5 → comparación lado a lado de las dos respuestas (usuario A vs. usuario B) confirmando que no coinciden; AC #6 → revisión de que la documentación del servicio MCP quedó actualizada con el catálogo y los hallazgos.
- **Fixtures / mocks:** los mismos dos PATs de prueba usados en 4.1 (o nuevos si los de 4.1 expiraron/fueron rotados); no se mockea nada — se prueba contra el MCP y Firefly III reales de desarrollo.
- **Edge cases to cover:** tool inexistente invocada por nombre incorrecto; parámetros faltantes o de tipo incorrecto en una tool de escritura; PAT expirado o revocado a mitad de sesión de Inspector; tool de escritura invocada dos veces seguidas (confirmar que no hay duplicación silenciosa de transacciones).

### Verificado en producción (2026-09-13)

Sesión de pruebas ejecutada con `@modelcontextprotocol/inspector` en modo **CLI**
(`--cli --server-url http://127.0.0.1:3100/mcp --transport http --header "Authorization:
Bearer <PAT>"`), contra el `mcp-firefly` desplegado en la historia 4.1, en la VPS de
producción. Node v22.23.1 (cumple el mínimo 22.19.0 de Inspector).

- **AC #1** — Conexión exitosa: `tools/list` respondió sin errores usando el transporte
  HTTP configurado en 4.1.
- **AC #2** — El PAT se pasó exclusivamente vía `--header "Authorization: Bearer $PAT_A"`
  por cada invocación (nunca como variable de entorno del propio Inspector), replicando
  el patrón que usará el Bot Service en Epic 5.
- **AC #3** — Catálogo completo: 140 tools, clasificadas en lectura (84), escritura no
  destructiva (37), automatización con efecto de escritura (3: `trigger_*`) y
  destructivas (16: `delete_*`). Documentado en [`mcp/tools-inventory.md`](../../mcp/tools-inventory.md)
  — insumo directo de la historia 4.3.
- **AC #4** — `get_accounts` (lectura) devolvió la cuenta real del usuario de prueba A
  (`id: "1"`, `name: "test"`, `current_balance: -60000.00 EUR`). `create_transaction`
  (escritura, `withdrawal` de `1.00 EUR` contra esa cuenta) creó la transacción `id: "4"`
  de verdad en Firefly III — confirmado por el `source_balance_after` devuelto en la
  respuesta.
- **AC #5** — El mismo `get_accounts` repetido con el PAT del usuario de prueba B
  devolvió `"data": [], "total": 0` — aislamiento confirmado a través del protocolo MCP
  completo (no solo `curl`, como en 4.1).
- **AC #6** — Hallazgos documentados en `mcp/README.md` (nueva sección "Sesión de
  pruebas con MCP Inspector") y `mcp/tools-inventory.md` (catálogo completo + resultado
  de la verificación funcional), listos para que Epic 5 y la historia 4.3 los reutilicen.

**Hallazgo adicional (no AC formal, útil para 4.3/Epic 5):** una tool inexistente
devuelve un error JSON-RPC legible (`tool_not_found`, exit code 5 en el CLI de
Inspector) sin crashear el servidor; un PAT inválido/vacío devuelve `isError: true` con
el error de autenticación de Firefly III reenviado tal cual, sin ningún fallback a un
token fijo — reafirma el diseño per-request verificado en 4.1.

Los 6 AC de la historia quedan verificados en producción.
