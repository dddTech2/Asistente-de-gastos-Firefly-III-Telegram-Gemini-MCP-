# 8.2: Tabla de auditoría de IA

**Story ID:** 8.2
**Epic:** 8 — Observabilidad y hardening
**Slug:** tabla-auditoria-ia
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As an **administrador del sistema**,
I want **una tabla de auditoría (`log_auditoria_ia`) que registre qué escribió cada usuario y qué tool ejecutó la IA en respuesta**,
so that **pueda revisar exactamente qué pasó ante cualquier duda — por ejemplo si Gemini interpretó mal un monto o categorizó algo de forma rara — sin tener que adivinar**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Existe una tabla `log_auditoria_ia` en Postgres con, como mínimo, las columnas: `chat_id`, `mensaje_original`, `tool_llamada`, `parametros`, `resultado` (éxito/error), `timestamp`, creada vía una migración versionada (no manualmente).
2. Cada vez que la IA (Gemini) ejecuta una tool call contra el MCP en respuesta a un mensaje de usuario, se inserta una fila en `log_auditoria_ia` con el mensaje original del usuario, el nombre de la tool invocada, los parámetros usados, y si la ejecución tuvo éxito o falló.
3. El campo `parametros` nunca contiene el PAT del usuario ni ningún otro secreto en texto plano, aunque la tool call internamente haya usado un PAT para autenticarse contra Firefly III — se registra la operación de negocio, no las credenciales de transporte.
4. Es posible consultar el historial de auditoría filtrando por `chat_id` y por rango de fechas (soportado por un índice adecuado, no un full table scan en producción).
5. A diferencia de `historial_conversacion` (TTL corto, ~24h), las filas de `log_auditoria_ia` no se purgan automáticamente — es un registro de auditoría de largo plazo.

## Dev Notes

- Requisito original: "Como administrador, quiero una tabla de auditoría que registre qué escribió cada usuario y qué tool ejecutó la IA, para poder revisar qué pasó ante cualquier duda" (HU-31, prioridad 🔴 alta). [Source: docs/plan/backlog-scrum-completo.md#épica-8-observabilidad-y-hardening]
- Esquema de referencia de la tabla, tal como está definido en el modelo de datos del Bot Service:
  ```
  log_auditoria_ia
   ├─ chat_id
   ├─ mensaje_original
   ├─ tool_llamada
   ├─ parametros
   ├─ resultado (éxito/error)
   └─ timestamp
  ```
  [Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive]
- El propio diseño explica el porqué de esta tabla: "`log_auditoria_ia` es la tabla que más vas a agradecer tener: si un día Gemini interpreta mal un monto o categoriza algo raro, necesitas poder ver *qué le escribiste* y *qué tool llamó con qué parámetros*, sin tener que adivinar." Esto fundamenta directamente el AC #2. [Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive]
- Nota importante sobre el motor de base de datos: el documento v1 dice que con volumen bajo "todo esto cabe perfecto en SQLite — no justifica un Postgres/Redis aparte" [Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive], pero el diseño v2 (50 usuarios) migra el estado persistente del Bot Service de SQLite a **Postgres** explícitamente para usuarios+PAT, y a Redis (TTL corto) para el historial de conversación [Source: docs/plan/system-design-v2-multiusuario.md#4-cambios-en-el-bot-service]. El v2 no vuelve a mencionar `log_auditoria_ia` explícitamente al listar esta migración de almacenamiento. Dado que es un registro persistente de auditoría (no efímero como el historial de conversación) y que Postgres ya es la pieza de persistencia durable en v2, se infiere que `log_auditoria_ia` debe vivir en Postgres junto a la tabla de usuarios, no en SQLite ni en Redis. [Inference]
- `resultado (éxito/error)` en el esquema de referencia se traduce en el AC #2 y en el diseño de columnas de la migración como un campo de estado, con espacio para el detalle del error — el documento no especifica el tipo de dato exacto (enum vs. texto libre), eso queda como decisión de implementación. [Inference]
- Distinción con la historia 8.1 (logs-estructurados): esta tabla es el registro de auditoría de negocio (qué pidió el usuario, qué tool se ejecutó), persistido en base de datos y sin purga; los logs estructurados de 8.1 son operacionales/técnicos, van a stdout, y no reemplazan esta tabla. Ambas historias pueden compartir el mismo punto de instrumentación (el sitio donde se ejecuta una tool call) pero escriben a destinos distintos con propósitos distintos.
- Requisito de protección de secretos que aplica también acá: "Si toca datos sensibles (PAT, credenciales), quedaron cifrados/fuera de logs" — se extiende por analogía a esta tabla de auditoría, que es igualmente un registro persistente y debe seguir el mismo principio de no almacenar PAT/credenciales en `parametros`. [Source: docs/plan/backlog-scrum-completo.md#4-definition-of-done-dod]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** test de migración (arriba/abajo) sobre una base Postgres de prueba; tests unitarios del servicio de sanitización de parámetros; test de integración que ejecuta una tool call simulada de punta a punta y verifica que la fila de auditoría queda escrita correctamente.
- **Key scenarios:** tool call exitosa queda registrada con `resultado = success`; tool call que falla (ej. Firefly III devuelve error) queda registrada con `resultado = error` y detalle; un `parametros` que originalmente incluía un header `Authorization: Bearer <PAT>` se guarda sin ese valor; una consulta por `chat_id` + rango de fechas devuelve solo las filas correspondientes.
- **Per-AC verification:** AC #1 → correr la migración contra una base de prueba y verificar el esquema de la tabla resultante (columnas y tipos); AC #2 → test de integración que simula una tool call y verifica que aparece exactamente una fila nueva con los campos esperados; AC #3 → test unitario del sanitizador con un payload de parámetros que incluye un campo sensible, assert de que no aparece en la fila persistida; AC #4 → test de la consulta con datos de al menos dos `chat_id` distintos y fechas distintas, verificando que el filtro no devuelve datos de otro usuario ni fuera de rango; AC #5 → inspección de la migración y de cualquier job de purga (ej. cron de limpieza de `historial_conversacion`) para confirmar que no incluye esta tabla.
- **Fixtures / mocks:** base Postgres de prueba (contenedor efímero o esquema de test); payload de tool call simulado con parámetros que incluyen un campo `authorization` de prueba; al menos dos `chat_id` de prueba para verificar el aislamiento del filtro.
- **Edge cases to cover:** `parametros` vacío o `null` (ej. una tool sin argumentos); `mensaje_original` muy largo (sin truncar silenciosamente sin dejar rastro); fallo de escritura en la tabla de auditoría (ej. Postgres no disponible) no debe tumbar la respuesta al usuario — debe degradar registrando el fallo vía el logger de 8.1, no lanzar una excepción no controlada.
