# 5.4: Pedir aclaración cuando el dato es inválido, en vez de fallar en seco

**Story ID:** 5.4
**Epic:** 5 — Integración con Gemini (conversación en lenguaje natural)
**Slug:** aclaracion-dato-invalido
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **usuario**,
I want **que si el dato que doy es inválido (cuenta/categoría inexistente), el bot me pida aclaración en vez de fallar en seco**,
so that **no pierda el registro del gasto que ya estaba armando**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Cuando el MCP/Firefly III devuelve un error de validación específico (ej. cuenta o categoría inexistente) al ejecutar una tool, el Bot Service reconoce ese error como "dato inválido" (no como una falla genérica) y lo reenvía a Gemini como resultado de la tool en vez de propagar una excepción cruda al usuario.
2. Ante un error de dato inválido, Gemini (guiado por el system prompt) le hace al usuario una pregunta de aclaración concreta (ej. "no encontré la categoría 'comida rápida', ¿quisiste decir 'Comida'?") en vez de mostrarle un error técnico o fallar en silencio.
3. Los datos ya capturados del gasto en curso (monto, descripción, fecha) se conservan durante el turno de aclaración — usando el historial de conversación (`historyStore`, de 5.1) — de forma que el usuario no tenga que repetirlos al responder la aclaración.
4. Una vez que el usuario aclara el dato (ej. "sí, esa" o "categorízalo como Comida"), el Bot Service reintenta la tool con el parámetro corregido y completa la transacción, confirmando el éxito al usuario.
5. Errores genéricos/inesperados (fallas de red, 5xx de Firefly) NO disparan el flujo de aclaración — siguen el comportamiento de fallback ya definido ("servicio no disponible por ahora"), diferenciando explícitamente error de validación vs. falla técnica.

## Tasks / Subtasks

<!-- Every task maps to one or more ACs via (AC: #N). A task with no AC mapping is a smell. -->

- [ ] Crear `src/gemini/errorClassifier.ts`: clasifica el resultado de una tool fallida en `validationError` (cuenta/categoría inexistente u otro dato inválido identificable) vs. `technicalError` (red, timeout, 5xx) (AC: #1, #5)
- [ ] Modificar `messageOrchestrator.ts` (de 5.1) para que, ante un `validationError`, reenvíe el error como resultado de tool a Gemini en vez de cortar el flujo; ante un `technicalError`, mantenga el fallback existente ("servicio no disponible por ahora") (AC: #1, #5)
- [ ] Crear `src/gemini/prompts/aclaracionDato.prompt.ts` con guía/ejemplos para que Gemini formule una pregunta de aclaración específica ante un `validationError` (AC: #2)
- [ ] Registrar el fragmento de prompt de aclaración en `promptBuilder.ts` (de 5.1) (AC: #2)
- [ ] Verificar que los datos parciales del gasto en curso queden en `historyStore` (de 5.1) durante el turno de aclaración, y que el prompt del siguiente turno los incluya (AC: #3)
- [ ] Verificar el reintento de la tool con el parámetro corregido tras la respuesta de aclaración del usuario, confirmando éxito al usuario (AC: #4)
- [ ] Tests de clasificación de errores, de la rama de aclaración del orquestador, y del flujo completo de dos turnos (error → aclaración → éxito) (AC: #1, #2, #3, #4, #5)

[Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive]
- Reintentos con backoff en llamadas a Gemini (rate limits) y a Firefly (timeouts de red) son parte del manejo de errores general del Bot Service, pero corresponden a fallas técnicas (HU-26, Épica 6), no a datos inválidos — esta historia no debe implementar backoff, solo clasificar y enrutar el error. [Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive]
- Esta historia depende de `historyStore` (Redis, TTL corto) creado en 5.1 para conservar el contexto del gasto parcial entre el turno del error y el turno de aclaración del usuario — es el mismo mecanismo que 5.5 endurece para memoria conversacional general, pero acá se usa específicamente para no perder datos ya capturados durante una aclaración. [Source: docs/plan/system-design-v2-multiusuario.md#4-cambios-en-el-bot-service] [Inference]
- `log_auditoria_ia` (resultado éxito/error) es la referencia de qué datos de auditoría capturar cuando una tool falla por validación — relevante para que 5.1's logging estructurado incluya el motivo de rechazo, aunque la tabla formal es de la Épica 8 (HU-31). [Source: docs/plan/system-design-asistente-gastos.md#3-deep-dive]
- La forma exacta del mensaje de error que devuelve el MCP/Firefly ante una cuenta o categoría inexistente (código HTTP, estructura del payload) no está documentada en los planning docs disponibles — se asume (validar contra el MCP real en desarrollo) que Firefly responde con un error 422 de validación distinguible de un error 5xx/timeout. [Inference]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** unitario para `errorClassifier` (tabla de casos de errores de ejemplo → clasificación esperada); integración liviana para la rama de aclaración de `messageOrchestrator` con mocks de Gemini y del MCP client cubriendo el flujo de dos turnos.
- **Key scenarios:** error de validación por cuenta inexistente; error de validación por categoría inexistente; error técnico (timeout/5xx) que NO debe disparar aclaración; flujo completo de dos turnos (mensaje inicial con dato inválido → pregunta de aclaración → respuesta del usuario → transacción completada).
- **Per-AC verification:** AC #1 → test de `errorClassifier` clasifica correctamente un error de ejemplo de cuenta/categoría inexistente como `validationError`; AC #2 → test del orquestador verifica que, ante `validationError`, se llama a Gemini con el prompt de aclaración y se obtiene una pregunta de vuelta al usuario (no un error técnico mostrado tal cual); AC #3 → test verifica que `historyStore` contiene los datos parciales (monto, descripción, fecha) entre el turno de error y el turno de aclaración; AC #4 → test de flujo de dos turnos verifica que el segundo mensaje del usuario dispara un reintento de la tool con el parámetro corregido y una confirmación de éxito; AC #5 → test de `errorClassifier` con un error técnico simulado (timeout) verifica que se clasifica como `technicalError` y dispara el fallback existente, no la rama de aclaración.
- **Fixtures / mocks:** payloads de error de ejemplo del MCP/Firefly (validación de cuenta inválida, validación de categoría inválida, timeout de red, 500 genérico); mock de Gemini que devuelve una pregunta de aclaración dado un `validationError`; mock de `mcpToolExecutor` para el reintento exitoso tras la aclaración.
- **Edge cases to cover:** el usuario responde la aclaración con algo ambiguo o fuera de tema (no hay AC explícito para esto — documentar como comportamiento no definido, posible seguimiento futuro); dos errores de validación en la misma llamada (ej. cuenta Y categoría inválidas a la vez) — documentar comportamiento esperado (aclarar uno o ambos) como decisión a validar en desarrollo; el usuario abandona la conversación antes de responder la aclaración (el TTL corto de `historyStore`, de 5.5, eventualmente purga el dato parcial — comportamiento esperado, no un bug).
